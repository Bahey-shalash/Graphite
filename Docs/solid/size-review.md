# Size review: when a big file, type or function is allowed to stay big
Snapshot: b13dec3 (main, 2026-10-18).

`scripts/size-report.py` measures code lines (comments, string contents and blank lines removed; interpolated code inside strings is kept) per file, per type (declaration plus same-file extensions) and per function (including computed properties and `body`). The thresholds are in the table below. The script exits with status 1 while an item over a threshold has no row in the register of section 4 of this document, or grew by more than a fifth since its row was written. [size-items.md](size-items.md) lists the 285 items over a threshold at this snapshot. The measure comes from the script; where an area document gives a different count for the same item (its reconnaissance counter handled string interpolation differently, or it counted a type across files), the register uses the script's number.

| Level | Function | Type | File |
| --- | ---: | ---: | ---: |
| Review (a row is required) | over 40 | over 300 | over 400 |
| Strong reason needed | from 80 | from 600 | from 500 |
| Structural smell | n/a | n/a | over 1,000 |

## 1. The rule

A size never forces a split and never forbids one. A size asks one question: **does this item have one responsibility at one level of abstraction?**

- If the answer is yes, the item stays whole and its row says `one concept` with the reason in one sentence.
- If the answer is no, the row says `split planned` and names where each part goes, by role.
- A number alone is never an answer. A 400-line file of one concept is correct; a 150-line type that mixes persistence and drawing is not.
- A long straightforward sequence stays whole: a SwiftUI form, a table of cases, a mapping `switch` with one case per value (`MarkdownTextStyler.apply`, row `one concept` in the register; `CC-EDITOR-01`), a flat token table (`ThemeProbeReading.tokens`, `CC-PLUGIN-11`).
- A function over 80 lines, a type over 600 or a file over 500 needs a stronger reason than "it reads in order": the row must state the responsibilities it contains.

## 2. Reasons to split

Split when at least one of these holds. Each reason is checkable by reading the item.

1. The item needs a name like `Manager`, `Helper`, `Utils` or `Misc` (`PDFPageManager.swift`, `SRP-LECTURE-06`).
2. Its parts change for different reasons (a key registry, an edit interpreter and file I/O in one file, `SRP-LECTURE-06`).
3. A section could be tested on its own (pure edits of a lasso selection, `SRP-INK-02`; narration masking, `SRP-VOICE-02`).
4. It holds unrelated types (`MarkdownSemantics.swift`: 18 types, 11 unrelated, `SRP-MDCORE-04`).
5. Understanding it means jumping around (the iPad coordinator's ordering rules are spread over 16 responsibilities, `SRP-EDITOR-01`).
6. Unrelated work conflicts in it (`NativeMarkdownEditor.swift` is touched by 41 of 242 commits, `SRP-EDITOR-01`).
7. One subsystem's private details clutter another's API (plugin view state written by a `WorkspaceModel` extension, `SRP-PLUGIN-04`).

Rules for how to split:

- Name the parts by role: a lexer, a parser and a generator, never `Part1`/`Part2`, never `Extensions2`.
- Never move code only to beat a number. A move that leaves the same responsibilities in the same order under a new name is not a split.
- One concept per file, named after it. A file split follows the types; a type split follows the responsibilities.
- A new protocol appears only where `RULES.md` allows it: a real second implementation or a test need. A split does not add one protocol per part and leaves no forwarding shim behind (`RULES.md`).

## 3. How to review

1. **List the stored state and the functions by responsibility.** The area documents' responsibility maps (section 3 of each area document) are the model: one row per responsibility, with its stored state and its functions.
2. **List the calls that cross responsibilities and the ordering rules the code relies on.** A split must keep them; write them down before moving anything.
3. **Decide per item: one concept or split.** Apply the question of section 1 and the reasons of section 2.
4. **Split along the responsibilities.** Name each part by role. Keep the coordinating type thin: it wires and holds no logic.
5. **Pin behaviour first.** A characterization test exists before the code moves; the blueprint of each area lists the first steps.
6. **Record the outcome in the same commit that crosses a threshold.** A new item over a threshold gets its row in that commit. A split that brings an item under its threshold deletes that item's row in the same commit. An item that grows by more than a fifth over its row is reviewed again.

The register columns: `File` (repository-relative path), `Declaration` (`(file)`, `Type` or `Type.function`, exactly as the script names it), `Code lines at review` (the number in [size-items.md](size-items.md)), `Outcome` (`one concept` or `split planned → <where the parts go>`), `Why` (one sentence naming the finding that decides it).

Two script behaviours matter when reading a row. The script merges all blocks of one type name inside one file (the iPad and the Mac `NativeMarkdownEditor` and `Coordinator` are one item each), and it counts overloads of one function name as the largest (`NativeMarkdownEditor.update`, iPad 46 and Mac 42, is one item at 46).

Rows exist only for items an area document reviewed: a responsibility map or a finding that names the item and states one concept or a split. Items no area document assessed have no row; they are listed under "Not yet reviewed" so the script keeps reporting them.
