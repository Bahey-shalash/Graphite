# Graphite architecture review

Graphite is a native Apple Pencil-first knowledge and study app that gives an Obsidian vault the notebook and PDF capabilities of Goodnotes without giving up open files.

## Assessment

Graphite is a Swift package with a thin Xcode application target. The intended product includes the full Markdown, notebook, PDF, recording, and knowledge-management requirements. What is implemented and verified today is tracked in `Docs/Coverage.md`, separately from this architecture.

The [SOLID and clean-code standard](solid/README.md) assesses the implementation against `RULES.md` from a line-by-line audit of `b13dec3` (2026-10-18): Core value types, file formats and storage contracts are sound; the coordinating layer (`WorkspaceModel`, no composition root, rules implemented more than once) is not. Its [rule status](solid/rule-status.md) and [finding status](solid/status.md) are the current assessment; architecture intent alone does not establish compliance.

The most valuable property of the architecture is explicit resource ownership. File access, indexing, open documents, thumbnail generation, and recording have separate lifetimes and queues. Opening a document does not depend on initial indexing completing. Typing does not publish changes to a vault-sized observable collection.

## Modules and dependency direction

Read aloud is partially implemented; [the checklist](Read-aloud-todo.md) retains the complete requested scope. Core's `ReadAloudDocument` reuses swift-markdown, the existing Obsidian syntax scanners, and the shared Markdown source-location converter. It prepares bounded spoken passages with UTF-16 source mappings, filters requested Markdown ranges after parsing the entire note, and rejects partial equations or unreliable mappings. Mathematical preparation is a synchronous throwing capability supplied by the caller. Core's default `MathSpeech` remains a conservative pure Swift subset; the production Apple reader supplies the structured interpreter described below. Unsupported expressions are announced rather than speaking commands or inventing mathematical meaning.

Apple's `ReadAloudSpeaking` boundary supplies installed voices, playback controls, cancellation, actual spoken-range events, the system's default voice per language, Personal Voice access, and the release of the audio session. `AppleReadAloudSpeech` offers Apple's natural voices only: it excludes novelty voices, third-party voice extensions, the MacinTalk (`com.apple.speech.synthesis.voice.*`: Fred, Kathy, Ralph…) and Eloquence (`com.apple.eloquence.*`: Eddy, Flo…) families, and lists a Personal Voice only once the person allowed Graphite (`requestPersonalVoiceAccess`, called only from the "Use My Personal Voice…" button). `ReadAloudVoice.preferred` ranks Personal Voice, then Apple's quality tier (Premium, Enhanced, compact), then the exact region, then the system's default voice for the language. `ReadAloudSession` keeps the person's explicit choice for Graphite (`GraphiteReadAloudChosenVoice`; the earlier key also stored automatic choices and is ignored). Without one it follows the system: it speaks with `AVSpeechSynthesisVoice(language:)` for the passage's language, whatever that voice's family, and sets `prefersAssistiveTechnologySettings`, which Apple documents as applying the person's own voice, rate and other speech settings while an assistive technology is on (the header says "like VoiceOver"; whether Speak Selection, Speak Screen and iOS 27's Timbre, Sentence Pause and Equalizer count is not documented), and the utterance's own values otherwise. The iOS 27 SDK's `AVSpeechSynthesis.h` adds no public API for timbre, sentence pause or effects. While VoiceOver, Speak Selection or Speak Screen is on (`UIAccessibility`), Graphite hides its own speed, because the system's rate replaces it; the passage-type pauses use `preUtteranceDelay`, which is not among the replaced settings. When the system has no voice for the language, the session falls back to the best installed voice for the passage's language, which `ReadAloudLanguage` recognizes on device with NaturalLanguage (first 4,000 UTF-16 units, confidence ≥ 0.6, device language otherwise). It reports when only compact voices exist for that language, so the UI can point to the system's voice settings (Settings › Accessibility › Read & Speak › Voices on iOS 27, Spoken Content before). No public URL opens that page, so Graphite names the path instead of offering a button. It owns passage progression, previous/next sentence and passage repeat, rate, stale-callback rejection, interruptions, and pause/resume. Between passages it passes a leading pause to the adapter (`preUtteranceDelay`) from `ReadAloudPassageKind`: 0.6 s around a heading, 0.35 s after a paragraph, 0.25 s after a list item, table row or PDF line, divided by the speed. On iOS the adapter activates the shared audio session as `.playback`/`.spokenAudio` when it first speaks and deactivates it (notifying other apps) when reading stops or finishes, but only while the category is still its own, so a lecture recording's session is never deactivated. An interruption pauses; when it ends with `shouldResume`, reading resumes only if it was speaking. Unplugging the output (`oldDeviceUnavailable`) pauses; a new route does not. Premium and Enhanced are Apple's quality tiers, not evidence that a voice meets the owner's human-sounding acceptance gate; the owner rejected the macOS Enhanced Siri voice ("Voice 4", `com.apple.siri.natural.Nora`) on 2026-10-11, and no Premium voice has been auditioned on a device. No cloud speech provider has been introduced.

Apple's `ReadAloudMarkdownPreparation` actor lazily owns a JavaScriptCore interpreter with a bundled offline MathJax 4.1.3 and Speech Rule Engine 4.1.4. Original LaTeX becomes MathML through base/AMS/boldsymbol/color packages, then English ClearSpeak (concise) or MathSpeak (detailed). This supports structured sums, products, bounds, integrals, limits, derivative notation, vectors, matrices, piecewise expressions and aligned rows. It does not recover LaTeX from a PDF or infer missing notation. Source expressions are function arguments, never executable scripts. The environment adapter supplies bundled XML/XPath implementations and English rule maps, with no native filesystem/network bridge, browser, Node runtime or runtime downloads. A fresh MathJax parser isolates expression state; external inclusion, URL/HTML extensions and user macro-definition packages are unavailable. [Dependency versions, licenses, rebuild instructions and runtime bounds](../Vendor/math-speech/README.md) are checked in; full runtime licenses ship in the resource bundle.

Math preparation is bounded to 8,192 source UTF-16 units, 32 nested source groups/delimiters, 256 substitutions, 4,096 MathML nodes, 64 tree levels, 65,536 serialized MathML units and 32,768 spoken units per expression. Its FIFO cache holds at most 128 requests and 262,144 combined source/spoken UTF-16 units. Cancellation is checked between bounded expressions; JavaScript is not interrupted mid-expression. Startup/resource failures surface as preparation errors. Math detail is a device-local preference; changing it rebuilds the same requested range, invalidates prior playback callbacks, and waits for Play. Edits clear the retained source snapshot. Voice samples use the same actor and math style; preview preparation is canceled on Stop, playback changes and sheet dismissal.

Core's `ReadAloudAudioTiming` validates character timing against the exact UTF-16 spelling of a prepared passage, checks finite ordered timestamps against decoded audio duration, and groups timings into Foundation word ranges. Playback-clock queries return no word during silence. It is a tested foundation for another speech engine, not an integrated audio player or cloud provider. It rejects normalized or altered provider text rather than guessing source locations. Input is bounded to the existing 1,200-unit utterance budget and ten minutes of audio.

Narration of Markdown reads tables row by row with each body cell introduced by its column header ("Gate: NAND, Inputs: 2"), reads a callout's title as its own heading, says a web address as "link to example.com", and expands e.g., i.e., w.r.t., vs., cf. and, before a number, Fig., Eq., No. and pp. Each replacement is a non-verbatim span over the written text with that text kept in `ReadAloudSpan.writtenText`, so `ReadAloudSourceToken` still yields the written words for rendered-block alignment. swift-markdown's smart punctuation (’ “ ” – — …) maps back to the plain characters written; any other rewritten character maps to the rest of its text run and the mapper resynchronizes on the next character, instead of refusing the note. Display math inside a callout or quote has its "> " markers removed before interpretation. `ReadAloudDocument.pageText` prepares a PDF page or selection: bullet glyphs and dot leaders are not spoken; a line that ends without punctuation before a capitalized or bulleted line becomes its own passage (`.line`); continuing lines join, a line-end hyphen before a lowercase word joins without a space; a first or last line that is short, unpunctuated and carries the page number or printed label is dropped as a running header or footer, and its text is remembered by the controller for the following pages of the same read, where pieces of it near the top or bottom are dropped too.

Highlighting (2026-10-12, third round): `ReadAloudSession.highlightRange` follows Settings › Read Aloud › Highlight While Reading (Words, the default; Sentences; Off). A voice that reports no word position within 0.7 s of `didStart` is remembered for the session and its passages are highlighted whole; ranges with no letter or digit (a dash) are ignored. `ReadAloudHighlightStyle` is one dynamic blue fill (24 % light, 40 % dark, 36 %/55 % with Increase Contrast) for Live Preview, the reading view, PDFs and the transcript, distinct from `==highlight==` yellow. `ReadingSourceAlignment` compares words after mapping ’ ‘ ʼ to ', “ ” to " and – — to -, because the voice's text carries the parser's typographic marks while the reading view shows what was typed; before, any such character disabled its whole block's highlight. `MarkdownTextView` measures its highlight only when the range, width or content height changes (not on every scroll frame), reveals only a new word, never while the person drags or the view decelerates, and places it a third of the way down; the reading view does the same. A person's scroll pauses following, which resumes five seconds after the last scroll (`ReadAloudController.followResumptionDelay`) or from Follow Reading. The stored voice keys of earlier builds (`GraphiteReadAloudVoice`, `GraphiteReadAloudChosenVoice`) are removed at launch; a choice is stored as `ReadAloudVoiceChoice` (identifier and source: picker or Personal Voice button) under `GraphiteReadAloudVoiceChoice`. Eloquence, MacinTalk and novelty voices are flagged `isRobotic`, listed under Classic and used only when picked there; they are never the automatic choice, the fallback, or the utterance voice when the system's default is one of them.

Pronunciation: `ReadAloudPronunciations` (Core) holds a built-in list of computing and VLSI terms with a respelling and, for terms said as words, IPA; plurals add "s" or "'s"; an unknown all-caps word without a vowel is spelled; other words are left to the voice. A vault's `.graphite/pronunciations.json` (at most 256 KB, read off the main thread by `ReadAloudMarkdownPreparation.pronunciations(vaultRoot:)`) adds or replaces terms. Replacements are non-verbatim spans keeping `writtenText` and `phoneticNotation`; `ReadAloudUtteranceRequest` carries IPA ranges, which `AppleReadAloudSpeech` sets as `AVSpeechSynthesisIPANotationAttribute` on an attributed utterance, so a voice that ignores IPA reads the respelling.

Read Aloud as a core plugin (2026-10-19, `Read-aloud-core-plugin.md`): Read Aloud is a core plugin (`CorePlugin.readAloud`) that is off by default (`CorePlugin.isEnabledByDefault`). `CorePluginSwitches` keeps, per device, the plugins on by default that were turned off (`GraphiteDisabledCorePlugins`) and those off by default that were turned on (`GraphiteEnabledCorePlugins`). `CorePluginSwitchMigration` runs once, in `WorkspaceDeviceServices`, while the second key has never been written: a device with a Read Aloud preference (a key starting with `GraphiteReadAloud` or `readAloud`) or a downloaded voice in `Application Support/Voices` keeps Read Aloud on, unless it was turned off before. `WorkspaceModel.readAloud` and `readAloudNavigator` exist only while the plugin is on: the controller comes from the factory `WorkspaceDeviceServices.makeReadAloudController` (the app's is `ReadAloudVoices.makeController`), so with Read Aloud off no voice library, MLX renderer, speech synthesizer or Now Playing entry is made. `WorkspaceModel.setCorePluginEnabled` builds them when the plugin is turned on, without a relaunch, and when it is turned off stops reading (`ReadAloudController.clearAndLeaveNowPlaying`: speech, audio session, rendering ahead, the lock screen entry), closes the reader and drops them. Every entry point reads the optional: the More › Read Aloud menus of notes and PDFs, the editor's Read from Here and tap to read, the Play Next and Add to Listening Queue items of the file list and tabs, the PDF Read Aloud pen (in the tab bar's Pencil tools too), the floating player, the toolbar controls, the reader sheet, the highlight in notes and PDFs, the `graphite://read` link and Settings' Read Aloud page and Voice Credits. The Read Aloud page is listed in the sidebar's Core Plugins section while the plugin is on. Turning it off deletes nothing; Settings then offers to delete the downloaded voices and prepared audio, which happens only on confirmation. Two modes (`ReadAloudQualityMode`): **High Quality**, the default once a voice is downloaded, and **Quick**, the system voice through `AppleReadAloudSpeech`. `NeuralReadAloudSpeech` (GraphiteVoices) implements `ReadAloudSpeaking` for both: in Quick mode, or with no downloaded voice, it passes every call to the system voice; in High Quality mode it plays passages that `ReadAloudPassagePreparation` rendered ahead. `ReadAloudSession` hands it the document's passages from the one being read (`prepareAhead`), and requests now carry the whole passage and the offset the spoken text starts at (`passageText`, `passageOffset`), so resuming inside a passage plays its audio from the first word at that offset. Preparation renders one passage at a time in reading order, moves a passage the reader is waiting for to the front, retries a failed render once, frees the model when the queue is done, and stops while the app is inactive or in the background (iOS refuses graphics work there; `willResignActive`/`didBecomeActive`). A passage that is not ready waits ("Preparing… 40%" in the toolbar and the controls popover, from `preparedShare`, the rendered share of the queued text in characters), unless the person turned on Read Unprepared Passages with System Voice (Settings › Read Aloud and the popover), which also releases a passage already waiting. Rendered passages live in Caches/ReadAloudAudio, never in the vault (`ReadAloudAudioCache`): AAC at 64 kbit/s plus a JSON file of word timings per passage, named by `ReadAloudAudioCacheKey`, a SHA-256 of the spoken text (with pronunciation respellings applied), the voice, its pinned revisions and `renderSettingsVersion`; speed is not part of it (playback applies it with `AVAudioUnitTimePitch`, pitch unchanged), so an edited note re-renders only the passages whose text changed. The cache keeps an index of sizes and last use and removes the least recently used passages past 250 MiB, never those of the document being read. Playback (`RenderedPassagePlayer`) uses `AVAudioEngine` with an `AVAudioPlayerNode`; pause holds the place within a passage; interruptions stop and report as the system voice's did; the audio session is `.playback`/`.spokenAudio` as before. Word highlight: after a passage is rendered, `OnDeviceSpeechAlignment` runs SpeechAnalyzer/SpeechTranscriber (iOS and macOS 26+) with `audioTimeRange` on the AAC file, and `ReadAloudWordAlignment` (Core) matches the recognized words to the passage's words by a global sequence alignment (exact, plural/one-letter and shared-stem matches), spreads unmatched words over the gap between their matched neighbors by length, and refuses the result when fewer than half the words match; the session then highlights the passage, as it already did for voices without word callbacks. A 20 Hz timer reports the word under the player's clock as `.spoken` ranges, so the Words/Sentences/Off highlight and the source mapping work unchanged.

Guarding against babbling (2026-10-12): autoregressive codec models (Qwen3-TTS, Chatterbox Turbo, Dia; `NeuralVoiceModelFamily.writesAcronymsAsWritten`) loop, invent words or make noise on letter-by-letter respellings and short lists, so (1) `ReadAloudVoiceText` gives them acronyms as written ("VHDL" for the passage's "V H D L"), keeps word respellings ("see moss"), and maps recognized ranges and resume offsets back to the passage; Pocket TTS keeps every respelling; (2) `NeuralSpeechEngine` renders them one sentence group (at most 260 characters) at a time with temperature 0.7, top-p 0.9, a repetition penalty and a token budget of about twice the text's expected length (`ReadAloudRenderCheck.expectedDurationSeconds`: 14 characters a second plus pauses at commas and sentence ends), and takes a seed; (3) `ReadAloudPassagePreparation` checks every rendering with `ReadAloudRenderCheck` against the passage as written (`ReadAloudVoiceText.writtenText`, which is how recognition writes it): at least 80 % of its letters heard in order, at most 1.8 times (and 4 s over) the expected length, no word or syllable looping four times where the text does not, no silence over 2.5 s inside it. A rejected rendering is tried once more with a random seed, then read by Pocket TTS from the passage's own text when Pocket TTS is installed (`NeuralVoiceLibrary.fallbackVoice`; the cache records `readsPassageText` so the highlight maps correctly), and otherwise left to the system voice (`systemVoiceTexts`); rejections are logged (`com.graphite.study`, category ReadAloudVoices). Settings › Read Aloud lists the downloadable voices on the page itself (High Quality Voices), with voices the device cannot run shown with the reason (`NeuralVoiceLibrary.unavailabilityReason`). Round 4's floating player shows "Preparing… 40%" while reading waits and "Prepared 60%" while rendering ahead, and is hidden with the plugin off.

Downloadable voices (`NeuralVoiceManifest`, Core; the list is `Sources/GraphiteVoices/Resources/NeuralVoices.json`): each voice names its model family, speaker, language, a measured quality note, its license and attribution, the platforms and least device memory it is offered on, and the files it needs per source repository at a pinned commit, with byte counts and SHA-256 checksums. Addresses are `<downloadHost>/<repository>/resolve/<revision>/<path>` (host https://huggingface.co), so a mirror changes only the host. The manifest is checked on load (format version, unique identifiers, paths that stay inside the voice folder, 64-digit checksums). `NeuralVoiceDownloader` downloads file by file in a background `URLSession` (`com.graphite.study.voice-downloads`; the iOS scene answers `.backgroundTask(.urlSession)`), moves each file into `<voice>.partial` in Application Support/Voices (excluded from backup), verifies size and SHA-256, keeps resume data for a lost connection (three automatic retries, then Paused with Resume), and installs by moving the folder into place with a `.graphite-installed` marker naming the revisions; a folder without a matching marker is never treated as a voice. Settings › Read Aloud lists each voice with its model, size, license and quality note, with Download, Pause, Resume, Cancel, Delete (confirmed) and Use This Voice, plus Voice Credits (also in Settings › General › About › Voice Credits; Pocket TTS's CC BY 4.0 requires one). `graphite://read?vault=…&file=…` opens a note and reads it aloud, for Shortcuts and for device checks.

The models run with MLX through a trimmed, patched copy of mlx-audio-swift (`Vendor/mlx-audio-swift`, MIT; Pocket TTS, Qwen3-TTS, Chatterbox and Dia only; changes in its `GRAPHITE-PATCHES.md`). `NeuralSpeechEngine` (an actor) loads a voice from its folder with no network access, renders on the graphics processor, turns MLX errors into thrown errors (`withError`, checked before reading samples, because reading an array whose computation iOS refused dereferences a missing buffer), streams Qwen3-TTS's decoder a second at a time, and keeps Dia on one voice with `DiaVoicePrompt` (`Resources/DiaVoicePrompt.json`, the codec codes of one of Dia's own clips from the owner's blind test; never a real person's voice). Nothing MLX is touched before a voice loads, because the Simulator ends the app on the first MLX call; on the Simulator a voice can be downloaded but not run. `-GraphiteVoiceBenchmark passages|sustained|background|alignment` opens a measuring screen instead of the workspace (`NeuralVoiceBenchmarkScreen`), which writes JSON results, WAV files and a log to Documents/VoiceBenchmark for `devicectl device copy from`; the measurements are in `Coverage.md`.
Fourth round (2026-10-12): `ReadAloudPronunciations.replacements(in:)` respells technical words from a built-in list of about 280 terms mined from the owner's notes (`ReadAloudPronunciationTerms.swift`; terms said in full are marked `isExpansion`, FF only near circuit words), numbers with about eighty unit symbols, prose subscripts (V_DD, V_{th}) and symbols; a lone subscripted equation ($V_{DD}$) is said the same way before the math interpreter. Plain respelling is the default; IPA is handed over only with `usesPhoneticNotation`, which nothing turns on, because the owner's Enhanced voice mangled it. Settings › Read Aloud › Pronunciations edits the vault's `.graphite/pronunciations.json` (written atomically) and lists the expansions. `ReadAloudFolding.hiddenRanges` leaves out folded heading sections and list items (`NoteFolding`) and collapsed callout bodies (titles stay); callout expansion lives in `CalloutFoldStore` (per note, per session) shared by the reading view and Live Preview, and `ReadAloudController.foldsDidChange` prepares the note again and resumes at the same place when folds change while reading. PDFs: `PDFReadAloudSource.page(_:pageIndex:livePageText:)` aligns the exported page's text to the live page's with a character difference, so words keep exact positions when PDFKit extracts a re-saved page differently; highlight text comparison ignores whitespace. `ReadAloudDocument.pageText` joins hyphenated line breaks (soft hyphen always; a form seen hyphenated on the page stays a compound; otherwise joins when the joined word is on the page or in `ReadAloudSpelling`'s system dictionary) and drops symbol-font bullets. `ReadAloudNavigator` (owned by the workspace) moves reading by section or page, to a tapped location, to the first visible line after scrolling away, runs the listening queue, and remembers the last place per note (source location) and PDF (page) in user defaults; `ReadAloudNowPlaying` maps next and previous track to the queue and skip forward and back to sentences. `ReadAloudFloatingPlayer` is the floating control (Settings › Read Aloud › Floating Player); its fifth-round layout is described below. The editor's tap and edit-menu "Read from Here" go through `ReadAloudEditorHooks`; the reading view has no tap-to-read yet. Speed ranges from 0.5× to 3×; `AppleReadAloudSpeech.rate(forSpeed:)` spreads speeds above 1× over the remaining rate range.

Fifth round (2026-10-12): the floating player follows the system's Spoken Content controller. `ReadAloudFloatingPlayer` is a dark panel in both appearances (`ReadAloudPlayerBackground`: thick material under 42 % black, 62 % with Increase Contrast plus a light edge, opaque #1C1C1E with Reduce Transparency) with white system labels only: a top row with the document's icon and name and, when both fit, the heading or page (or "Preparing… N%", "Prepared N%", "Reading Selection" with Repeat, a range prompt, an error, or Back to Reading and Read from Here while following is paused), and a row of speed (menu), back and forward a sentence (a long press, or a VoiceOver action, moves a section or page), Play or Pause, Stop (`ReadAloudNavigator.stopAndRewind`) and the page button (sections or pages, Transcript and Voice, Start Over, range, Repeat, Up Next); a round close button on its corner stops reading. Glyphs grow with the text size up to 1.3 times and the panel stops growing at accessibility size 1, so the six 44-point controls always fit; each shows in the Large Content Viewer. `ViewThatFits` is not used there: in that panel it made an AttributeGraph cycle that kept the note under it from loading. `ReadAloudPlayerPlacement` puts the panel at one of six places (bottom center first, or where it was dragged) and takes the first of the saved place, the other edge and their neighbors that is clear of the word read and of what covers the window; the PDF view reports both (`GraphitePDFView.reportReadingHighlightFrame`, `reportPaletteFrame`: the floating Pencil palette's frame, or the bottom 150 points while it floats on iPad, where `PKToolPicker.frameObscured` reports nothing). The Read Aloud pen (`PencilToolKind.readAloud`, `ReadAloudPenGlyph`, the laser's pointer with two blue sound waves) is in the fixed Pencil bar and the floating palette's menu on PDF pages, not on drawings, which have no text. On a canvas it is `ReadAloudPenController`, a tap recognizer that takes the touches the canvas would draw with and no resting hand (`CanvasToolTouches`), and the canvas does not draw meanwhile. `PDFAnnotationCoordinator.handleReadAloudPenTap` finds the word under the tap (or the whole page when the page has no text) and `ReadAloudNavigator.penTapped` decides: a first tap reads from the word to the end and marks it; a second tap, while that is read, reads exactly from the first word through the second (`readPDFRange` with both ends, so High Quality prepares only that range), with Repeat replaying it; a third starts over. The marks are `ReadAloudPenMarkerView`s in the page's overlay view, so they scroll and zoom with the page and never enter the file; they go when reading stops. Like the laser, the pen is put away with the app.

Reading while writing (2026-10-13): ink never interrupts Read Aloud. A PDF's `changeVersion` changes with every stroke, highlight, picture, erase and save; reading compares `PDFSession.readingTextVersion` instead, which changes only when pages are inserted, deleted, moved or turned (`PDFEdit.changesPageTree`), so the highlight, the pen's endpoints, "Set Reading Start" and the pages still to read all survive annotating. `ReadAloudController.pdfContentDidChange` (the session's `contentDidChange`) ignores everything else; after a page change it finds the page being read and the last page by identity (`readingPDFPage`, `readingPDFLastPage`), prepares the page again under its new number and goes on at the same passage and word (`pendingPosition`, `ReadAloudSession.move(to:offset:)`); a page removed pauses reading with a plain message. The pen's marks keep the words around them (`PenMark.context`) and are found again by text (`PenMark.located(in:)`) for their marks and for Repeat. Handwriting is never read: text comes from `PDFPage.string` and recognition and layout rasters from `CGContext.drawPDFPage`, neither of which includes annotations, so ink (Graphite's own strokes are ink annotations, never flattened) is not in what is read or in word positions. A note edited while it is read (`MarkdownSession.textDidChange`) is prepared again once typing pauses for 400 ms, and `ReadAloudReanchoring` (Core) finds the sentence being read by its text near its old place (whole, or its first or last 60 characters) and reads on from there; its highlight is hidden meanwhile (`isReanchoringNote`); a sentence that is gone pauses reading and says so.

`ReadAloudSection` discovers Markdown heading sections off the main actor, retaining exact original ranges, including nested subsections and Setext headings. Native PDF selection endpoints carry the document revision; requested ranges are extracted lazily and stop on the selected end page/word.

UI's window-owned `ReadAloudController` prepares Markdown off the main actor and composes PDF extraction through the existing page-export worker and a separate extraction actor. It loads one requested PDF page at a time, preserves current unsaved page edits through export, respects copying permissions, and stops on unreadable pages. In the app (`playsWhenPrepared`) a chosen passage starts as soon as it is prepared and the page stays in view; rebuilding a passage for another math style or PDF reading order, and a scanned page that needs review, wait for Play. While a passage is loaded the window toolbar shows `ReadAloudToolbarControls`: Pause/Resume, and a popover (`ReadAloudControlsPanel`) with title, state, scope and voice, previous/next sentence around Play/Pause, a segmented speed control, Follow Reading and Stop. The Reading Options sheet (`ReadAloudReader`), opened from the popover or by itself when preparation fails or a scan needs review, is a form with the shared `ReadAloudVoiceSettings` section, the passage's math or PDF order, Show in PDF, notices, and the transcript with the spoken word highlighted; Settings › Read Aloud shows the same voice section: "Same as Read & Speak (voice, quality)" first, then every voice Graphite offers grouped by quality (Personal Voice, Premium, Enhanced, Default) with its language, the passage's language first. A voice sample uses its own session and preference domain, so trying a voice never changes the chosen one. Markdown editors also draw temporary source highlights without changing text, selection, or undo history. Voice/speed choices live in device preferences; passages remain in memory and no narration sidecar is written; High Quality audio is cached outside the vault, in Caches (see Read Aloud voices). Tab navigation retains the session; vault switching clears it before replacing folder access. Edits invalidate reading offsets. Reading continues in the background and with the screen locked (the app declares the `audio` background mode); `ReadAloudNowPlaying` publishes the title, scope, state and passage progress to `MPNowPlayingInfoCenter` and answers play, pause, toggle and next/previous track (next/previous sentence) only while a passage is loaded. The next PDF page is prepared inside a UIKit background task, and the audio session stays active across that page break. Lecture recording stops narration rather than attempting untested simultaneous audio-session use.

`ReadAloudSourceToken` separates prose words from whole equations while retaining original UTF-16 ranges. Reading-view builds prepare these mappings only for the speaking note. `ReadingSourceAlignment` requires complete ordered agreement with each rendered block, including table-cell boundaries, before adding source attributes; transformed or missing text disables the block's mapping. The vendored Textual renderer carries these attributes into public SwiftUI `Text.Layout` runs and draws temporary, noninteractive backgrounds from their actual bounds. Inline and numbered display formulas highlight as whole expressions, without claiming term geometry. Live Preview tables, math, and nested callouts prepare bounded block-local mappings off the main actor; ordinary editor text uses native TextKit geometry. The Mac editor explicitly creates a TextKit 2 text view, because the inherited scrollable-text-view factory can create TextKit 1 and omit the required layout manager.

Follow Reading uses source geometry with viewport margins, opens folded Markdown sections/callouts when needed, and makes bounded attempts to realize a distant lazy block before following its actual word. Native editor following preserves selection. Manual scrolling suspends following for the corresponding source pane. Highlight events do not reparse the note or alter its files; unsupported rendered mappings retain transcript highlighting. Gesture delivery, UIKit widget placement during narration, and Pencil interaction still require device validation.

PDF native selections are copied and retained only on the main actor. On Read Selection, `PDFReadAloudSource` captures immutable text and page/range anchors for each selected piece, including discontiguous and cross-page selections. It bounds capture to 256 pages, 4,096 ranges, and the text budget below. It never searches for a repeated string to recover its position. Page narration verifies the worker's exported text against the corresponding live page before enabling source highlights. Selection capture and individual highlights check PDFKit character counts against UTF-16, composed-character boundaries, and the exact round-trip selection text; unsafe coordinates are rejected or left undrawn. `PDFReadAloudHighlighter`, owned by the native view observer, adds temporary `PDFView.highlightedSelections`, removes only its own selections, and preserves user selections and search highlights. No annotation or undo operation is made. Native selection geometry handles the page transform. Show in PDF explicitly reveals the active word, or the starting page before playback, when that source pane is open. Optional Follow Reading reveals the native PDF word with viewport margins, once for each word (`PDFReadAloudHighlighter.revealedWord`) and never while a finger or Apple Pencil is on the pages or they are still moving; on iOS it scrolls PDFKit's scroll view itself, a word below or above the screen going near its top, because `PDFView.go(to:on:)` left a word a fraction of a point short of the margin and the next word moved the page back by 20 points. Revealing at every view update scrolled the page back and forth without end, since moving the page reports the word's new place, which updates the view. A scroll or a pinch on a PDF suspends following until Back to Reading (or Follow Reading in the controls); in a note it still comes back by itself five seconds after the last scroll. A new reading always follows. Paused or stopped reading never follows (`shouldFollow` requires speaking), and the Read Aloud pen's markers never scroll. Native PDF geometry is tested, while actual gesture/event delivery still needs interaction validation.

Apple's `PDFReadAloudExtraction` actor returns a page-local `PDFReadAloudPage` value with original text, prepared text and exact source segments. For selectable text, Page Layout is the default reading order on macOS/iOS 26 and later: Apple's [RecognizeDocumentsRequest](https://developer.apple.com/documentation/vision/recognizedocumentsrequest) supplies paragraph/line order from an on-device raster. Only geometry/order is used in this path; recognized spellings never replace the PDF's original words, numbers or symbols. The same Core Graphics crop/rotation transform renders the page and locates native tokens. Every non-whitespace native token must match exactly one line unambiguously; detected tables, missing/ambiguous mappings, recognition failure and older systems fall back to complete file-order text with a visible notice. Nothing is silently skipped. Recognition examines one page at a time, at most 2,048 pixels along its longer side, 16,384 native/recognized tokens and 2,048 detected lines. PDFKit instances remain worker-owned across analysis; only immutable values cross back to UI. No recognition transcript or raster is written to the vault.

Reading Order is a device-local preference. Changing it cancels existing playback/preparation, rebuilds the current requested page/range and waits for Play. Native start/end offsets are translated through the prepared segments before range validation; an endpoint without an exact mapping is rejected. Explicit native Read Selection retains the user's chosen pieces independently of this preference. Synthetic single-column, two-column and spanning-heading layouts are tested; this is not evidence that arbitrary scientific papers, tables, right-to-left/vertical text, formulas or rotated layouts have correct semantic order. A rotated/cropped fixture verifies safe original coordinates or explained file-order fallback. Layout errors retain the transcript review and native-selection alternatives.

Pages without embedded text now use on-device text recognition. Page Layout uses `RecognizeDocumentsRequest`; Line Order uses accurate `RecognizeTextRequest` without language correction. Recognition cancels the PDF's display rotation while rasterizing, then maps Vision word boxes through the inverse drawing transform into native page coordinates. These are recognized word regions, not verified mathematical term bounds. A scan always pauses for transcript review, including when reached after another page finishes. Blank/unrecognized pages fail explicitly. Mixed native/scanned PDFs remain lazy; no whole-document recognition is launched.

`PDFRecognizedReading` retains derived text ranges, page geometry, word rectangles and line-derived confidence flags. Review Recognized Words can replace a word with a bounded one-line phrase (256 UTF-16 units), rebuild later text offsets and retain the same original rectangle. Corrections rebuild playback and wait for Play; stale review identifiers and changed PDF revisions cannot revive old text. Recognition can be wrong at high confidence. Corrections are memory-only for the current page, never PDF text, annotations or sidecars. Changing recognition order explicitly clears them and recognizes the page again. Native PDF endpoints are not fabricated for scans. The review list offers Start Here and End Here for indexed recognized words, inclusive, with Whole Page reset. A chosen word range is resolved against the corrected snapshot, retains original word rectangles, waits for Play and stops on that page without continuing into later pages. Corrections preserve word identities even when a replacement is a phrase. Changed page/review identifiers reject stale range requests. Choosing recognition order clears the chosen words as well as corrections. Direct page-tap/region endpoints and cross-page recognized word endpoints remain open.

`PDFRecognizedReadingOverlay` attaches an empty, noninteractive container to PDFKit's scrolling document view, with small colored word views. It creates no page-sized raster, selection or annotation. PDFKit geometry drives placement and following; native layout/scale notifications update positions. Page revision/identity and crop/media/rotation checks protect recognized anchors. PDFKit can add transient Live Text after displaying a scan, so the later presence of recognized native text must not invalidate image anchors. The native iPad pane is tested for visible text/highlight pixels, zoom alignment, touch passthrough and removal on Stop. Physical Pencil/gesture delivery and Mac on-screen compositing still need validation.

Read Section Pages uses the PDF’s bounded outline entries. A section includes its subsections and ends on the next same-level or ancestor section’s starting page; the last section reaches the final page. Full boundary pages are included, including shared-page headings, and the picker explains that neighboring text can be spoken. Graphite bookmarks are excluded; missing, invalid or backward destinations do not create misleading ranges. Exact boundaries still require native text selection. This control delegates to the same lazy, revision-checked PDF page reader.

Remaining work includes the deferred human-sounding voice and provider comparisons, broader PDF reading-order/scan accuracy validation, header/footer and paper-content preferences, hyphenation, mixed embedded-text/image regions, PDF math recognition, term-level formula bounds, unsupported TeX packages/macros and standalone documents, exact semantic PDF outline boundaries, durable resume checkpoints, background/lock-screen playback, and physical-device accessibility/performance validation. Each lazy PDF-page transition checks the original document revision, so changed pages cannot silently continue with stale anchors. Encrypted PDFs currently require native selected-text reading; page extraction is explicitly unavailable rather than reopening a locked snapshot without its password. Markdown input, a PDF page's extracted text, and total selected PDF text are each limited to 1,048,576 UTF-16 units; utterances are limited to 1,200 units and expanded Markdown speech to twice the input budget. Larger notes, even with a small selection, need a future incremental semantic parser.

## Storage contracts

- App icons are bundled Icon Composer documents in `App/Icons`. On iPhone and iPad, Appearance settings offers blue (primary), red, black, charcoal, and blue graphite. `AppIconSettingsSection` calls `UIApplication.setAlternateIconName`, prevents overlapping requests, reports errors, and reads the selection back from the system after completion and when the app becomes active. iOS persists this device-local choice; no vault file or duplicate preference is written. Xcode generates primary/alternate declarations from the icon build settings. macOS uses the primary blue icon and does not expose the iOS-only picker. The setting offers presets, not arbitrary RGB recoloring. Settings thumbnails use separate foreground image assets over the icon's pearl background; they approximate the default appearance, not system tint or animated lighting. The icon is a graphite crystal of nine flat facets, each its own vector layer with a gradient, so the system draws the glass, highlights, shadow and appearance variants; the presets differ in the sheen of the front facets. The documents and thumbnails are generated by `Design/GraphiteIcon/GraphiteCrystal/make_graphite_crystal_icon.py`.

- The selected folder is the workspace. No vault import, shadow copy, or authoritative database.
- Graphite remembers several vaults, like Obsidian's vault switcher. The list (`VaultList`, in `UserDefaults`) holds each vault's folder name, where to find it, when it was last opened, and the document last open in it, which reopens on return. Where to find it is either a bookmark for a folder the user picked, or a path inside Graphite's own Documents folder (Files shows it as On My iPad › Graphite), because iOS moves that folder when the app updates. A vault created inside a picked folder keeps the bookmark for the picked folder plus its name inside it, since the permission belongs to the folder the user granted. Creating a vault writes only an empty folder; `.obsidian` appears when a shared setting is first changed, as in Obsidian. Removing a vault from the list never touches its folder. Each vault has its own index database, named after its identifier in the list (see Index location below), so switching back does not re-index. One vault is open at a time; switching saves the open document first and is refused while recording. When another app moves or renames the open vault's folder, Graphite opens the vault again from its saved location, whose bookmark follows the folder; when the folder was deleted, or cannot be found that way, it asks the user to open it again.
- Markdown edits preserve source bytes unless the user edits them, including a leading UTF-8 byte order mark: saving a note, rewriting its links after a rename, adding a block `^id` to it, and setting a property from a base all write the mark back when the file had one. No formatter runs on save.
- Drawings are PNG, PDF, or SVG, chosen per drawing with a default in Graphite's preferences. Every format holds the complete visible drawing. Re-editing data is one versioned record (`DrawingPayload`: canvas size, background, PencilKit stroke data, and a digest of the visible content it was written with), stored in a standard place per format: a private ancillary `grPK` PNG chunk (its final uppercase letter marks it unsafe to copy after image modifications), the PDF's XMP metadata stream, or an SVG `<metadata>` element. When the visible content no longer matches the digest, the record is ignored and the file is treated as an ordinary image. For PNG the digest covers every chunk except the `grPK` record and the text and time chunks (`tEXt`, `zTXt`, `iTXt`, `tIME`), so colour, orientation and animation changes count; drawings saved before this rule carry a pixel-only digest, which is still accepted until their next save. For PDF it covers the decoded page content, the page resources it draws with (numbers normalized, `/ProcSet` ignored), any rotation, crop box or user unit, and no added annotations; only one-page PDFs are checked, and their streams are decoded within fixed budgets: a stream that could expand past them is found in the file's bytes and inflated in chunks. For SVG it covers every byte outside the metadata element. Unknown or corrupt metadata degrades the same way.
- Vector drawings are PencilKit strokes converted to filled outlines with round caps (`StrokeOutliner`), drawn in sRGB. A stroke the pixel eraser cut is outlined whole and clipped to its eraser mask, moved with the stroke's own transform, as PencilKit draws it. Ink colors are resolved in light appearance because drawings are saved as they look on white paper. Brush texture and pressure shading are simplified; PNG keeps them exactly.
- A drawing's saved region is the full canvas width and, vertically, the ink plus a margin, so embeds are only as tall as their content. Ink outside the canvas is never cropped. PNG export uses 2× scale, falls back toward 1× for tall drawings within a 48-megapixel budget, and refuses beyond that with advice to use PDF or SVG. Rendering happens in horizontal bands that start on whole pixel rows and are streamed into an 8-bit sRGB PNG encoder (`BandedPNGEncoder`), so peak memory is about one band; before saving, a small decoded thumbnail of the finished file is compared with the rendering.
- New drawings use a fixed 760 pt canvas (the reading view's note width limit), zoomed to fit the screen. A tool's width is its width in the drawing's points, and so in the note, at any zoom: `InfiniteCanvasView` multiplies it by its zoom, as a PDF page canvas does, and takes the tool again when the zoom changes (before 2026-10-19 a stroke written zoomed in to 4 times was a quarter as wide in the drawing). PencilKit's widest pen, pencil and highlighter limit this at high zoom: the drawing's zoom is the person's, so those inks are narrower in the drawing when width times zoom passes 25.66, 16 or 60 points. The drawing editor keeps its own undo history. While the app is in the background, an unsaved drawing is kept as an ordinary SVG drawing, with its strokes in the standard metadata element, plus a JSON description of its note or file, in the app's Application Support "Drawing Drafts" folder, outside every vault, as user content, not cache. The editor reopens it when that vault next opens after the app was ended, and it is removed when the user closes the editor (Insert, Done, Cancel or Discard).
- A drawing made on an image is a new ordinary drawing in the format new drawings take: the picture with the ink over it, named after the image ("Diagram annotated.png") and saved where the note's attachments go, or beside an image opened on its own. The image file itself is only read. The PNG's re-editing record is `DrawingPayload` version 2, which adds the picture (its encoded bytes, at most 16 MB, prepared by `DrawingPictures` upright and no sharper than a saved drawing) and its frame on the canvas, so the ink can be edited again over the same picture; a build that knows only version 1 shows the file as a plain image. The draft kept while the app is in the background is still an SVG, with the picture in its metadata. In the note, every embed of the image is rewritten to the new file in the style it was written in (a bare name, a path, a Markdown link, with its size or alias), as one edit that Undo takes back; other notes keep showing the original.
- A drawing can hold pictures and have paper. Pictures placed on a drawing (from the photo library, a file, or the pasteboard) are under its ink and are drawn into the saved file. Paper is a pattern of squares, lines or dots under the ink (`DrawingPaper`, positions in `DrawingPaperGeometry`, drawn by `DrawingPaperRenderer` into the PNG or as one outline shape in SVG and PDF). Each drawing says whether its paper is part of the saved drawing, which notes and other applications then show, or only a guide while drawing, which leaves the saved file as ink on its background. The record of a drawing with pictures or with paper that is shown is `DrawingPayload` version 3, which an older build treats as a plain image rather than saving the ink again without them; a guide changes nothing visible, so it does not raise the version and an older build only loses the guide. A pattern has a spacing (narrow, standard or wide, three quarters to one and a half of the pattern's own), a line color (gray, blue, green or red) and a strength (light and strong are halfway to white and to the darkest shade of the color, opaque so lines that cross are not darker where they cross), and the paper under it a color (white, ivory, yellow, gray) or none. Paper colors, and the style of a pattern the saved drawing shows, are version 4 of the record, which a version 3 build treats as a plain image; the style of a guide is kept without raising the version. The editor's menu has "Preview as in the Note", which hides a guide and shows no paper as a checkerboard. A saved drawing starts on a line of its paper, so the pattern stays in step with the ink when it is opened again. A drawing is saved as it looks on white paper, and one without paper is transparent; in a dark note its embed is shown on white (`EmbeddedImageView`), as it looks in every other app, rather than its ink being changed. Pictures share the record's existing size budget with the strokes (16 MB of pictures, 32 in a drawing). A placed picture can be turned by any angle about its middle (`DrawingBackgroundImage.rotationRadians`, clockwise; its `frame` stays the upright rectangle it fills before the turn, and `boundingFrame` is the box around it as turned, which the saved region and the canvas's height follow). A record with a turned picture is version 5, with one angle per placed picture (`pictureRotations`, written only when one of them is turned), which a version 4 build treats as a plain image rather than saving the ink again with the pictures upright; upright pictures keep version 3. The picture of a drawing made on an image is never turned.
- Pictures in vector drawings. PDF and SVG drawings show their pictures (the picture of a drawing made on an image and the pictures placed on it) as PNG does, in the same order: the background (white under a picture drawn on), the paper when it is shown, the pictures, the ink (`VectorDrawing.shapesUnderPictures`, `pictures`, `shapes`). The SVG writes each picture as an `<image>` with `preserveAspectRatio="none"` and an `xlink:href` data URI of the picture's stored bytes, JPEG as JPEG and PNG as PNG, between the paper group and the ink group; `xlink:href` because it is the SVG 1.1 attribute every renderer reads. One picture is at most 7 MiB in an SVG, because it is one XML attribute and libxml2, which Foundation's parser uses, refuses attributes of 10,000,000 bytes or more; larger pictures need PNG or PDF. Graphite's own SVG preview reads the pictures back only from `data:image/png` or `data:image/jpeg` base64 URIs, never a path or address, within the same count and size bounds as the record, and decodes each no larger than it is shown. The PDF draws them through Core Graphics: a JPEG is handed over unchanged and stored as DCTDecode, a PNG is stored as Flate pixels with a soft mask. The PDF digest also covers the data of every XObject the page's resources name, with each image's mask, so another app changing a picture's pixels is detected although the page commands and dictionaries stay the same; a page without XObjects hashes exactly as before, so older drawings keep their digest. Because several images can share their dictionary keys and length, every stream in the file that could be the one Core Graphics resolved is hashed (a JPEG as its compressed bytes), and a candidate may not contain `endstream`, so a length counted from one stream never runs into another. The record (`DrawingPayload`) did not change. A turned picture is drawn by every writer through one routine (`VectorDrawingRenderer.drawPicture`: the frame turned about its middle, the image stretched to it); the SVG adds SVG's own `transform="rotate(degrees middleX middleY)"` to the `<image>`, which every SVG renderer reads, and Graphite's preview accepts only that form, about the picture's middle: any other transform on a picture makes it refuse the file, which stays an ordinary SVG for the system's preview, as other files Graphite did not write do. Known compatibility limit: a build that does not know version 5 of the record (main as of 2026-10-12, run on such a file in a test of its own) shows an SVG drawing with a turned picture as "cannot be shown", because it previews only SVGs whose record it can read, and it cannot read version 5; with upright pictures the same build shows it. No encoding keeps such a build working without harm: a version 4 record would let it show the picture upright, since it ignores the `transform`, and let it save the drawing again with the picture upright; drawing the turned picture into a new upright bitmap of its box would show it right everywhere but resample and re-encode the picture in the file every other reader shows, and lose the angle for that build's editing too. Browsers, Quick Look and other SVG readers show the turned picture, and PNG and PDF drawings are shown by such a build as plain images.
- A picture placed on a PDF page is a standard stamp annotation whose appearance is the picture (`PDFPicture`), so every PDF reader shows and prints it. The annotation also keeps the picture's own bytes under a Graphite key (`GraphitePictureV1`, base64 text after a fixed prefix: PDFKit writes a text value that starts with a slash as a PDF name, and the base64 text of every JPEG starts with one), which is what lets Graphite move, resize, remove and restore the picture exactly; without the key the stamp is still the visible picture. A picture is drawn upright as the page is read when it is placed (`GraphitePictureTurns` records the page's rotation then). Placing a picture puts the page's Pencil ink after it in the page's annotations, so ink stays over pictures in the file as it is on screen. Moving or resizing replaces the annotation by a new one, because an annotation read from a file keeps the appearance it was written with. A picture turned by hand (`PDFPicture.rotationRadians`, clockwise as the page is shown) keeps `bounds` as its upright frame in the page's coordinates; its annotation's rectangle is the box around it as turned (`annotationBounds`), its appearance is the picture turned in that box, and `GraphitePictureRotation`, `GraphitePictureWidth` and `GraphitePictureHeight` hold the angle and the upright size, only for a turned picture. A turned picture keeps its bytes under `GraphitePictureV2` instead of `GraphitePictureV1` (`PDFPageManager.turnedPictureKey`), and goes back to `GraphitePictureV1` when it is turned upright again; Graphite reads both, and a turned picture under `GraphitePictureV1`, as the build of 2026-10-11 wrote it, still reads turned. A build that reads only `GraphitePictureV1` (main as of 2026-10-12, run on such a file in a test of its own) takes a turned picture for another application's stamp: it shows it turned, from its appearance, and does not select, move or stretch it, while its upright pictures work as before; when it saves without changing the page tree, Graphite reads the turned picture back intact. When its save also inserts, deletes or moves pages, PDFKit drops the keys it was not told to keep (see `preserveGraphiteKeysThroughPageTreeRewrite`): the turned picture stays visible as an ordinary stamp but can no longer be arranged in Graphite. With the key of 2026-10-11 that build stretched a turned picture upright into its box when moving it, and lost its angle. When another application resized the rectangle, the picture keeps its proportions and fills the rectangle's width; without the keys the stamp still shows the turned picture to every reader, Graphite included, and Graphite then takes it for an upright picture filling its rectangle when it is moved or changed. Each picture is at most 8 MB and is stored twice: as the appearance, and as base64 text under the key. A JPEG is handed to Core Graphics unchanged, but PDFKit still writes the appearance of an annotation in a document read from a file as inflated pixels with a fully opaque soft mask (seen in a written file on 2026-10-12), several times the JPEG's size, and copies the whole annotation dictionary, picture key included, into its own `/AAPL:AKExtras` markup data; saving undoes both (see `PDFObjectCompaction` under Save and conflict boundary), so a saved photo takes about its JPEG size plus its base64 text (alpha only until it is checked on the iPad).
- Notebooks and slide decks share PDFKit. Templates are vector PDF page content (blank, dotted, grid, ruled, Cornell, engineering, isometric, music); dotted paper is one tiling-pattern cell, which carries its color in the cell because Core Graphics' own PDF renderer draws nothing from an uncolored cell. New notebooks and inserted pages take the spacing, paper color, line color and strength of Settings › Pencil Drawings › Notebook Paper (the new notebook sheet can change them), and an inserted page takes the size of the current page. Writing guides (squares, lines or dots from a PDF's More menu, light gray) are drawn under the ink of each page's canvas while writing and never written into the PDF; the paper that is page content stays as it is. Standard annotations carry visible ink. Optional custom annotation values only improve re-editing.
- Audio is recorded as IMA4 in CAF and published as AAC in M4A (see Recordings below). Lecture video is recorded as H.264 and AAC in MP4 (see Recordings below). Recording belongs to the study session, not a document view.
- Settings that Obsidian shares with the vault (attachment location, new link format, Wikilinks, strict line breaks) are read from and written to `.obsidian/app.json` with Obsidian's own keys. A save writes only the keys whose value differs from the settings the change started from (the copy the settings screen shows, otherwise what Graphite last read or saved), so a key changed in Obsidian in the meantime keeps its value. Every other member keeps its exact text and position. A name that appears twice reads the way Obsidian's `JSON.parse` reads it (the last value). The file is printed as Obsidian prints it (two-space indentation, `"name": value`), and an empty `app.json` reads as Obsidian's defaults. A file that is not a JSON object is never overwritten, and the write is revision-checked like any other save. Graphite's device preferences (default view and editing mode, appearance, accent color, inline title, file extensions in lists, text size, readable line length, spell checking, which built-in features are on, the Colors palette, default drawing format and background, embedding finished recordings) live in `UserDefaults`. Attachment placement goes through `AttachmentResolver`; editors never decide paths themselves.
- Appearance settings Obsidian shares with the vault are `.obsidian/appearance.json` (`ObsidianAppearance`, Core; keys checked against Obsidian 1.14.4 and the owner's vaults). Graphite reads `interfaceFontFamily`, `textFontFamily`, `monospaceFontFamily`, `baseFontSize`, `baseFontSizeAction`, `accentColor`, `theme`, `cssTheme` and `enabledCssSnippets`, and writes the three fonts, the size, `baseFontSizeAction`, `cssTheme` and `enabledCssSnippets` (written as `JSON.stringify(settings, null, 2)` lays out a list). A font value is a CSS font list read as Obsidian reads it (double quotes dropped, split at commas; single quotes around a name are dropped too) and written as Obsidian's font list writes it (`Iowan Old Style,Georgia`, no quotes); the default font is `""`. The first family installed on the device is used (`FontFamilyList.firstAvailableFamily`, matched without regard to case); CSS's generic names (`serif`, `monospace`, `system-ui`, `ui-rounded`, …) stand for the system font's designs; a list with nothing installed means the default font, and Settings says "Default (Not Installed)". Writing uses the same member-preserving JSON writer as `app.json`: only keys whose value changed are replaced, in place, unknown keys keep their bytes, the file is replaced atomically with a revision check, and a vault without the file gets one only when something is set. A size is written 600 ms after it last changed, so a pinch or a run of ⌘+ writes once; switching vaults writes a pending size first. The vault monitor reloads the file when it is reported changed (`WorkspaceModel.isAppearanceFile`), as does returning to the app. Obsidian 1.14 keeps the font size per device once it has one (in its local storage) and reads `baseFontSize` only on a device that has none, so a size set in Graphite reaches Obsidian only there; fonts and `baseFontSizeAction` are read by Obsidian from the file.
- Themes and CSS snippets (Phase 2 of `theme-support-assessment.md`): Obsidian's files, `.obsidian/themes/<name>/theme.css` with `manifest.json`, and `.obsidian/snippets/<name>.css` (`ObsidianStyleFiles`, Core; a theme is read up to 8 MB, a snippet up to 1 MB). Settings › Appearance › Themes and Snippets chooses the theme, installs one from Obsidian's directory (`community-css-themes.json`) as Obsidian 1.14 does (`ObsidianThemeInstaller`: the repository's current `manifest.json` names a version, that release's `manifest.json` and `theme.css` are downloaded, else the default branch's; the manifest's name must be the directory's), and turns snippets on and off. They are used only in the community plugins' page and its copies: `CommunityPluginHost.vaultStyles` reads the chosen theme and the enabled snippets that exist and sends them (`runtime.start`, then `appearance.styles` whenever the appearance, the accent, or a file under `.obsidian/themes` or `.obsidian/snippets` changes, gathered for 100 ms). The page puts the theme and then the snippets in `<style>` elements after every plugin's, reports them through `app.customCss` (`theme`, `themes`, `snippets`, `enabledSnippets`, `setTheme`, `setCssEnabledStatus`) and fires `css-change`, so Style Settings reads the theme's `@settings` comments. `vault.getConfig` reads `appearance.json` as well as `app.json`; `vault.setConfig` of a key Graphite writes, and `app.customCss.setTheme`, go through Graphite (`appearance.setConfig`); `theme` (and `app.setTheme`, which Minimal Theme Settings calls) is kept in the page only, because Graphite's own appearance setting decides light or dark. The accent goes to the page as `--accent-h/-s/-l`, which themes derive their accent shades from. The page links Graphite's default variable layer first (`graphite-default-variables.css`, the same file the theme resolver measures against, below), then `community-plugin-runtime.css`, which writes Graphite's look as Obsidian's base color scale (`--color-base-00` … `--color-base-100`) plus the few semantic colors that differ from the layer's derivation, all pointing at the scale; a theme that replaces only the scale (Flexoki) restyles plugin pages too. Every default is declared with `:where(…)`, no specificity, so a theme's `.theme-dark { … }` overrides them as it overrides Obsidian's own layer. Copies of blocks and views take the page's style sheets (`pluginStyles`), and its body classes and inline style other than the runtime's own and light or dark (`bodyPresentation`): Style Settings' `css-settings-manager` and values, Minimal Theme Settings' scheme and option classes and variables. A `MutationObserver` on the page's head and body sends them again (`styles.changed`, gathered for 150 ms) when a plugin or setting changes them, so shown copies restyle without being drawn again; each copy sets light or dark from Graphite's appearance, so both follow the system live. Style text sent to copies is capped at 3 MB: a larger theme (fonts written into the file) is left out of copies and stays in the page, while plugin styles, snippets and Style Settings' values still go. With a theme, a view's copy fills its tab or panel on the theme's `--background-primary`; blocks stay transparent on the note. Notes themselves take the theme natively (theme Phases 1 and 3, below).
- Accent precedence: an accent chosen in Graphite's Appearance settings (per device, `GraphitePreferences.chosenAccentHex`) wins; without one, the vault's Obsidian `accentColor`; without that, Graphite's default, which is Obsidian's default purple. Graphite never writes `accentColor`. "Use the Vault's Obsidian Accent" forgets the device's choice. An accent chosen before this change, including one set by the old "Restore Default Accent", counts as a choice. The lasso's selection outline on PDFs (`LassoTools`) reads the device's stored accent only and does not follow the vault's.
- Properties are the note's YAML frontmatter. Editing one rewrites only that property's lines (`NoteProperties.replacingFrontmatter`). Every other property keeps its exact YAML, including comments, quoting, number spelling, anchors, nested lists and entries with non-text keys. The frontmatter keeps its own line endings, and the body keeps its exact bytes. When entries cannot be matched to lines (a flow mapping, or an anchored value whose aliases would break), every property is rewritten in Obsidian's style instead. Property types come from the values themselves and from `.obsidian/types.json`, which Graphite writes only when the user changes a type (see Tags and Properties views). Reading view and Live Preview read a note's properties with those assigned types (loaded per open note), and a property edit is written with the same types, so unchanged values such as `code: 007` declared as text keep their exact YAML. On the Mac, Live Preview draws the same properties view (`LivePreviewWidgetView`) over the frontmatter at the top of the note: one `NSHostingView` inside the AppKit text view, the YAML concealed under it by the iPad's styling (`MarkdownTextStyler.concealBlock`), its last line reserving the height the view measured. Measured heights are shared by the Mac's editors per frontmatter, column width, text size, fonts and theme (`MeasuredBlockHeightCache`), so a note opened again does not correct an estimate. The cursor is kept out of the concealed YAML: a selection starting in it starts after it (Select All keeps it), and an edit that starts in it and reaches its end, as a backspace at the start of the text, is refused. "Edit Source" shows the YAML until the cursor leaves it.
- Bases are Obsidian's `.base` YAML files and `base` code blocks. Graphite evaluates them against the index. Base YAML and frontmatter are bounded by `YAMLNesting`, by at most 9 anchors (quoted text, and comments on lines with quotes, are counted too), and by alias expansion proportional to the text. Null values count as absent keys, and merge keys apply. Editing a `.base` file keeps keys and values it does not understand and is revision-checked, and it refuses to overwrite filters Graphite cannot fully read, or a `views` entry that is not a list. Editing a note property from a base cell goes through the same frontmatter rewrite and refuses a change that would alter another property's YAML, replace a property holding nested values, or write a value that would not read back as written. The cell editor starts from the property as written in the note, so embeds, Markdown links and a date's separator are kept, and the property and view editors stay open with the edit until its save succeeds. A note saved from a base is not reported by the file presenter, so the workspace has open tabs of it adopt the saved text. The `hasLink` and `linksTo` prefilter compares link targets through the index's folded columns, so a link written in another case, in any script, is never dropped before the evaluator sees it. The evaluator resolves each written link once per folder, since a link's meaning depends only on the folder of its note. A base running again (after a save anywhere, a header sort or a view switch) reads again only the index records whose files changed (`BaseRecordReuse`), and an unchanged result is not redrawn. Card covers and `image()` values from files and web addresses are downsampled to 640 px thumbnails under a byte budget, and they update when their file changes.
- The Colors plugin syntax (`~={#hex}text=~`) stays text in the note. Turning the Colors feature off only stops Graphite from drawing it. A color ends with its block: a paragraph, a heading, a list item, or a table cell. Markers inside code spans (of any number of backticks), fenced or indented code blocks (also inside quotes), and math are not markup. A palette name wins over reading the same letters as hex; a token written with `#` is always hex.
- Community plugins are Obsidian's own packages in `.obsidian/plugins/<id>/` (`main.js`, `manifest.json`, `styles.css`, `data.json`), and which are on is `.obsidian/community-plugins.json`, written as Obsidian writes it and merged with changes made elsewhere (`CommunityPluginList`). A plugin's settings stay in its `data.json`; installing or updating never touches it. Plugins run in a web view through `CommunityPluginHost`, and every file operation they make goes through `CommunityPluginVaultBridge` and `VaultStore`: inside the vault, coordinated, atomic, and refused when the file changed since the plugin read it. Nothing about plugins is stored outside ordinary files except what is per device: whether plugins are turned on for the vault (`UserDefaults`), the plugins' web storage (a `WKWebsiteDataStore` per vault) and their secrets (the keychain: the data protection keychain on iPad and iPhone, the login keychain on a Mac build signed without an application identifier). `Docs/Community-plugins.md` describes the runtime, what works and what does not.
- Links match names the way Obsidian does: case-insensitively for every letter, not only ASCII, whatever Unicode form a file system stored the name in (the index keeps folded keys, lowercased and then composed: `folded_path`, `folded_name`, `folded_alias` and `folded_target`), with a dot in a name not taken for an extension when no such file exists (`[[Homework 2.1]]`), and with partial paths (`[[covers/Book.png]]`) matching the end of a path. Backlinks find links written as the full path, a partial path, a vault-rooted path or an alias. Search lists files whose name contains every word before files that only mention them.
- File management renames, moves, copies and deletes through `VaultStore` with coordinated file operations; a move never replaces another item. `VaultFileOperations` (in Index) plans the link changes before anything moves: it asks the index which notes link to each moved file (text and properties), reads each note with its revision, and rewrites only the path of each link that reaches a moved file, in the style it was written in (`LinkRewriter`, in Core): a bare name or alias that still finds its target is kept as written, and one that became ambiguous gets a path; a vault path stays a vault path, a relative path is recomputed, Markdown links in shortest or absolute format keep that format, and `#subpath`, alias, embed mark and label stay. Markdown link destinations are read with CommonMark's rules (balanced parentheses, titles, code spans and images in labels); a link inside another link is rewritten as one edit; reference-style links are updated through their definition line; a property link that is a whole quoted YAML value is escaped for its quotes; non-ASCII characters keep the form they were written in; a path written with other capitals is rewritten to the spelling the file system stores. A moved note's own relative links are recomputed from its new folder, and a folder's files are listed from the disk as well as the index. Open notes with unsaved text are saved and indexed again before planning, and nothing moves until the index has read the whole vault, since a linking note it has not read would keep a broken link. The move happens first; then each note is written back only if it still has the planned revision, keeping a leading byte order mark. Notes left unchanged are reported, each with its reason (changed elsewhere, too large, not UTF-8 text, unreadable, links not located safely, a link that could not be rewritten, or not saved). A move without link updates still reports every moved file, so the index follows them. Deletion follows the vault's "Deleted files" setting: the system trash (`FileManager.trashItem`, after a coordinated deletion asks other presenters to save and let go of the item; the call stays outside that coordination because on iPadOS `trashItem` coordinates the move itself, and nesting it deadlocked), the vault's `.trash`, or permanent removal. Obsidian's file settings (`trashOption`, `alwaysUpdateLinks`, `promptDelete`, `fileSortOrder`, `newFileLocation`) are shared through `.obsidian/app.json` and written only when changed in Graphite.
- Images and files come into a note through `WorkspaceModel.saveAttachment`: pasted, dropped, photographed, or picked data is written with `.absent` into the folder the attachment policy gives, then embedded at the cursor. The editor reads a pasted image during the paste action (iOS refuses pasteboard reads after it) and takes drops as item providers through its paste configuration; a note dragged from the sidebar becomes a link. Pasted HTML becomes Markdown through `HTMLToMarkdown` (Core), a lenient reader of the tags web pages use, unless "Auto convert HTML" is off. On the iPad the pasteboard is read during the paste and the conversion runs off the main thread; the Markdown goes where the paste was asked for while the note is unchanged, and otherwise the plain text goes at the cursor. A pasted image in a format other than PNG, JPEG, GIF or WebP is encoded to PNG off the main thread too.
- Link and tag suggestions: `LinkCompletion` (Core) reads what is typed before the cursor (`[[…`, `[[Note#…`, `[[Note#^…`, or `#tag`), skipping code. `CompletionProvider` (UI) answers from the index (the quick switcher's fuzzy match for files and aliases, tag counts), from the target note's outline for headings, and from `NoteBlocks` for blocks; choosing a block without an `^id` writes one into that note first, with a revision-checked save. The editor applies the result as edits, so it can be undone.
- Typing helpers are pure functions in `MarkdownEditing` (Core) that return one `MarkdownTextEdit` (a range, its replacement, and the selection afterwards): list continuation, indenting, checkbox and list toggles, moving lines, wrapping in markers, and bracket pairs. The iPad editor asks them first when Return, Tab, Backspace, or a character is typed, and applies the edit through `UITextView.replace`, so it joins the undo history. The keyboard toolbar, the Format menu, key commands, and the command palette all run the same `EditorCommand`s. Obsidian's typing settings (`smartIndentList`, `autoPairBrackets`, `autoPairMarkdown`, `useTab`, `tabSize`, and `autoConvertHtml` for pasted HTML) come from `.obsidian/app.json`; in a vault that indents with tabs, `tabSize` is the width of a level indented with spaces.
- Tabs and split view: `TabLayout` (Core) is the layout alone, one or two groups of tabs with an active tab each, a focused group, the divider position, and the recently closed files; each tab has its own `NavigationHistory` and a pin. It is a value type with unit tests, saved per vault as `SavedTabLayout` in the user defaults. The documents live in the UI: `WorkspaceModel` keeps a `TabDocument` per tab (its note or PDF session and the heading waiting to be shown), and `selection`, `markdownSession`, `pdfSession` and `history` read the focused tab, so commands and the sidebar act on it. The focused tab and the number of open tabs are kept in step with the layout (`activeTabID`, `openTabCount`), and the focused document is found through them, so the views that show it, the window's root view among them, are not updated for changes of the layout that leave it in place: each frame of a drag of the divider updated the root view and the sidebar. While Back or Forward reads the tab's next file, the tab goes on showing the file it showed, as when a file is opened, instead of an empty pane. A file is open in at most one tab, so two editors never save over each other: opening a file that is open shows its tab. Restored tabs load their files when first shown, and a file that cannot be read says so in its tab. Before a file moves, every tab is saved; tabs of moved files reload from the new place, and tabs of deleted files close first. A note's native editor (its text view, which owns the note's undo history, and the controller that styles it) is kept by `MarkdownEditorRetention` when its tab is hidden, moved to the other side, or switched to reading view, and shown again in a new SwiftUI container; see Markdown views. Beyond that bound the editor is rebuilt when the tab is shown again, and the session keeps its text, cursor and top visible line but not its undo history. Only the focused side puts its buttons in the window's toolbar, and a PDF shows the Pencil tool picker only while focused. Focus follows touches through a window gesture recognizer that fails at once, so it never competes with the editor's own taps. A page link from a note shows the PDF where it is open, on the other side without moving focus, so a lecture's page links can be followed one after another; an embedded PDF's Open in PDF View, in Live Preview as in reading view, takes focus to the PDF's tab (`MarkdownPane.openPDF`). When a PDF's width changes, the page at the top is kept there: autoscaling alone would keep the scroll offset and land on another page.
- Where documents were left: each vault keeps, on the device as folds are and never in the vault, the place every note and PDF was left at (`DocumentPlaceMemory` in Core, `WorkspacePlaces.swift`; at most the 400 left most recently, renamed and deleted files followed). `DocumentPlaceStore` reads a vault's places from the preferences once, keeps them in memory, and writes them back only when they change; every workspace of the app shares one store, so two windows on a vault do not overwrite each other's places, and a test can give its workspace a store of its own. A note's place is the character at the top of the view, in the editor or the reading view (a reading view laid out at its very top is the start), and the cursor (`NotePlace`); a PDF's is the page at the top of the view and how far down that page the top edge is, as a fraction of its height, which does not depend on the zoom (`PDFPagePlace`). Places are taken the moment Graphite stops being active (iOS can end a suspended app without telling it), before the save that follows: that save is a task, and by the time it ran iPadOS could already have resized the window for its app switcher snapshots, so an editor laid out again reported a line about a dozen paragraphs further down (seen in the simulator on 2026-10-12). They are also taken before leaving the vault, when a tab closes, when a hidden PDF is released, and when a tab opens another file. The live editor and PDF view report where they are (`MarkdownSession.recordEditorPlace`, `PDFSession.livePlace`). A note loaded into a tab starts there (`MarkdownSession.returnTo`: the editor's jump to the line at its top, or the reading view's start, and the cursor, kept within a note another app shortened); a PDF starts on that page at that height (`PDFSession.keptPlace`, shown once the view has a size, as a resize's place is), unless a page was asked for, as by a link (`PDFSession.go(to:)` forgets the kept place). The place's page is the one at the view's top edge, which can be the page before the one PDFKit counts as current, across the middle of the view, so the place is never checked against that one. The same place brings a PDF back where it was after another tab, a reload after an external change, and a release, rather than to the top of its page. Adopting text another app changed keeps the note's scroll position, as an insertion does.
- Footnotes: `Footnotes` (Core) parses references, definitions and inline footnotes and numbers them as Obsidian does. Reading view removes the definitions, replaces each reference with a link whose number is wrapped in private-use markers (raised and shrunk by the parser, like highlights), and lists the footnotes in a block of their own after the note, each anchored so the link scrolls to it. Live Preview styles references with a scanner span and conceals their brackets away from the cursor.
- Folding: `NoteFolding` (Core) finds the regions that fold and keys them by kind, header text and occurrence, so a fold survives edits elsewhere; the keys are kept per note in the device's defaults, as Obsidian keeps folds outside the note. The editor hides a folded section with attributes only (concealed text, collapsed lines), draws chevrons and "…" as buttons over the text, keeps the cursor out of hidden text, unfolds before an edit or a jump reaches it, and carries a fold to its header's new key when the header line is edited. Reading view folds headings with the same keys; list items there are rendered by Textual as one block and do not fold.
- File recovery: `FileRecoveryStore` (Core) keeps copies of notes as ordinary Markdown files in Application Support, one folder per note named after a hash of its path, with the path written beside them; the folder of each vault is named after its identifier in the vault list. They are user content, never cache, and never go into the vault, so they do not sync. A session reports its saved text just before a save or a reload replaces it (`willReplaceSavedText`), and the workspace copies it in the background at most once per interval; deleting a note copies it whatever the interval. Copies follow renames and moves, are pruned by age when a vault opens, and are deleted with the vault's entry in the vault list. Restoring goes through the note's editor when it is open, so it can be undone, and otherwise writes the file with a revision check, or recreates it.
- Tags and Properties views: the left sidebar switches between Files, Tags and Properties, as Obsidian's left sidebar tabs do; the choice, sort orders and nesting are kept on the device. The index answers both views: `nestedTagCounts` expands every tag into its levels with a recursive SQL query and counts distinct notes per level, and `propertyUsages` counts notes per property name with a few stored values each, from which `NoteProperties.type(ofKey:sampleValues:declaredTypes:)` (Core) infers the type unless `.obsidian/types.json` assigns one. `TagTree` (Core) nests and sorts the levels. The lists are loaded by the sidebar's `List` itself (`VaultOverviewModel`), because a section's modifiers inside a `List` apply to each row. Changing a type writes `types.json` through `VaultStore`, keeping the rest of the file. Renaming a property goes through `PropertyRenaming` (Core), which replaces only the name on its line and checks that every property reads the same afterwards; open notes change through their editors (undoable, autosaved), other notes are written only if unchanged since they were read, and notes that cannot be renamed are reported.
- Bookmarks: `BookmarkList` (Core) reads Obsidian's `.obsidian/bookmarks.json` into `Bookmark`s that keep every field as a `JSONValue`, so kinds Graphite only lists (graphs, web pages) and keys it does not know are written back unchanged. `VaultStore.updateBookmarks` applies each change to the file as it is at that moment, with a revision check, so a change synced from Obsidian meanwhile is kept, and the panel reloads the file whenever it is shown. Moves and renames follow through `followMoveInNavigation`, like tabs and folds.
- Index location: each vault's index is named after its identifier in the vault list, which `openVault` works out before recording the opening; an index named after the vault's path, as earlier versions named them, is moved there once, and indexes unused for 30 days are deleted. Paths inside hidden folders (`.obsidian`, `.trash`) are never indexed.
- Graph view: `VaultIndex.linkGraph` (Index) reads every link, in text and properties, and resolves each with `GraphLinkResolver`, which holds the vault's file names and aliases in memory and matches them as the SQL resolver does (through the folded names and paths the index stores, which ignore case for every letter), once per written target, link kind and folder. Wikilinks and Markdown links resolve alike, as in Obsidian: beside the note, then from the vault root, then by name or partial path; a Markdown path is percent-decoded first and never matches an alias. `LinkGraph` (Core) is the result, with Obsidian's filters and the local graph's neighborhood. `GraphLayout` (Core) is d3's force simulation, which Obsidian uses: link springs, many-body repulsion through a Barnes–Hut quadtree, and a pull to the center, stepped with d3's cooling. The UI steps it in an actor off the main thread and draws with a SwiftUI `Canvas`; the workspace keeps the graph until the index changes and the full graph's positions while the app runs. Filters and forces are kept on the device.
- Map view: `PlacedNote.propertyNames` (Core) names the properties that place a note, as the vault's Geocoding Properties and Map View plugins are set (`data.json`, at most 1 MB each), then `coordinates` and `location`. `VaultIndex.placedNotes` (Index) reads only those properties' rows of the `properties` table, through its index on the key, and reads each value with Bases' `BaseCoordinate`, in that order; a value that is not a coordinate places nothing. The workspace keeps the result until the index changes, as it keeps the graph. `NotesMapView` (UI) wraps MapKit's map view rather than SwiftUI's `Map`, which cannot group markers: nearby notes gather into one numbered marker as the map zooms out, the open note stands apart in the accent color, and a marker opens its note. `VaultMapScreen` shows every placed note, presented as the graph view is; `LocalMapPanel`, in the right sidebar, shows the open note and the notes one link away in either direction, from the same `LinkGraph` neighborhood as the local graph.
- Deep links: the app declares the `graphite` URL scheme. `VaultURI` (Core) reads a link into a vault and an action with Obsidian's names; the root view queues links until the last vault has reopened, so a link that launches Graphite waits for it, and `WorkspaceModel.handle` switches vault if the link names another known one. `file=` resolves through the index like a link but never creates a note; `new` writes through the note's editor when it is open (undoable), otherwise with a revision check, and `overwrite` keeps a File recovery copy first.
- Recordings: `RecordingController` (GraphiteApple) records IMA4 in a CAF file in Application Support's recovery folder, with a JSON manifest beside it (`RecordingRecoveryManifest`, Core) naming the vault, the destination and the note. A CAF of fixed-size IMA4 packets stays readable up to its last packet if the app dies, which an M4A does not; Stop converts it to M4A with `AVAssetExportSession` and publishes it into the vault with an atomic write, removing the CAF only then. When a vault opens, recordings left behind (other than one being made, and not header-only files) that belong to it or to no known vault are offered back one at a time: Save to Vault, Delete Recording, or Not Now. Starting and resuming run off the main thread, because audio hardware can take seconds to answer. A recording is named after its note with a fixed 24-hour timestamp (for example `Lecture Recording 2026-09-23 22-15.m4a`). A recording that could not be saved into the vault is the only copy of its lecture, so no new recording starts until it is saved again, to a destination the workspace works out afresh with the vault's attachment policy, or deleted after a confirmation. A recording saved after another vault opened is saved in its own vault, and the missing embed is reported.
- Video recordings: `RecordingController.startVideo` records through a `VideoCaptureSource` (GraphiteApple), the one place that touches capture hardware: `CameraCaptureSource` is an `AVCaptureSession` with video and audio data outputs, and tests use a source that makes its own frames and sound. A `VideoRecording` receives the samples on its own queue and writes them with a `MoviePartWriter` (`AVAssetWriter` through its inputs' receivers from macOS 26 and iOS 26, with the deprecated `expectsMediaDataInRealTime` still set because a receiver without it stops taking video when no sound arrives; H.264 at about 2.2 bits per pixel a second without frame reordering, AAC mono 44.1 kHz) into the recovery folder, with the same manifest as audio. The MP4 is written as one-second movie fragments, so a file nobody closed plays up to its last whole fragment; closing it leaves an ordinary MP4. With frame reordering on, the fragment writer failed as soon as frames were unevenly spaced, as after a dropped frame. A pause keeps the file open and closes the gap in its timeline. When the capture session is interrupted (the app leaves the screen, a call or another app takes the camera or microphone, system pressure, a runtime error, or an iPad that will not share the camera while Graphite shares the screen) the file is closed at once under a background task, the video pauses completely and says why, and when the session reports the interruption over the video goes on by itself, unless the person had paused it, in a new part ("Name.part-2.mp4"). Stop joins the parts with a passthrough `AVAssetExportSession` of an `AVMutableComposition`, nothing encoded again, and publishes the file like an audio recording; unfinished parts are offered back as one recording. iPadOS gives no ordinary app the camera in the background, and since iOS 18 multitasking camera access only to VoIP apps or apps with Apple's multitasking-camera entitlement, which Graphite does not have. A video does not start with less than 500 MB free and stops itself below 250 MB. Frames are rotated upright by the connection (`AVCaptureDevice.RotationCoordinator`); the file keeps the size of its first frame and fits turned frames inside it. The floating preview (`RecordingPreviewOverlay`) is an `AVSampleBufferDisplayLayer` fed the same frames, so the recording never depends on it; from macOS 27 and iOS 27 its renderer is fed through a render synchronizer's receiver, released when the recording ends or the preview changes, as a renderer still held by one synchronizer cannot join another.
- Backlinks and mentions: the Backlinks panel reads each linking note (at most 200) and keeps the links that could name the note by name or alias (`Mentions.linkCandidates`, Core), resolving only those, to show each link's line. Unlinked mentions start from a `content:"name"` search, then `Mentions.unlinkedMentions` finds whole-word matches outside links, code, math, comments, tags and web addresses. Link turns a mention into a link through the note's editor when it is open, so it can be undone, and otherwise rewrites the file only if it still has the words that were found.
- Templates and daily notes: `TemplateSettings` and `DailyNoteSettings` (Core) read and write Obsidian's own settings files, keeping keys Graphite does not know. `MomentDateFormat` writes dates with Moment.js format strings, as Obsidian does, and reads back the dates in daily note names. `TemplateRenderer` fills in the variables; `TemplateInsertion` turns a rendered template into one edit from the start of the note to the cursor, so the note's merged properties and the template's body are undone together. A note shown in reading view has no editor to apply an insertion, so the session changes its text directly then.
- PDF study tools: the PDF view enables UIKit's find interaction, which PDFKit fills with its matches. Links to pages and quotes are written by `PDFCitation` (Core) and offered from both text selection menus: Graphite's own while annotating, and PDFKit's (through `buildMenu`) for protected PDFs, which are not annotated. A PDF is opened with its password when it needs one; the password stays in memory for the session. An encrypted PDF is never written: PDFKit would save it without its encryption, and Graphite does not know its owner password, so `PDFSession.apply` refuses every edit and the pane hides the tools that make them.
- Commands and shortcuts: the window's commands are SwiftUI `Commands` (`GraphiteCommands`), so iPadOS lists them in the menu bar and shows their shortcuts; they reach the window's workspace through a focused scene value. Editing shortcuts belong to the text view (`UIKeyCommand`), so they apply only while a note is edited; the link commands on Return exist only while the cursor is on a link (`LinkLocator`), so Return keeps its meaning elsewhere.
- The Mac's windows: `GraphiteMacScenes` (UI) is one main window and a `Settings` scene, both on one `WorkspaceModel`, so a setting changed there reaches the open vault at once. Settings opens with ⌘, from the app menu, as in every Mac app, in a window of its own laid out like System Settings (a list of pages beside a grouped form, without a sidebar toggle). ⌘W closes it through its own shortcut, which AppKit finds before the menu bar's "Close Tab": a menu command's state is refreshed when its menu opens, so a command deciding from it which window to close could close the main window, which quits the app. "Manage Vaults…" there closes the window and shows the vault list in the main window (`WorkspaceModel.isVaultManagerPresented`). The iPad keeps Settings as a page-sized sheet with a Done button.
- The Mac's drawing: AppKit would hand every view larger than 768 by 768 pixels that draws itself, the note editor's text view among them, to Core Animation's Metal renderer, whose start reserves about 170 MB of graphics memory for a second each time a note opens. `MacViewDrawing` (UI) registers `NSViewCanUseGPUAcceleration` as `false` in `GraphiteApp.init`, before the first window draws, so such views are drawn on the processor as small ones are; PDFKit's own Metal rendering is not affected. Measurements in `Coverage.md` ("A small core").
- The Mac's file tree is AppKit's outline view (`MacFileTree`, UI), as NetNewsWire's and Finder's sidebars are, in the source list style and the system's sidebar row size. The outline view asks only for the rows it shows, so a vault's root lists at once whatever its size (25,000 files in 0.2 s in its test); SwiftUI's list kept a view per row on the Mac. `FileTreeController` keeps one `FileTreeNode` per listed path and reuses it when a folder is listed again, so expansion and selection survive; a folder lists its contents when it first expands, and again when the vault changes while it is expanded. It follows the workspace's root listing, expanded folders, open file, sort order, other versions and font through `MacFileTree.updateNSView`, and writes expansions back to `expandedFolders`. Choosing a file opens it, with the mouse or the arrow keys; a click on a folder's name folds it, as in Obsidian. A row's menu is the sidebar's SwiftUI menu (`VaultEntryMenu`, shared with the iPad's rows) drawn by `NSHostingMenu`. A dragged row carries the same vault item the editor and the tab bar read; a drop on a folder moves into it, on a file into its folder, elsewhere to the root. Cells are laid out by hand, without constraints, and draw a selected row's muted extension themselves: the table colors its cells' `textField` in one color. Picking several files, search results and the other panels stay SwiftUI lists, and the search field is in the toolbar, where SwiftUI can place it over an outline view, as in Notes and Mail.
- Shared views state their styles rather than take each platform's defaults, which differ: the sidebar's picker and vault switcher sit in `sidebarBar` (`GraphiteTheme.swift`), on the bars' material on the iPad and, on the Mac, on the sidebar's own with the system's scroll edge effect (`safeAreaBar`, macOS 26 and later), the bars' material being opaque white there; property values are plain text fields and dates short dates on both, where the Mac's defaults are bordered boxes and steppers. A safe-area inset whose content exists on one platform only is applied on that platform: on macOS 27 an inset with no content takes all the height, which left the Mac's PDF page 0 points tall.
- Getting around: `NavigationHistory` and `RecentFiles` (Core) record opened documents; back and forward move through the history without adding to it, and both follow renames and deletions. An entry that fails to open is dropped only when its file is gone; after a read error or a save conflict it stays. The quick switcher asks the index for files whose name, path, or alias contains the query's characters in order, then ranks them with `FuzzyMatcher`, which scores word starts, runs of matched characters, and short names, ignoring case and accents. The candidates are narrowed in SQL by `FuzzyCandidatePattern`: a `LIKE '%a%b%'` pattern for names written in ASCII, and for other names a GLOB pattern that writes each query character as the set of characters whose folded form contains it (`ß` for `ss`, `ﬁ` for `fi`), so the narrowing never drops a name `FuzzyMatcher` accepts. The command palette ranks commands the same way; its commands are built for the current document from `WorkspaceCommandList`.
- Search reads Obsidian's search syntax (`SearchQueryParser`, in Core) into an expression; nesting deeper than 32 levels is read flat. The index turns it into SQL over the full-text index and the tag, property, and file tables (`SearchSQLCompiler`). Parts SQL cannot decide exactly, such as `line:`, `section:`, tasks, `match-case:` and property values, compile to a condition that selects more files, never fewer; `SearchMatcher` then checks each candidate against its text, tags and properties. Inside `line:`, `block:`, `section:` and `task:`, tags and nested operators read that part of the note. Each database read stops after 5,000 checked candidates or 250 ms (checked between notes), which leaves the database to saves and other lookups between reads. A search whose page is still empty keeps reading, so a page is empty only when the search is finished. The next page continues after the last file checked, by its place in the sort order, so files added or removed in between do not shift it. Cancelling the search task stops it (GRDB interrupts SQLite, and the note-by-note checks stop); a search replaced by the next keystroke is cancelled this way, and the sidebar ignores its cancellation. Words match the start of words, ignoring case and the accents of Latin letters, exactly as SQLite's `unicode61` tokenizer reads them: the words go to FTS5 as typed, so the tokenizer folds them as it folded the notes, and `SearchTextTokens`, which `SearchMatcher`, excerpts and highlights use, follows the tokenizer's Unicode 6.1 tables character by character (a test compares the two on every assigned character through SQLite). Foundation's broader folding is not used for this, because a word it folds (`ß` to `ss`, `й` to `и`, `ά` to `α`) is not a word the index holds; `strasse` therefore does not find `Straße`, which would need a custom tokenizer. Chinese, Japanese and Korean letters, and Thai, Lao, Khmer and Myanmar text, match anywhere inside a word, and a term with no words (symbols such as an emoji) is found as written; for both, the index selects candidates with a literal search (`instr`) that reads every note body, and `SearchMatcher` decides. A note's `.md` extension is not searched by plain words. Attachments and unread notes have no indexed text, so no content condition matches them. The whole note, frontmatter included, is indexed, so property values are searchable and a match's position is its position in the file; `SearchExcerpts` gives up to five matching lines per result. Regular expressions run through a SQLite function backed by `NSRegularExpression`; there, in `SearchMatcher` and in base formulas, a pattern that runs longer than one second or whose task is cancelled gives up (`TimeLimitedRegularExpression`), and the search (`SearchError.regularExpressionTooSlow`) or the cell reports it. A `/pattern/` that does not compile is named in the sidebar in place of results (`SearchError.invalidRegularExpression`), since excluding it would list every file. Tag suggestions count a tag once, whatever its capitals. Measured on 2026-09-25 with the release build of `GraphiteBenchmarks 100000` on a Mac with an Apple M5 Max and 128 GB of memory, running macOS 27.0: 100,000 synthetic notes index in 9.2 s; a plain search takes 14 ms (p95 15 ms, over 100 runs); an exclusion 25 ms, a phrase 16 ms, `line:` 30 ms, and a regular expression 604 ms (medians of 10 runs each). These are Mac figures, not iPad ones. On 2026-10-21 the benchmark gained a word no note contains (`nowhere`), `file:nowhere`, a phrase in few notes and three quick switcher queries, the slow cases for a name scan; on the owner's Mac with other builds running they took 20–26 ms, 11–16 ms, 22–28 ms and 14–17 ms.
- Saving a `.base` file splices the edit into the original text (`BaseDefinitionEditor`): only changed entries are rewritten, and every other line keeps its exact text (comments, indentation, flow style, tags, document markers, line endings). New lines use the file's most common line ending, and lists are indented like the file's. The result is read back and must mean the edited configuration; otherwise the whole file is written from the parsed tree, and its comments are lost. Yams hands an alias a copy of its anchored node, forgets anchors when its parser goes, never writes a scalar's tag and does not report a collection's style, so the editor records all four while the parser lives (`WrittenYAMLNode`). An entry Graphite rewrites is written by `RewrittenYAMLWriter`, which pairs each part with the part it replaces (lists by meaning, then position; mappings by key) and writes an unchanged part with its anchor, as an alias when it still means what the anchor holds, with its tag, and in flow style when it was. An alias whose anchored value changed is written out in full, so it keeps meaning what it meant. When the whole file must be written, written forms are kept if it reads back the same; an output that does not read back as the edited configuration (for example a tag whose name cannot be written back) is refused and nothing is saved.
- Table column widths are the view's `columnSize`, a mapping from a property's full name to a width in points. Obsidian applies only numbers other than zero and shows a column at least 40 points wide; Graphite reads it the same way and caps widths at 2,000. A header's trailing strip resizes its column: the width under the finger is kept in the table's state while the finger moves (`BaseColumnResize`), and lifting it saves the whole-point width through `BaseDefinitionEditor.setColumnWidth`, under the property's full name, the only spelling Obsidian reads. The column shows the new width until the saved file comes back, and snaps back if the save is refused.
- A map view's `mapTiles` (and `mapTilesDark` in dark mode) is read as Obsidian's Maps plugin reads it (`BaseMapBackground`): URLs with `{z}`, `{x}` or `{y}` are raster layers, one URL without them is a MapLibre style. SwiftUI's `Map` cannot draw tile overlays, so a map with raster tiles is MapKit's map view (`BaseTiledMapView`) with one `MKTileOverlay` per template; the first replaces Apple's map content, so nothing of Apple's map is loaded. Templates are filled in as MapLibre fills them (`BaseMapTileTemplate`). Only `https` and `http` templates are used, and tiles come from an ephemeral session without cookies, credentials or disk cache, with a 4 MB limit per tile, so opening a base contacts only the server the base names. Styles (vector tiles) cannot be drawn by MapKit; Apple's map is shown with a notice.
- `html()` gives an `.html` value, which is text for every function and comparison, as Obsidian's HTML value is a string. Obsidian renders it in its web view after DOMPurify; a Graphite cell is native text, so `BaseHTMLText` reads the markup itself into runs with a fixed set of inline formatting and web or mail links. It is a small tolerant reader, not a browser: elements that could run code or load content (scripts, styles, frames, embedded media, forms) are dropped with their content, images show their `alt` text and are never fetched, and other link schemes are plain text, because the markup usually carries text from notes.
- A `kanban` view (Obsidian 1.14) is a board of the view's groups (`BaseKanbanView`): one column per `groupBy` value, empty values in "None". Moving a card writes the column's value into the note's grouped property through `BaseDocumentModel.setProperty`, the checked frontmatter edit every view uses. Cards move only when the board groups by a note property and the file is a Markdown note. The keys Obsidian 1.14 writes for the board's own settings are not documented and are left untouched.
- Index databases, thumbnails, and UI history live in application caches/support. Deleting derived data never deletes vault content.
- Unsaved recovery, if persisted, must contain ordinary recoverable files and be identified as user content, never mislabeled as disposable cache.

## Save and conflict boundary

File recovery publishes snapshots with `AtomicFileWriter` and an absence expectation. A sequence suffix distinguishes copies made within the same millisecond without changing their dates, and history merges copy every source version before removing its original folder, preserving their order. Copies of a `FileRecoveryStore` share a mutation lock so background snapshot tasks cannot race the interval check, pruning or moves. Deep-link appends inspect line-ending scalars, preserving CRLF, CR and LF separators; creating a unique note after a name collision refreshes the sidebar after the new file is saved.

Markdown saves first drain queued insertions through the attached text view's native undo history, or directly into the session when no editor is attached. Waiting insertions count as unsaved work. Each text change and queued request advances an edit version. Reload checks that version and the file revision after its asynchronous read and refuses to replace work that arrived meanwhile. External-change checks also reject results from reads overtaken by a save. Save a Copy captures its bytes before awaiting filesystem operations and retains newer edits in the open session. Editing commands rebase their replacement ranges past queued insertions and refuse overlapping replacements instead of consuming the queued text.

Bases queries fail closed when a global or selected-view filter could not be fully parsed: they show an explanation and load no result records. A malformed view does not prevent querying a separate readable view. Missing named views explicitly report the fallback being displayed. YAML edits compare the proposed output against the edited tree after reading it back, including custom scalar and collection tags. Edits keep tags and anchors where they can (see the `.base` saving entry above) and refuse an output that would strip a tag or change what the file means. Property-type settings likewise refuse to replace a non-object `types` entry.

Recording start attempts are checked after permission returns. Recorder callbacks identify the recorder they belong to before changing the controller. A recorder resuming on a worker returns to main-actor ownership before Stop touches it; repeated Resume requests share that operation. An error during resume keeps the controller finalizing until the worker releases the recorder, then retains the audio in the failed state. Retry and Discard cannot read or remove a file still being recorded. These transitions have deterministic tests without a physical microphone; real audio-session interruptions and hardware stalls still require device testing.

Template date offsets use the requested time zone for calendar arithmetic as well as formatting. Multiplication overflow and offsets beyond the documented 10,000-year safety bound preserve the written placeholder. Task search uses note blocks to include indented and lazy continuation lines and exclude task-shaped text in frontmatter, code, and display math. A blank line ends lazy task continuation. Quoted task blocks are unwrapped with a bounded nesting depth, and a quoted thematic break cannot be interpreted as note frontmatter. Null-property search distinguishes an absent scalar value from an empty list or quoted empty string. Bases folder membership respects the written path's case and slash boundaries, and `duration("")` returns an empty value.

Ink-selection resize fits the rebuilt strokes' render bounds to the requested frame, with up to three corrections before committing the one history step. PencilKit includes rendering padding that does not scale with the stroke's points; simply multiplying those bounds made the selection frame jump in width after resizing on the iPhone simulator. Strokes are rebuilt from the original drawing for each correction, and their widths and eraser masks move with them.

The iPad PDF pane keeps its Read/Write choice in `PDFSession`, separately from tool-picker visibility. Read stops the Pencil overlays taking touches and restores PDFKit touch routing; each displayed page's canvas still shows its ink, decoded from the stored drawing in both modes, and the ink annotations stay hidden under it while it does (they show while the drawing is decoded, and on pages without a canvas, as for thumbnails). PDFKit draws ink annotations as center lines of one width in one flat color, so reading used to show a highlighter as a thin opaque line, a pencil without its grain and every stroke without its pressure, at any zoom: turning writing on or off changed the page (reported by the owner from the iPad, 2026-10-12). Showing PencilKit's own rendering in both modes makes the switch change nothing; the saved file, and what Preview or the Obsidian PDF view show, are unchanged. Write makes the canvases take touches again. Switching modes dismisses the annotation selection menu and clears its stale selection. The choice lasts for the open session, is not written to the PDF, and does not survive eviction or reopening. Protected files remain read-only. An Apple Pencil touching a page while reading switches the pane to Write (`GraphitePDFView.beginWritingWithPencil`, recognized by `PencilTouchDownRecognizer` the moment the touch begins), as Apple asks that a Pencil mark without a mode being chosen first; that first touch draws nothing, since the page's canvas was not taking touches when it began, and the page does not scroll with it. A finger still reads, and a PDF embedded in a note keeps its own Annotate button. New page canvases inherit the native tool picker's current ruler state as well as its selected tool. Compact widths keep the Write toggle in the navigation bar (see the shared controls below); Show Pencil Tools is a switch in the PDF's More menu at every width.

The drawing editor has an explicit `GraphiteDrawingDrawsWithFinger` preference, defaulting to Pencil-only input; it is separate from the existing PDF finger-drawing preference. The native picker's duplicate drawing-policy control is hidden. Palette visibility and Fit to Width affect the current canvas without replacing its drawing or undo manager. Export a Copy is grouped under Drawing Options. Compact layouts also put Show Tools in that menu and reserve confirmation placement for Insert/Done. The canvas is clear over the editor's white background, because PencilKit paints an opaque canvas's paper over everything beneath the ink, and the paper pattern and the pictures are beneath it: a paper view that covers only what is on screen and is redrawn as the canvas scrolls and zooms (a tall drawing needs no tall bitmap), then the pictures as image views. "Move or Resize Images" (or a finger tap on a picture when fingers do not draw) turns drawing off and shows a frame around the selected picture (`SelectionFrameView`: drag to move, a corner to resize in proportion); adding, moving, resizing and deleting a picture are steps of the drawing's own undo history, while changing the paper or the background is a change to save, not a step. The editor opens at the top of the drawing: fitting the width zooms about the middle of the view, which otherwise left the top under the navigation bar. Further experience work is tracked in `Premium-experience-plan.md`; physical Pencil quality remains unverified.

Safe writes stage in a private item-replacement folder on the destination's volume (outside the vault, so a crash never leaves a staged file in a synced folder; a hidden file beside the destination only when the volume offers none), order the staged bytes before the rename (`F_BARRIERFSYNC`), compare the expected source revision inside an NSFileCoordinator write accessor, and replace atomically, then flush the drive's cache (`F_FULLFSYNC` on the folder) before reporting success. An externally changed or deleted file yields a conflict. It is never silently overwritten. A no-op Markdown save performs no write. File-provider availability, disk-full, permissions, and coordination errors are user-visible outcomes.

Coordinated access is not a distributed transaction or a lock respected by arbitrary POSIX writers. Reconciliation and revision checks narrow the race, but sync providers may still keep conflict versions. Graphite looks for them through a `ConflictVersionStore` (GraphiteApple; `FileProviderConflictVersions` uses `NSFileVersion`), only for files the sidebar lists, files open in tabs, and files the vault's presenter reports, which include a file gaining, losing or resolving a version. The checks run off the main thread, a hundred files at a time, at most 5,000 waiting, and stop when another vault opens. An iCloud file is answered from `ubiquitousItemHasUnresolvedConflictsKey`; a placeholder of another provider (`SF_DATALESS`) is not asked about, so nothing downloads. The Versions sheet lists the versions, compares a note's text line by line (`TextVersionComparison`, Core) and shows other files through their usual previews. Keep Current removes the listed versions; Replace calls `NSFileVersion.replaceItem(at:)` inside a coordinated write that first checks the file's size and modification date against the listing; Keep as Separate File lets the version write itself to a staged file that is moved into place only where nothing exists, named as Obsidian Sync names conflict files. Each version used is marked resolved and removed inside a coordinated write of its file; nothing else is removed. Open documents take the result through the external-change path. Real iCloud and third-party providers still have to be tested on devices.

A drawing insertion is two ordinary file operations: save the drawing file first, then insert its embed into the open note, which autosaves. Cancelling the editor creates nothing. If the note is no longer open or conflicts, the drawing remains in the attachment directory and the user is told where; pasted and picked attachments are kept the same way, and the missing embed is reported. Do not delete a drawing automatically merely because insertion failed. A drawing is inserted after selected text, never replacing it, and an embed or link inserted after the note changed follows the text it was placed in. Embeds are inserted on their own line after any frontmatter, keeping blank lines so paragraphs never merge and a following `---` never becomes a heading underline.

Graphite's own writes coordinate with its own vault file presenter, so they are not reported back to Graphite as external changes. Saved notes and drawings refresh only their own index rows. External changes reported for up to 200 individual files are refreshed file by file; larger or directory-level changes trigger one reconciling scan, and a scan requested while one runs follows it rather than being dropped. A refreshed path that no longer exists is removed with every file inside it, and a refresh never indexes hidden or symbolically linked items. Changes inside hidden folders such as `.obsidian` refresh nothing, and previews reload embeds only for changes they can show. Changes reported without a pause are refreshed at most 2 seconds after the first of them. The reported paths are classified off the main thread, and a refresh for individual files re-reads only the open tabs showing those files. A PDF changed by another app reopens on the page being read, and edits made while it reopens are kept as a conflict. A vault whose `.obsidian/app.json` cannot be read uses Obsidian's default settings. A note save that is already running is awaited rather than rejected, so navigation and autosave never race.

PDF UI documents stay on the main actor. A background worker reopens the baseline snapshot taken when the PDF was opened and replays the session's immutable edit commands before writing. This avoids sending a live PDFDocument across actors or serializing a textbook on the UI thread. After each successful save the written file becomes the new baseline, so later saves replay only newer edits. Successive ink updates to one page merge into one edit, and each update converts only the strokes that changed. The page's re-editing record (its archived PencilKit drawing) is not rebuilt at every stroke: the canvases write it once before a save, an export, a page-structure change, or when a canvas is released. A page's stored drawing is decoded in the background when its canvas is created; the canvas takes input once it is shown. External changes invalidate the baseline. A PDF that carries Graphite drawing metadata opens as a drawing, not as a notebook, so annotating it cannot silently invalidate its strokes.

PDFKit writes every object of the file it read, whether or not anything still refers to it, unless the page tree changed. Each save of a re-read file therefore kept the annotations it replaced: a picture moved, turned or cropped, erased ink, removed markup. Four moves of one photo left 4.4 MB of a 5.5 MB PDF unreachable. After PDFKit writes, `PDFObjectCompaction` (GraphiteApple) rewrites the file with only the objects reachable from the trailer, each copied byte for byte with its number, the others listed as free; outlines, links, form fields, page labels, named destinations, document information, other applications' annotations and Graphite's keys are reachable and so kept exactly. It understands only the single uncompressed cross-reference table PDFKit writes; an incremental update, a cross-reference stream, an encrypted file or a syntax error leaves the file as PDFKit wrote it, and so does a compacted file that does not open with every page. The same pass writes a picture's appearance image as the picture's own JPEG (`DCTDecode`), with the color space PDFKit wrote, when the picture key (`PDFPageManager.storedPictureKeys`: `GraphitePictureV2` for a picture turned by hand, `GraphitePictureV1` for an upright one, one list shared with `PDFPicture`) holds a JPEG of exactly the image's size and color components (RGB or gray) and the soft mask is fully opaque (a turned picture's appearance draws that same image through a rotation in its content stream, which is left as it is, so the swap needs no transform); and it removes the copy of that key from PDFKit's markup data (PDFKit and other readers read the annotation's own keys, and PDFKit does not put the copy back; Apple's markup tools, should they rebuild an annotation from that copy, would leave an ordinary stamp that still shows the picture). Saving, Save a Copy and page export (`PDFFileService`, `PDFPageManager.export`) all compact. Measured on a Mac (debug build of the tests; the compaction alone in an optimized build): a 102 MB, 592-page lecture saved in 0.27 s before and 0.39 s after (compaction 0.05 s optimized), a 30 MB, 695-page textbook in 0.11 s before and 0.22 s after (0.03 s optimized), and an unedited save makes such files slightly smaller (old unreachable objects of the original go too). Not measured on an iPad.

Encrypted PDFs, and PDFs whose permissions forbid annotation or document changes, open read-only. A PDF with digital signatures (a `/Perms` dictionary in its catalog, `/SigFlags` AppendOnly, or a signature field with a value) opens read-only until the user chooses Edit Anyway and confirms Edit and Invalidate Signature, because PDFKit rewrites the whole file and any save invalidates the signatures. A save that fails for a reason other than a conflict keeps the edits, is retried with increasing delays, and offers Save a Copy or Discard Edits. Autosave waits 10 times as long as the last save took, between 2 and 30 seconds. Baseline copies in the temporary directory carry the process identifier and are removed at the next launch when their process has ended.

PDF form fields are shown read-only: `PDFViewPageObserver` marks the form fields (widget annotations) on visible pages read-only in the live document, because Graphite records no edit for a typed value and a save would drop it. Filling forms is not supported yet. Thumbnails draw a page's own content off the main actor, one page at a time, skipping cancelled rows; pages of the open file are drawn from a separate copy mapped from the file the session read, reopened every 64 pages, and annotations are drawn over the content on the main actor. All viewers share one thumbnail cache with a budget based on device memory (at most 32 MiB). Embeds of one PDF annotate one at a time (`EmbeddedPDFSessions`): before an embed starts annotating, the other embeds and a PDF view showing that file are saved, and a clean stale copy is read again. A session whose closing save failed is kept in memory until an embed of that PDF shows it again. Hidden tabs keep at most the most recently visible PDF open; older hidden PDFs are released after a successful save, never with unsaved edits, a save running or a conflict, and reopen at the same page when shown, losing that PDF's undo history.

Each PDF's undo history belongs to its session (`PDFSession.undoManager`, `PDFEditHistory.swift`), not to a view or a page canvas. PencilKit would otherwise record strokes in the window's shared history, aimed at the page's canvas: releasing a canvas far from the page shown dropped its steps, rebuilding the view on a tab switch dropped them all, and two PDFs side by side shared one history. Page canvases now return an undo manager that records nothing; after each drawing change the canvas registers a step in the session holding only the strokes the change removed and added, with their places in the page's drawing (`PencilDrawingChange`, GraphiteApple). Undo and redo give the page its earlier or later drawing through its canvas when one edits the page, and otherwise straight into the page's ink annotations, rebuilding the ink tracker from the page's stored drawing record; the page is scrolled into view. A step refuses to apply when the page's drawing is not the one it recorded (a change outside the history), reports it, and leaves the history. Strokes are told apart by `PDFStrokeFingerprint`, which keeps a stroke's color and transform at the 32-bit precision PencilKit stores them with, so a stroke read back from the page's stored drawing, as when a tab switch rebuilds the view or a released canvas is made again, is the stroke the step recorded. Until 2026-10-10 it compared them at full precision, and a step for a stroke in a color made from a hex value, or one the lasso moved, refused after such a read. The tool picker's first responder and the PDF view return the session's undo manager, so the palette's Undo and Redo, ⌘Z, the system undo gestures, and the workspace's Undo and Redo buttons act on that PDF only. Markup steps use the same history.

Page changes are undoable too: rotating, moving, duplicating, inserting paper, importing and deleting pages. Every undo and redo is an ordinary `PDFEdit` that saving replays on the file, so the file and the open document never disagree; steps name pages through `PDFHistoryPage` boxes that follow a page when undo or redo inserts a new copy of it (a deletion undone, an insertion redone), and ink and markup steps recorded before a deletion reach the restored copy. Deleting first copies each run of consecutive pages as saving would write it (content, ink, markup and re-editing records, by replaying the edits on the baseline), which takes time proportional to the PDF; if the PDF keeps changing during three attempts, the pages are deleted without an Undo step. Copies up to a megabyte stay in memory, larger ones in a private temporary file named like the baseline copies. Bookmark changes, accepting a page-structure rewrite, and accepting signature invalidation are not undoable. The history keeps at most 100 steps (`PDFSession.maximumUndoSteps`), goes with the session when a hidden PDF is released or the PDF reopens after an external change, and is not kept across launches.

PDF pages, PDFs embedded in notes and the drawing editor share one Pencil palette (`PencilToolPalette`): the system's own tool picker, so it has every tool Apple Notes has (pen, fine liner, marker, pencil, crayon, fountain pen, reed pen, watercolor, eraser, lasso, ruler), each once, and PencilKit keeps each tool's color and width and the tool in use across canvases and launches. A first version built its own list of three pens in black, blue and red; on the iPad they all came up black: the state PencilKit saved for that picker held the standard picker's saved pen, marker and pencil rather than the colors the items were created with (in a simulator with no such saved state the colors held), so three pens of one kind were one pen three times. The palette leaves an app one accessory button, so Graphite's button opens a menu with its additions: Favorite Colors, Draw Shapes and Select Ink. Favorite Colors gives the tool in use one of the colors of Settings › Colors, the list the notes' Format › Color menu uses and the Colors plugin for Obsidian starts with, keeping the tool's kind, width, opacity and nib angle; PencilKit's only way to recolor the item in use is the deprecated `selectedTool` setter, used in one place. "Draw Shapes", also in the More menus, switches the shape tool (`GraphiteDrawsShapes`, one preference for every canvas); while it is on, the button shows the shape symbol, inverted. With it on, a stroke just drawn is replaced by the shape that `ShapeRecognizer` finds in it (Core; pure geometry on the stroke's points, with thresholds relative to its size that favour leaving a stroke alone): straight lines, level or upright when nearly so; arcs, which are parts of one circle drawn in one direction, at least 32 points across and turning through 24° to 300°; arrows, which are a line or an arc ending in a head drawn without lifting (back along one barb, to the tip, along the other); circles and ellipses; triangles, rectangles with right angles, and polygons of up to six corners. `PencilShapes` (GraphiteApple) builds the shape as a PencilKit stroke in the same ink and width, so a shape is saved like any other ink, and the replacement belongs to the stroke's one undo step. Handwriting, wavy lines, curves that bend both ways, spirals and scribbles stay as drawn.

All these canvases are `HistoryCanvasView`s, whose changes go to the document's history as `PencilDrawingChange`s (the drawing editor has a history of its own, `DrawingCanvasController.history`). The class also carries three corrections to PencilKit's lasso, each found in the running app. PencilKit's lasso selection is a text input inside the canvas (it serves Writing Tools) and makes itself first responder, which raised the keyboard over the page when strokes were selected with a finger and took the palette's Undo and Redo away from the document. A view with no input view of its own uses its ancestor's, so the canvas supplies an empty one, and the tool picker's hidden first responder (`PencilToolPickerHostView`) takes first responder back whenever it moves to a view inside one of its canvases; the selection stays, and its menu and dragging work without it (its keyboard shortcuts then do not reach it). A focused PDF keeps that first responder while it is being written on even when its tools are hidden (`PDFAnnotationInput.holdsFirstResponder`). The PDF view takes and gives up first responder on the turn of the main queue after SwiftUI updates it, not inside the update: when the first responder changes, SwiftUI asks its views about focus, which it cannot answer while it is updating them. It logged "Cycle detected" each time focus moved to a PDF beside a note, and once the tab bar held the document controls the update never finished. PencilKit tells strokes apart by an identity of their own and keeps showing the version of a stroke it already shows: a stroke the lasso moved is the same stroke to PencilKit, so after Undo the canvas still showed it in its new place while the saved file had it back. Undo and redo therefore put strokes back as new strokes built from the same ink, path, transform, mask and random seed. And a selection shows its strokes in a view of its own, so the canvas ends the selection (by changing the tool and back) before the history changes the drawing.

Each pen-up on a PDF page costs the same on a full page as on an empty one (`FR-104`). A stroke of an inking tool only adds a stroke after the others, so after `canvasViewDidBeginUsingTool` with an inking tool (`HistoryCanvasView.toolUseDidBegin`) the change is recognized from the stroke before the new one (`PencilDrawingChange(appendingLastStrokeOf:to:)`, through `HistoryCanvasView.changeSinceRecorded(to:)`), `PDFPageInkTracker.updateAppending` converts that stroke alone, `PDFPageManager` only adds its annotation when the record is deferred and nothing is removed, the session merges the update without building removal sets, and only the new annotation is hidden under the canvas. Erasing, the lasso, undo and redo, and a tracker that has not matched its strokes to annotations take the full path, which fingerprints every stroke and reads every annotation of the page. Before 2026-10-19 every pen-up took the full path: three passes over the page's strokes and four over its annotations. Debug builds, and builds made with `-DGRAPHITE_WRITING_TRACE`, trace writing (`PencilWritingTrace`, subsystem `com.graphite.study`, category `PencilWriting`): signpost events Pencil down, Stroke began and Pencil up, intervals over each part of the pen-up, and a log line with the tool each stroke begins with (and the tool `toolForDrawing` expects, the chosen one, the zoom and the bar or palette) and the width each stroke lands with in the drawing's points.

Saved PDF ink and vector drawings (SVG, PDF) are as wide as PencilKit drew the stroke. A point's size is not its drawn width: the pen and the monoline draw 2 × size − 4 points, the pencil about 1.7 times the size (`PencilInkRenderedWidth`, measured for the notebook import). `PencilStrokeSampler.centerLineSamples`, which every saved outline and ink list reads, gives each sample the drawn width for those inks; the fountain pen and the highlighter, whose drawn width turns with the nib, keep the size. Until 2026-10-20 the size was saved, so a pen of size 3 (2 points drawn) was saved 3 points wide and one of size 8 (12 drawn) 8 wide (`ImportedStrokeBuilderTests.testSavedPDFInkIsAsWideAsPencilKitDrawsTheStroke`).

Apple's palette is drawn above every screen of the app, and presenting a screen leaves the palette's first responder where it is, so Settings opened over a PDF being written on showed the palette on top of the Settings sheet (seen on 2026-10-10, on commit e4c22aa, in the iPad simulator). Each owner of a palette, the PDF view (in a pane or embedded in a note) and the drawing editor, therefore hides it while a screen is presented over its document (a sheet, a popover, a menu, an alert, a file picker, the photo library, or a full-screen cover such as the drawing editor over a PDF) and shows it again when the screen goes, with the tool chosen before, since it is the same `PKToolPicker`. A view is covered when it is not inside the screen presented last (`UIView.isCoveredByPresentedScreen`, which the note's Pencil double-tap also asks). UIKit tells the views under a presentation nothing when it begins or ends, so `PresentedScreenObserver` checks the view each time the main run loop is about to wait, after any event, timer or animation that can present or dismiss a screen, and the owner changes its views on the next turn of the main queue. It observes only while a PDF holds first responder for writing (`PDFAnnotationInput.holdsFirstResponder`) and while the drawing editor is open, and costs nothing while the app is idle. Under a screen the PDF keeps first responder, so the palette comes back with the PDF's history, but it no longer takes first responder back while covered: a text field in a sheet keeps it even when the PDF's view is updated under the sheet. The PDF, and the drawing editor, take first responder back when the screen goes, so the palette, which shows only for its host, returns even after a sheet's text field had it. The palette's own color picker, its system menu (Auto-Minimize, Pencil Settings) and Graphite's accessory menu (Select Ink, Draw Shapes, Favorite Colors) are presented from the palette's window, which the check does not walk, so the palette stays while they are open; a document's own menus (More, Drawing Options) are presented from Graphite's window, so the palette steps aside while one is open and returns when it closes.

PDFKit zooms a page by scaling the view that draws it, its overlays included, and PencilKit draws its tiles at the canvas's own zoom and the screen's scale. The laser pointer (`LaserPointerController`, one per canvas, and `LaserPointerOverlayView`, one per window) is for pointing at a page while presenting or sharing the screen. Holding the Pencil still at the end of a stroke turns the stroke into its shape, without the shape tool being on (Settings › Pencil Drawings, on by default, `StrokeHoldPreference`), and moving it on from there stretches the shape, as in Apple Notes. Every canvas carries a `StrokeHoldRecognizer`, a gesture recognizer that only watches: it never recognizes, cancels or delays a touch, and neither prevents PencilKit's recognizer nor is prevented by it. It follows the touch that draws (one of the touch types the canvas draws with, while an ink is in use) and reports when the touch has stayed within six screen points for 0.45 seconds after a stroke at least 24 points long (`StrokeRest`), each move, and the lift. PencilKit offers no way to change a stroke while it is drawn or to end it before the touch lifts: setting its recognizer to ended from outside left the stroke growing, and a stroke it is made to discard stays on screen until the lift whatever is done to the canvas. So `HistoryCanvasView` recognizes the shape from the touch's own points and shows it over the stroke in the ink's color. When the touch lifts there, the stroke PencilKit reports is replaced by the shape exactly as the shape tool does, in the stroke's one undo step. When the touch moves on instead, the canvas makes PencilKit discard its stroke (its recognizer is switched off until the lift, so the stroke grows no tail), the shape follows the touch (`RecognizedShape.dragging`: an open shape keeps its start and turns and stretches so its end is under the hand; a closed one keeps its middle and scales by the hand's distance from it), and at the lift the canvas adds the shape as a stroke of its own. That stroke cannot take its width and pressure from a drawn stroke, so the canvas remembers each tool's footprint (`StrokeFootprint`: the average size, opacity and pressure of its newest stroke, by ink and width; a tool's width is a setting, not a measure, and a pencil set to four points draws under two). With a tool that has not drawn yet, moving on goes back to drawing. A hold at the end of handwriting shows nothing, and a stroke that never arrives leaves nothing waiting.

Palm rejection: iPadOS cancels some touches of a hand resting on the screen while Apple Pencil writes; the rest reach the page as finger touches, which scrolled or zoomed the page, opened PencilKit's menu, or selected text. `PencilActivity` follows the Pencil on every page (`PencilActivityRecognizer`, which only watches and never recognizes or fails, so it hears every Pencil touch of a sequence, even one that begins while a hand still rests; and a hover recognizer for a Pencil above the screen, told from a trackpad's pointer by its height). It is active while the Pencil touches or hovers and for 0.6 seconds after (`PencilActivityState`). The touch and the hover recognizers are held weakly, and before the state is read UIKit is asked about each (the touch's phase; the hover recognizer's state, enabled flag and window): one still going on counts as heard from now, and one whose ending was lost, as when its view left the window, is taken to have ended when it was last heard from. A touch or hover nothing can be asked about is over one second after its last report, so fingers scroll again within a second of the Pencil lifting or leaving hover range, never twenty seconds later. Hovers are told apart by a number each hover recognizer gets once, not by object addresses. While palm rejection is on (Settings › Pencil Drawings › Palm Rejection, `PalmRejectionPreference`, on by default, read as each touch lands) and a page is written on, `PalmRejectionRecognizer` takes every finger touch that lands while the Pencil is active (`PalmRejection.isHandResting`); with no Pencil activity it lets every touch go at once, however broad (the earlier rule that took any touch 34 points across as a palm, Pencil or not, was removed: it rejected thumbs and flat fingers, and with finger drawing took back the person's own strokes). The drawing editor counts as written on except while pictures are arranged. The PDF view's scrolling and zooming, its taps and long presses (Graphite's, and PDFKit's on each page as it is shown), the drawing editor's scrolling, zooming (its pinch is made to wait once UIKit creates it, when the canvas can first zoom) and picture taps, and PencilKit's long-press menu wait for it to fail (`require(toFail:)` through `PalmRejectionInstallation`, which holds them in a weak `NSHashTable`, so a recognizer made at a freed one's address is not skipped). PencilKit's drawing recognizer is never made to wait, so ink is never delayed or blocked, and palm rejection prevents nothing by itself. That a recognizer which never receives a kind of touch (the Pencil's, a trackpad's) does not hold up recognizers waiting for it is how UIKit is understood to work, and is what the existing markup tap also relies on; it is to be confirmed on the iPad. With finger drawing on, a stroke a hand began is taken back on the next main-queue turn only when every touch PencilKit's drawing recognizer follows is one of the hand's (`numberOfTouches` and `location(ofTouch:in:)` against the hand's touches, within half a point) and no Pencil touch is known to be down (`PalmRejection.isStrokeDrawnByHand`, `HistoryCanvasView.takeBackStroke(ofHand:)`): a Pencil stroke cannot be cancelled by it, even if `PencilActivity` missed the Pencil's touch. A hand that lands before the Pencil is used, on an iPad whose Pencil cannot hover, is left to iPadOS's own rejection. Notes, where the Pencil writes through Scribble, are not covered.

PencilKit's marker draws like a felt tip: broader as Apple Pencil tilts and broader or finer as it turns, so highlights over lines of text come out different heights. With "Highlighter Ignores Tilt" (Settings › Pencil Drawings, and the highlighter's options on the fixed bar; off by default, `EvenHighlighterPreference`), `HistoryCanvasView` gives each marker stroke just drawn one tip at every point when PencilKit reports it (`EvenHighlighter.evenStroke`, which keeps the stroke's random seed and so its texture): a chisel two thirds of the tool's width (PencilKit's marker chisel draws 1.5 times its point size, `chiselLengthPerPointSize`, measured with `renderBounds` on iOS 27 and macOS 27), turned across the stroke at every point (`tipAzimuths`, from the points a tip's length before and after, so a tremble does not turn it), at one opacity (`tipOpacity`, 1.5, PencilKit's value for a slow stroke; it gives a marker's points more than 1 and less the faster they move, and draws them stronger the more they have) and the stroke's average pressure, through the same points. A highlight is as tall across a line as the tool is wide (in the drawing's points, the tool's width over the canvas's zoom), and as wide in any other direction. Alpha first gave the points the whole width at a fixed azimuth, which drew highlights about 40 percent thinner than the tool, so each shrank at the lift.

PencilKit's live stroke follows the Pencil's tilt and cannot be changed while it is drawn, so with a real Pencil the stroke still changed at the lift (reported by the owner from the iPad, 2026-10-12). PencilKit (iOS 27 SDK) has no ink or tool option that ignores tilt: `PKInkingTool`'s `azimuth` (iOS 26) fixes only the angle, and monoline, which ignores tilt, is at most 4 points wide. So while the even highlighter is in use the canvas draws with an invisible stand-in of the highlighter (`EvenHighlighter.invisibleStandIn`: the same kind and width, its color's alpha 0; `HistoryCanvasView.toolForDrawing`, which `PDFPageCanvasView` scales for its zoom) and shows the stroke itself: `DrawnStrokeFollower` hears every sample of the drawing touch (coalesced, plus UIKit's predicted ones) and a `CAShapeLayer` under PencilKit's views draws the band the even stroke will be (`EvenHighlighter.bandPath`: through the points, rounded through each as PencilKit smooths a stroke, carried past each end as far as the band reaches; 22/24 of the tool's width tall; in the highlighter's color at `bandOpacity`, measured on a PencilKit canvas: PencilKit softens a marker's edges over a pixel or two, so a band 8 points wide reaches 0.86 of its color, 20 points 0.90, 50 points 0.99). Under PencilKit's views, as PencilKit draws a highlight under other ink, which stays as dark as it is. At the lift the invisible stroke becomes the even one in the highlighter's real ink (any stroke of the stand-in's ink is always given it, even after the tool changed), and the band stays until the canvas has drawn it (below). In a hosted test, a tilted stroke's band and the stroke it became are the same size and color but for PencilKit's softened edges; in simulator recordings of finger strokes, across a line, diagonally and over text, nothing changes at the lift but those edges. The preference is followed while the canvas is shown (`UserDefaults.didChangeNotification`), so the stand-in is never left in use without it. The band hides while a held shape shows and comes back if the stroke goes on; when PencilKit drops the stroke, as palm rejection or a held shape makes it, the band goes. It is one step with the stroke, before the shape tool or a hold looks at it, so a shape made from it is even too, as is a shape dragged from a hold.

Replacing the stroke just drawn (its even form, its shape from the shape tool or a hold, or a shape dragged from a hold) gives PencilKit a new drawing, which it draws anew: for about 30 milliseconds, two to four frames, it showed neither the stroke nor what replaced it (simulator recordings, highlighter and shape tool). `HistoryCanvasView.coverUntilRendered` first lays a snapshot of the canvas as it was beside it in its superview, with the canvas's transform, and hides the canvas's own content with an empty `layer.mask` (a snapshot over the canvas still showing would darken every translucent stroke, which is why a dissolve tried before was left out); a mask does not change what touches reach the canvas. The cover goes when PencilKit reports the drawing drawn (`canvasViewDidFinishRendering`, from the PDF view's and the drawing editor's coordinators), or after half a second. Recordings show no frame without the stroke since.

On a PDF page, a highlighter stroke covers the text under it at full opacity: the page canvas is a PencilKit canvas over the page, composited normally, and PencilKit gives no way to blend one kind of stroke differently from the others. Blending the whole canvas with multiply, as real highlighters and Goodnotes look, would make light ink vanish on dark slides and darken colored ink over figures, so it is not done; a proper fix needs the highlighter's strokes drawn in a layer of their own under the canvas, for display and in the saved annotations. Settings › Colors says so and points to a lower opacity or the text Highlight command, which keep the text readable (seen in the simulator at about 40 percent).

Pictures on PDF pages are placed from the More menu, the fixed bar, or an embedded PDF's toolbar while annotating. A new picture is at most 60% of the page as it is shown, in the middle of what the view shows of the page, and selected. `PDFPictureSelectionController` shows the selection frame over the PDF view, follows the page as it scrolls and zooms, and moves the annotation when a drag ends; the PDF view routes touches on the frame to it before the page's canvas. A finger tap on a picture selects it (a Pencil always draws), drawing or a tap elsewhere ends arranging, and a bar in the palette's place offers Delete and Done. Adding, moving, resizing and deleting are ordinary `PDFEdit`s (`addPicture`, `movePicture`, `removeAnnotation`) and steps of the PDF's history. A stamp annotation draws differently for the two uses PDFKit has for it: for the appearance written to a file the origin is the MediaBox's and the page's rotation is not applied; on a shown page the annotation applies the page's rotation and display box itself. One annotation cannot tell the calls apart, so each is made for one of them (`PDFPictureAnnotation`), as written documents and the shown document are separate (see Save and conflict boundary). A picture being arranged, on a page or on a drawing, can be turned by any angle with the rotate handle, an arrow on a stem above its selection frame (`SelectionFrameView.allowsRotation`: the frame is a view turned by `rotation`, and its owner gives and is given its `unrotatedFrame`; the turn follows the finger around the frame's middle and holds at 0°, 90°, 180° and 270° within 5°, with a tick of the selection haptic; on a frame narrower than two handles the rotate handle stands further out, clear of the corners' handles). Where the handle above the frame would be outside the view the frame is in, or under its bars, as for a picture at the top of a PDF's first page where it fell over the tab bar and no touch reached it, it stands below the frame instead (`rotationHandleStandsBelow`, decided again as the frame moves or its scroll view scrolls, and kept while the handle is dragged). The rotate handle and the corners' handles follow one rule for where a touch reaches them, the reachable region: the bounds of the view the frame is in less its safe area, where bars cover it, which moves as a scroll view scrolls. A corner's handle that would reach out of it moves inward along the frame's sides until its 44-point touch area is inside, never past the opposite side (`SelectionFrameView.handleCenter`); this covers a picture near the top of a PDF view, whose corner handle had been under the tab bar, which took its touches, and lassoed ink past a page's edge (see the lasso above). On a PDF page the frame also stays inside what the PDF view shows (`SelectionFrameView.staysInSuperviewSafeArea`): it is drawn only there, and touches outside it are refused, so they go to the bar; before, the frame's line was drawn over the tab bar. Frames around ink and pictures in a canvas leave that off, since ink may hang past its page. The region is kept in the superview's coordinates: on a frame turned by other than a quarter turn, a handle out of reach goes to the nearest point at which its touch area, turned with the frame, is inside it, still on its corner's side, and the frame is masked with the region as turned; taking the rectangle around the turned region instead drew a turned picture's frame and rotate handle over the tab bar. For VoiceOver the frame's value is its angle ("Upright", "Rotated 15° clockwise"), and its Rotate Clockwise and Rotate Counterclockwise actions turn it by 15°, one step of the history each, and announce the new angle. A rotation by the handle changes only the angle, not the picture's bytes, and is one step of the history, named Rotate Image (`PDFSession.rotatePicture(_:to:)`, `DrawingCanvasController.pictureRotationChangeDidEnd`). On a turned frame a corner's drag is measured along the frame's sides and keeps the opposite corner where it is on screen; a crop frame turns with the picture about the picture's middle, and the part kept becomes a picture of its own at the same angle where it was shown (`PictureRotation.rectangle(_:withMiddleTurnedBy:about:)`). Taps find a picture by its turned outline. A two-finger twist does not turn a picture: it would compete with the PDF view's and the canvas's pinch to zoom. A picture can also be rotated a quarter turn clockwise with Rotate Image Right, the name of the step too, after Preview's Rotate Right and the PDF pages' own command (`PDFSession.rotatePictureRight`, `DrawingCanvasController.rotateSelectedPictureRight`), which keeps its angle from the handle, cropped, and brought to the front of or sent behind the other pictures, each one step of the history (`PictureEditing` in GraphiteApple, `PDFEdit.replacePicture` with a `PDFPictureOrder`, and the same operations in `DrawingCanvasController`). Turning and cropping change the picture's own bytes (a photograph stays a JPEG, anything else becomes a PNG), so every reader shows the result; the picture as it was stays in the undo history only, as the original file was only read when the picture was placed. A crop is chosen with the selection frame in a crop mode (`SelectionFrameView.cropLimits`: corners move freely inside the picture, and everything outside the frame is dimmed). On a PDF page the crop is taken in the page's coordinates and brought back to the image through the picture's own quarter turns (`PictureEditing.imageRegion`), so it keeps the part shown on a page turned any way. Reordering takes off and puts back only Graphite's own pictures and ink on the page; other applications' annotations stay where they are. Picture views (on a drawing, and the selection frame's drag preview) are drawn with Core Animation's trilinear minification filter: with the default filter a picture made smaller than its pixels showed jagged, pixelated edges. On a PDF page a picture is drawn by `PDFPictureAnnotation`, which sets high image interpolation itself, also after the PDF is opened again: PDFKit draws a stamp's saved appearance with the interpolation of the context it draws into, and PDFView on iOS draws it with low interpolation even with `PDFView.interpolationQuality` set to high, so a picture made small showed moiré once its PDF was opened again. Every document Graphite shows has `PDFPictureDrawingDelegate` as its delegate (`PDFPageManager.prepareForDisplay`, when the PDF is loaded and for pages put back by undo), which makes PDFKit read each stamp of the file as a `PDFPictureAnnotation`; at its first drawing such a stamp reads Graphite's picture from its keys (once, under a lock, as PDFKit draws on several threads) and draws it as after an edit, and any other stamp is left to PDFKit's own drawing. Other subtypes are read as without the delegate. Nothing is written: the file's stamp keeps its appearance and keys, and the written documents never have the delegate. Opened again in the simulator, a picture 720 pixels wide shown about 166 points wide is pixel for pixel what it was after an edit at the same zoom. The saved appearance itself (an image XObject with `/Interpolate true`, at the picture's own pixels) is drawn smoothly by Quick Look and Ghostscript; poppler shows moiré, as it does for the same JPEG drawn straight into page content, so nothing in the written appearance causes it. Pictures stay under the ink. A picture over the ink is not implemented: it needs a layer stored with each picture (a new version of the drawing record, and an order of PDF annotations that readers keep), a view over the canvas for it on screen, and the PNG, PDF and SVG writers to follow it.

In a note, a double-tap on Apple Pencil, or a squeeze of Apple Pencil Pro, starts a drawing (`UIPencilInteraction` on the editor's text view; Settings › Pencil Drawings, on by default): where the Pencil hovers, else at the cursor. A Graphite drawing there opens for editing, an image there is drawn on, and anywhere else a new drawing is inserted. The iPadOS settings are honored: a double-tap set to Ignore does nothing, and a squeeze starts a drawing only when iPadOS leaves it to the app to show its tools. A gesture reaches every Pencil interaction in the window, and the note stays in the window under the full-screen drawing editor, so the note answers only when no screen is presented over it, and `WorkspaceModel.beginDrawingAtCursor` does nothing while a drawing is open: a double-tap in the drawing editor is the editor's, answered by Apple's palette or the fixed bar, and never replaces the drawing (seen on an iPad with the fixed bar). The handlers are tested; the other gestures need a physical Pencil and are unverified.

What Graphite uses of Apple Pencil and PencilKit, and what it does not. From the system, according to Apple's documentation and not tried on hardware: barrel roll and hover previews in the canvases, the palette on squeeze and its undo slider (floating palette; the fixed bar answers double tap and squeeze itself), and Scribble in the note editor, which every text view has and Graphite does not turn off. From the system and seen in the simulator: the tool picker with every tool, and the lasso's menu. Added by Graphite: double-tap and squeeze in notes, holding at the end of a stroke to make a shape, a tap of Apple Pencil Pro when a stroke snaps to a shape or its shape is shown (`UICanvasFeedbackGenerator.pathCompleted`), favorite colors, shapes, and the fixed bar. Not used: custom tool items in the palette, the Scribble tool item (it would put a palette over every note), hover in notes beyond placing a drawing, and roll angle in Graphite's own drawing code, which has none. Apple Notes' handwriting refinement (Smart Script) has no public API in the iOS 27 SDK (Graphite's lasso offers Straighten and Smooth instead): PencilKit's headers offer nothing for it, and PencilKit reports its model as unavailable in the simulator. Whether the lasso's menu offers Straighten, Refine or Copy as Text in Graphite's canvases on a supported iPad is unverified; Graphite keeps the keyboard focus away from the lasso selection to keep the keyboard down, which may hide them.

PDFKit rewrites the document when a save also inserts, deletes, or moves pages. That rewrite drops the standard annotation name (`/NM`) and Graphite's own annotation keys, so Graphite keeps a backup name and sets its keys again before writing. It writes a changed outline (bookmarks) only when pages also change, so Graphite forces the outline to be written. It also drops document settings such as page labels, viewer preferences and a declared catalog `/Version`; Graphite detects them, and digital signatures (`PDFStructureInspection.hasDigitalSignature`), and asks before the first page change. PDFKit resolves outline and link destinations lazily and writes one whose page was removed before it was read as a destination to the first page, so Graphite resolves them before moving or deleting pages and restores them afterwards; outline entries and links to deleted or unexported pages are removed (an entry with children keeps them and loses only its destination). Another application's named markup gets the same backup name as Graphite's.

## Markdown views

Markdown, PDF and canvas panes share `DocumentModeToggle` for reading and writing (one pencil button, as Obsidian's view toggle, marked by the accent and a faint fill while writing; it replaced a segmented Read/Write control on 2026-10-06, and it reads as a checked item in a toolbar's overflow menu, where the segmented control was dropped) and `UndoRedoButtons`, which follow the document's own history through `UndoAvailability`. A long press on Undo or Redo offers "Move Through Changes…", a scrubber (`UndoHistoryScrubber`) that undoes one change for each step a drag takes toward the leading side and redoes them on the way back, as far as the history goes (`UndoAvailability.step(by:)`), for every kind of document. When the documents area is at least 1,100 points wide (`DocumentToolbarLayout`), both sit in the window's toolbar just before More. While the system's floating Pencil palette is over a PDF, the PDF shows no Undo and Redo of its own, in the toolbar or the tab bar (`PDFSession.showsFloatingPencilPalette`): the palette has them, and two pairs for one history were redundant. Narrower, iPadOS would move them into the toolbar's overflow menu, a menu away, so they go to the end of the side's tab bar instead (`TabBarDocumentControls`), which is there anyway and mostly empty: each side of a split shows the controls of its own active document. A row of their own (`DocumentControlRow`) is used only where the tab bar has no room for them (a side under 480 points) or is hidden (focus). A compact width never uses the row (`DocumentToolbarLayout.usesControlRow` is false there): see the compact layout below. In focus, a PDF being written on with the fixed tool bar puts the tools, Undo, Redo and Write in one row. Where a side's tab bar has room for the tools as well (`DocumentToolbarLayout.showsPencilToolsInTabBar`: at least 320 points left for them beside one tab, the tab bar's own buttons and, when it holds them, Undo, Redo and Write), the tools of the PDF written on in its active tab go into the tab bar (`TabBarPencilTools`, the same `PencilToolRow` as the bar), scrolling sideways where they need more, after a hairline; where they can share it, with the fixed bar chosen, a tab is no wider than the tab area they leave, whichever tab is shown, so a long name ends with an ellipsis and keeps its close button rather than being cut off, and tabs keep their width when a PDF and a note take turns. That is an iPad in portrait or landscape with one side, and a side of a split in landscape when the sidebar is hidden. Otherwise they keep their row. In portrait on an iPad this leaves the navigation bar and the tab bar above the page while writing, two rows where there were four; a side too narrow for the tools, as beside the sidebar in portrait, keeps three. The drawing editor puts its tools, Undo and Redo, and its options in the same order, with Insert or Done in the confirmation position. On the iPad the keyboard's shortcut bar already offers Undo and Redo, so the note's keyboard toolbar leaves them out; the iPhone keeps them. On the iPad and the iPhone a note's Format and Insert menus are in its More menu while writing, since the keyboard's toolbar formats and inserts while typing; the window's toolbar keeps Draw. The Mac, which has no keyboard toolbar, keeps both menus in the toolbar. Markdown retains Live Preview and Source choices in its More menu.

The chrome follows Obsidian's Minimal theme (`GraphiteChrome`, `Hairline` in `GraphiteTheme.swift`): the tab bar, the control row and the fixed tool bar take the page's own background and are set off by a one-pixel line rather than a gray band and a `Divider`; a tab is its name alone, muted until it is the tab in use, which gets full-strength text and a faint fill (notes carry no icon, other files a small one), and its close button shows on the tab in use and under the pointer while keeping its room on the others, so tabs do not change width when chosen; the small buttons of bars outside the window's toolbar share `QuietIconButtonStyle` (drawn 36 points square, taking touches across the bar's 44-point height, `GraphiteChrome.barHeight`). A regular-width window's toolbar keeps to Back, Forward, the document's own controls and More: the Quick Switcher, the command palette and Focus are the last section of each document's More menu (`WorkspaceMoreMenuItems`; the window shows a More menu of its own for documents without one), Exit Focus stays in view while Focus hides everything else, and the title has room for a long name. Under the title (iPadOS 26 and later, and the Mac) a PDF shows its page ("Page 1 of 44"; Go to Page is in More) and a note its word and character counts, which used to float over the note's bottom corner; a phone shows the words only. The file list is drawn as Obsidian's file explorer draws it (`VaultEntryRow`, `FileTreeRowLabel`): names without icons, a folder marked by a chevron before its name that turns as it opens, each level indented with a faint guide line, files lined up with folder names, an extension muted after the name (always for files other than notes, which tells a lecture's note from its slides, and for notes where Settings shows extensions), no separators, and rows of 32 points beside a document and 40 on a phone. The panel picker above it shows symbols, which fit four panels in a phone's width or a narrow sidebar, and VoiceOver reads their names. The note's keyboard toolbar uses muted icons. The welcome tour (`WelcomeTour`, its pages in `WelcomeTourPage` and their words in `WelcomeTourCopy`) opens once per device: `FirstLaunchWelcomeTour` shows it when `LaunchMode.presentsWelcomeTour` is true (never in a hosted-tests launch) and the last vault has reopened or failed to, and marks it seen in `GraphiteWelcomeTourShown` when it closes. Compact widths (a phone, or an iPad window as narrow as one) have a layout of their own, after Obsidian mobile. `GraphiteRootView` binds the split view's `preferredCompactColumn`, starting with the document and showing it when the file already open is chosen again (`VaultSidebar.showDocument`) and when the selection changes, which happens once a chosen file is loaded, so the slide to the document shows the new file rather than the one before it; the file list is a step back. For the same room, the recording control shows only while there is a recording to follow; a recording starts from the command palette. A PDF hides the bottom bar while the palette is docked at the bottom of the screen, and the bottom bar gives way while the keyboard is up or a note takes typing (`MarkdownSession.isTyping`, since with a hardware keyboard the keyboard's toolbar shows alone and no keyboard notification says so). The file list is a plain list in the page's color, its title switching vaults (`VaultSwitcherMenuItems`) in place of the vault bar, with the search field at the bottom. iPhone Duo uses the same layouts: the outer display is a compact width and the inner display a regular one, and the system stands the bars on the side. On iOS the More commands of a note, a PDF, a canvas or the window go into the system's overflow menu (`ToolbarOverflowMenu`), so the bar has one "•••" button and nothing doubles it when buttons overflow; the Mac keeps a More menu. Every bottom-bar button is a symbol with a title (the Tabs button a numbered square, `TabCountLabel`), because the system keeps items that show text in a horizontal bar. The buttons are separate toolbar items and groups with flexible spacers, and finding a file, a new note and the tabs have a high visibility priority. Graphite's own views follow a partly folded display through `DisplayFolds`, which reads the system's active division regions from a view's geometry (iOS 27.1). The decisions are pure functions in `DisplayFoldLayout` (Core): the largest region no fold crosses, the split fraction that centres a divider on a fold, and an even column count over one. `WorkspacePanes` holds its divider on the fold without changing the saved split. Palettes, the notice banner and the Read Aloud floating player are placed beside the fold (`placedBesideDisplayFold`), and the library grid takes an even number of columns. The system's split view, sheets, alerts and menus move for the fold themselves.

Colors stay quiet: neutral surfaces, neutral document toolbars, and one accent. The default accent is an ink blue (`#2d5da1`). The ten presets are mostly muted (ink blue, graphite gray, teal, green, amber, orange, red, pink), with a bright blue and Obsidian's purple kept as choices; any other color can be picked. The accent is one color chosen for light appearance. `AccentLegibility` (Core) keeps it readable as text in both appearances, keeping its hue: in dark appearance it is mixed with white by the smallest amount that reaches 4.5:1 on the elevated dark background (`#1C1C1E`), and in light appearance with black by the smallest amount that reaches 4.5:1 on the grouped light background (`#F2F2F7`), which darkens the teal, green, amber, orange and purple presets; with Increase Contrast the target is 7:1 (`PlatformColor.graphiteAccent`, `AppearanceVariants`). Text size and motion follow the system's accessibility settings. A note's text size is the size chosen in Settings › Appearance (12 to 28 points) at the system's default text size, scaled as body text is when Larger Text changes it (`GraphitePreferences.noteTextSize`, `UIFontMetrics`), so notes grow up to about three times at the largest size, in Live Preview, Source mode, reading view and on canvases; footnote numbers are never smaller than 11 points. At the accessibility text sizes a property's name goes above its value. Controls drawn smaller than 28 points take touches over at least that (a tag's remove mark, a tab's close button, a heading's fold chevron). With Reduce Motion on, folding, the pages sidebar and animated scrolling and zooming happen without animation, and slides become fades (`GraphiteMotion`). Alerts take the first sentence of their message as the title, which says what happened, rather than "Graphite" (`MessageAlert`); something that happened as asked but differently, such as a file moved to the vault's trash folder because the storage has no system trash, shows as a banner over the document that stays until dismissed or another document opens (`WorkspaceModel.notice`, `NoticeBanner`). Labels, titles, toggles, pickers and menu items use title case; footers, messages and descriptions sentences.

A note's undo history belongs to its text view: UIKit gives each `UITextView` its own undo manager and ignores an overridden `undoManager` for typing, so the history cannot move to the session. `MarkdownEditorRetention`, owned by the workspace, therefore keeps the text views (with their controllers) of the three notes most recently hidden, holding at most 2,000,000 UTF-16 units together, and none after a memory warning or when another vault opens. `NativeMarkdownEditor` hosts the text view in a `MarkdownEditorContainerView` created for each SwiftUI view. SwiftUI makes a note's new view before it dismantles the old one (the split opening or closing, a tab moving to the other side) and can dismantle a view it has only just made, so the text view stays in the view that shows it until that view is dismantled and then moves to the newest view of the note that is left (`EditorContainersInUse`); that view's latest update is applied as the text view arrives. Moving it while the new view is made also took the keyboard from it inside SwiftUI's update, which made SwiftUI update again from inside that update. When SwiftUI dismantles the view first, the editor ends editing inside the text view (also in an embedded PDF or a rendered block's field) before letting go of it; giving the keyboard up can lay the window out at once and make the note's next view in the middle of that, and such a view gets the text view only once the old one has let it go. The text view itself is `MarkdownTextView()`, TextKit 2 by default, not `UITextView(usingTextLayoutManager:)`, whose factory skips the subclass's own property values. A hidden editor is suspended: it stops observing edits, releases its rendered blocks, and marks the session unattached, so insertions requested meanwhile go into the session's text; when it returns, the text it lacks is applied as one undoable replacement, the same path an external change takes while it is on screen. A kept editor is discarded when its tab closes or shows another file (closing a tab unloads its document first, because the editor's actions reference it). Beyond the bound, a note loses its undo history when hidden, as every note did before. On the Mac, each editor also has its own undo manager (`undoManager(for:)`), where AppKit would share the window's among notes.

Each Markdown session owns a lightweight `ReadingPosition` checkpoint containing a vertical offset. `MarkdownPreview` observes scroll geometry and restores that offset after its blocks load. Initial empty layout does not overwrite the checkpoint, and with no checkpoint the offsets a new view reports before it has decided what to restore are kept aside (`offsetBeforeRestoring`) and recorded only once it has nothing to restore: recorded straight away, an offset taken while the view settled could be restored as if saved and pull back a scroll made meanwhile. A new heading request overrides restoration. User scrolling cancels a pending restoration, and shortened content can clamp the restored offset. This retains the position across view recreation while the session remains open, without retaining offscreen view trees. It is not a semantic text anchor: changes to text, width, folding, or embedded content can move the passage at that offset. The checkpoint is not persisted across launches.

A note opens in one of Obsidian's three views: reading view, Live Preview, or Source mode. The default comes from Graphite's preferences.

Reading view splits the note into blocks (`NotePreviewDocument`): Markdown runs, headings with anchors for links and the outline, callouts, display math (centered), whole-line embeds, and bases. It renders the Markdown with Textual. Obsidian syntax that CommonMark lacks (highlights, colors, comments, task checkboxes, `$$…$$` in table cells) is rewritten to private-use markers before parsing and turned into attributes or attachments afterward, so the note itself is never changed; private-use characters U+E000–U+E00B already in a note are escaped before that rewrite (`ReadingMarkerEscaping`) and shown as written, in reading view and in Live Preview's rendered blocks; a marker that reaches Core's rewrite unescaped is shown as U+FFFD. `%%` comments are removed from the whole body before it is split into blocks, and `%%` in code, including fences inside quotes and callouts, is text. Callouts nest at most 16 levels deep. A web image on its own line stays Markdown rather than becoming an embed. Any task status character draws a checkbox, and statuses other than a space are checked. Section embeds accept Obsidian's heading path, `Note#Parent#Child`.

Reading view ticks tasks as Obsidian does: a tap on a checkbox turns `[ ]` into `[x]` and any other status into `[ ]`, changing that one character of the note through its session, so the autosave writes it and an editor that keeps the note's history can undo it. The checkbox knows its place from where the reading view got its text, not by searching for it: `NotePreviewDocument.locatedBlocks` gives each line of a Markdown run its offset in the body, through removed comments and dequoted callouts; `Footnotes` and `NoteBlocks` say where their prepared text and embedded parts start (`ReplacedTextOffsets`); and `preparedForReading` asks, for each task line it marks, where that line's task is in the note (`ReadingTasks.location`), following the lines a multi-line formula joins into one. A task's marker is followed by its status and, when it has one, its place: the status character's offset and a checksum of its line without the status (`ReadingTasks.markedText`). The tap is applied only if the text still has a task there on a line with that checksum, so a tap on a drawing older than the text changes nothing rather than another task; lines that cannot be followed exactly (a comment or link over two lines, footnotes, callout titles) draw a checkbox that is a picture. The parser turns a marker at the start of a list item into an invisible attachment carrying the task, and the list item style draws a button in place of the bullet; Textual's text selection overlay leaves the button out of hit testing (patch 10). A marker anywhere else, as in indented code or a table cell, reads as the note wrote it. A task inside an embedded note is ticked in that note: through its session when it is open (saved at once, since reading view reads embedded notes from their files), otherwise by a revision-checked rewrite of its file that keeps its byte order mark; the embed is then drawn again.

Tables fit the note as they do in Obsidian (`ObsidianTableStyle`, with the vendored Textual's `TableColumnsLayout`). A table narrower than the note keeps its own width. A wider one wraps its text and shrinks its images, each column giving up the same share of what it can give up, and no column becomes narrower than its widest word or formula; an image is not drawn narrower than 48 points. Only a table that still does not fit scrolls sideways, and only such a table is put in a horizontal scroll view (`Overflow(scrollsOnlyWhenWider:)`, Textual patch 16): every table used to be in one, which cost layout and scrolling work and took swipes meant for the note, and the scroll view also moved a table up and down by the fraction its content's rounded height exceeded its frame. The table is laid out in place at the width offered, measured with a layout that keeps exactly that width (a flexible frame grew to wider content, which then never measured wider and was centered over the column's edges), and moves into the scroll view once wider; it leaves it only when the column grows past the width it was found wider than, since its widths measured inside the scroll view switched it in and out without end. The style offers the table the width of its scroll container, which a horizontal scroll view does not do by itself. A cell with nothing in it keeps its place, so a heading after an empty first cell stays over its column. Cell borders and the header shading are separate rectangle views: one `Canvas` over the table needs a texture as tall as the table, which fails for a long table and left it without lines.

Textual finds math in the text Markdown leaves behind, which loses formulas in two ways: a line break splits a display block into separate text runs, and Markdown reads LaTeX punctuation (`\{`, `\\`, `*`, `_`) as its own. So before parsing, a display block is put on one line and Markdown punctuation inside any formula is backslash-escaped, which CommonMark turns back into the characters as written (`ObsidianInlineMarkup.protectingMath`). `$$` delimiters are paired by `DisplayMathLines`, which `protectingMath`, soft line breaks and Live Preview's block scanner share. MathJax environments the typesetter lacks (`align`, `equation`) are rewritten to ones it draws (`LaTeXCompatibility`): alignment environments become a two-column `aligned`, and `eqnarray` is drawn natively. Equation numbers are drawn as Obsidian's MathJax draws them, which is only where `\tag` asks: Obsidian leaves MathJax's `tags` option at `none`, so nothing is numbered automatically and `\notag` changes nothing. A display formula with a tag is kept as written between private-use markers; `LaTeXCompatibility.numberedEquation` separates the formula (drawn exactly as without its numbers) from its tags, each tag belonging to its row in `align`, `gather`, `eqnarray` and their relatives, to the last row in `multline`, and to the whole formula otherwise. When such a formula is a block of its own, `ObsidianMarkdownText` lays it out with `NumberedEquationView`, in reading view and Live Preview alike: the formula centered in the column, and each number, in parentheses (none for `\tag*`), at the column's right edge on its row's baseline. The typesetter gives no row positions, so a row's baseline is found by typesetting the rows down to it as a `gather` (rows are placed from the top, each by the rows above it) less that row's depth. Where the formula and its numbers do not fit side by side, the number goes on a line of its own below, and a formula of rows is drawn row by row, so nothing is cut off. A numbered formula among other text, as in a list item, gets its numbers after its rows; inline math and table cells have none. Formulas are measured and drawn through Textual's `DisplayMathRendering` and `DisplayMathView` (patch 11), which draws a formula as a canvas symbol so that rounding its frame to whole pixels cannot break it into lines. A formula it still cannot parse stays as source text. Code fences follow CommonMark everywhere (`CodeFence`, `CodeFenceTracker`): a fence closes only with a run of the same character at least as long.

For colored formulas, `LaTeXCompatibility` converts MathJax's scoped `\color{…}` declaration to explicit `\textcolor{…}{…}` groups and unstarred `\operatorname{…}` to upright `\mathrm{…}` text. The latter preserves the operator's label, but does not implement full operator spacing or limit placement; starred operators remain unsupported. These are rendering-only conversions. Textual honors explicit LaTeX colors in formula attachments and the inline-math image renderer; uncolored attachments retain their surrounding foreground style. This is not complete MathJax command or color-model compatibility.

Live Preview is the native TextKit 2 text view editing the note's exact source. Nothing is converted.

- **Hiding markup.** Markup is hidden with attributes only: a near-zero font and a clear color. A quote's `>` keeps its width under the bar drawn over it, and the lines a long quoted line wraps onto start under its text (after a list item's marker too), not at the margin where the bars are drawn. It shows one element at a time, as in Obsidian (`RevealedMarkup`). An inline element (bold, italic, strikethrough, highlight, code, inline math, a link or inline embed, a footnote, a color) shows its markup while the selection touches it, a cursor at either edge included, so the closing `**` stays in view while typing at the end of bold text; the elements around it show theirs too, because the selection touches them as well. A line's own markers (a heading's `#`, list, task and quote markers, a block's `^id`) show while the selection is on the line. The scanner gives every inline span the range of its element (`MarkdownStyleSpan.inlineElementRange`). Emphasis is matched with code, formulas, footnotes and links replaced by placeholders of the same length, so `**bold with a [[link]]**` is one bold element holding a link, and a `*` inside code is not a delimiter.
- **Restyling as the cursor moves.** Only the markup that starts or stops showing is restyled (`MarkdownTextStyler.applyRevealedMarkupChange`). The lines looked at are the old and new selections' lines, or, for a selection that grows or shrinks, the lines around the end that moved (`RevealedMarkupChange`). Within them, only the markers whose state changes get new attributes, with the spans around them (a heading's size, bold text around a link) applied to the marker alone; a color's markers are restyled wherever they are in its paragraph. A formula or a drawn replacement is always restyled whole. Rendered blocks the cursor enters or leaves are found from the ends of the two selections and restyled whole. Edits still restyle whole lines, with the lines revealed before and after the edit. `MarkdownBlockContextCheckpoints` also remembers the spans of the last two ranges it scanned until the next character edit, so a cursor moving along a line scans it once, and whether the note may contain `~={`, kept up to date from each edit, so a note without colors never walks to the blank lines around a line looking for them.
- **Taps.** A tap on a link whose markup is hidden follows it, also on the cursor's line; a tap on a link that shows its markup places the cursor in it. A drawn checkbox takes a tap unless the cursor is on its line, where `[ ]` shows as written. On the iPad a touch on a rendered block's view or a fold button belongs to it: the text view's own gestures (taps, the loupe, selection, drag) do not begin there, only its scrolling and zooming (`MarkdownTextView.gestureRecognizerShouldBegin`), and such a touch does not count as touching the note, which may start editing only after a touch on its text. A block's view that leaves the text view first makes whatever inside it has the keyboard give it up (`RenderedBlockHost.removeFromTextView`): UIKit hands a removed view's first responder to the view around it, and the note began editing, its cursor at its start and the properties showing their YAML, after a drag that started on a property scrolled them away. "Edit Source" is in each block's menu (a long press, or a secondary click on the Mac) and among its VoiceOver actions, not a button beside each block. The menu belongs to the block's hosting view (`RenderedBlockEditSourceMenu`: a `UIContextMenuInteraction`, or the Mac's `RenderedBlockHostingView` answering `menu(for:)`) and is made when it opens; SwiftUI's context menu worked out its items and symbol image every time the block was drawn, a large part of each frame of a scroll on the iPad.
- **One styling for both editors.** The iPad's and the Mac's editors style the text with the same object, `MarkdownEditorStyling`, which works on either text view through `MarkdownStyledTextView` (its text storage, selection, input-method composition, column width and typing attributes, which `UITextView` and `NSTextView` both provide). It follows every character edit from the text storage (`LivePreviewTextState`), takes in the text and its rendered blocks, restyles the whole note or an edit's lines, restyles the markup the selection reveals as it moves, reserves the heights rendered blocks measure, and owns the rendered blocks' engine below. Each editor says when to style, from its text view's callbacks, and what follows a restyle (the iPad lays out again; the Mac places its blocks), and keeps what is its own: the iPad's folds (whose regions move with an edit only when they were found in the snapshot the edit started from), keyboard and Pencil, the Mac's properties kept out of the cursor's reach. Markup and a block's source are revealed at the cursor only while the note is edited: on the iPad while the text view has the keyboard, on the Mac while it is the first responder, so a note opened from the file list, its cursor at its start, draws the callout or table there until a click in the note.
- **One engine for rendered blocks.** The iPad's and the Mac's editors share the rendered blocks' engine (`LivePreviewRenderedBlocks`): which blocks are concealed, the height each one's lines reserve (the height its view reported, else one measured by any editor at this width, text size, fonts and theme (`MeasuredBlockHeightCache`), else for the properties the height their view last had, else an estimate kept for that width (`LivePreviewBlockHeightEstimate`)), the views placed on the layout fragments TextKit has laid out for the viewport, the pool of views kept off screen (`DetachedWidgetPool`: 24 MB on the iPad, emptied on a memory warning, 64 MB on the Mac, each view estimated from its block's size, a table from its cells, so a note of small tables keeps most of its views as it scrolls back; keeping and taking a view cost the same however many are kept), and the refresh of their environment (`LivePreviewWidgetSignature`). The views are `UIHostingController`s on the iPad and `NSHostingView`s on the Mac, made by the same code (`RenderedBlockHost`). A view is given the height its lines reserve in the text now; a height measured since, at a new width or by another editor, restyles the block from the placement pass, on the next turn of the run loop. A report within a point of what the text reserves keeps it, so a block is not restyled for a rounding. The properties keep one view while they are edited, though each edit gives the frontmatter a new key, so a field being typed in keeps its state. What stays each platform's: when a pass runs (UIKit's layout passes, with the retries below; AppKit's report of each layout of the viewport, `textViewportLayoutControllerDidLayout`, macOS 27), folds (iPad only), and when the properties show their YAML: on the iPad while the cursor is in it, as any block's source; on the Mac only after the view's "Edit Source", until the cursor leaves it, as in Obsidian, the cursor kept out of the concealed YAML. The spelling checker marks nothing in a concealed block on the Mac.
- **Rendered blocks.** Blocks such as properties, tables, math, callouts, embeds and bases (`LivePreviewBlockScanner`) are hidden the same way. Their last line reserves the height of a SwiftUI view, which is placed over it. The views are positioned from the layout fragments TextKit has laid out for the viewport, from its first line in the viewport for a block that starts above it; forcing layout elsewhere would move the text they must line up with, and a fragment outside the viewport keeps an estimated frame (a jump to a heading placed the callout above it over the heading). A view whose fragment a restyle replaced, as a change of appearance does to all of them, stays where it is until TextKit lays the fragment out, and while TextKit has no viewport range the views stay rather than being removed (removing them made each report its height again, restyle, and lose the viewport again, without end). Such a fragment is laid out in the same pass: the viewport is laid out and the views placed on it, once more if that layout scrolled the view (as when a block below a selection UIKit keeps in sight takes its height back). Waiting for the next turn of the run loop showed, as the cursor left a drawing, a frame or two with the text below already moved down and the drawing's space empty. When a view's measured height changes the text below it, placement runs again on the next turn of the run loop, a bounded number of times. Each view lives in its own hosting controller, which does not inherit SwiftUI's environment from the editor, so the appearance and accent are passed in explicitly. When they change (text size, Colors, the accent, light or dark, the note's name), every view is given the new environment in place and keeps its own state; when only the index changes, as after each save, only bases, embeds and the callouts that hold one are, since only they read it (a callout of text only was drawn again each time typing paused). A changed file (`drawingVersion`: a drawing saved, or any file the vault shows changed, the note's own save included, since the system reports it back to the vault's file presenter) reaches every view in place too: each looks its files up again and keeps showing what it shows until then, and a table or callout keeps its prepared text until the new one is ready. The views used to be rebuilt for it, and a new view shows nothing until it has found its file, so every drawing in the note blanked for a few frames a moment after each pause in typing. A view whose block scrolls off screen, or that the cursor enters, is kept in a pool bounded by an estimate of its memory (audio and video players are never kept) and shown again when the block returns; the pool empties on a memory warning. A view made again for an embed the pool no longer keeps draws, in its first frame, the picture it showed last: where each embed's image was found is remembered (`LivePreviewEmbedImageLocations`, bounded) and `ReadingImageCache` keeps the decoded picture, and the lookup replaces it if the file changed. Measured heights are also recorded in a bounded cache shared by every editor, keyed by the block, the column width and the text size, so a note opened again reserves its blocks' measured heights on the first layout. A note styled before its text view has a width (as when it opens again in a tab) can only estimate them; each view's report is compared with the height the text actually keeps for it (`heightsKeptInText`), not with the shared measurement, which had matched the report and left the estimate in place: the properties of a long frontmatter kept about 260 points of empty space below them, so an embedded PDF under them sat lower than before and a tap where its toolbar had been landed on the text and started editing.
- **Editing a table in place.** As in Obsidian, a Live Preview table stays drawn while its cells are edited (`LivePreviewTableEditor`, `LivePreviewTableEditingOverlay`). A tap on the table finds the cell from Textual's cell bounds (`interactiveTableOverlay`, Textual patch 17) and opens an editor over it holding the cell's Markdown, `<br>` shown as a line break (`MarkdownTableEditing.editableText`). The editor is a native text view (`TableCellTextField`: `UITextView`, `NSTextField`) rather than SwiftUI's text field, which on the iPad took a hardware Return as submitting and gave up the keyboard, losing what was typed next; it decides what Return (the cell below, adding a row after the last), Tab and Shift-Tab (the next and previous cell, adding a row after the last cell), Escape and the arrows (out of a one-line cell) do, and puts a line break in the cell on Shift-Return. After a key moves the editor it shows the new cell's text at once, since keys typed before SwiftUI's next update went into the old cell's text and were written into the new cell. A tap that opens another table's editor takes the keyboard from the cell being edited at once (`TableCellTextField.endEditingInOtherTables`), writing its draft: keys typed before the new field took the keyboard went into the old cell. Smart dashes and quotes are off in it, text an input method is still composing is not taken as the cell's, and each cell has its own undo history, emptied when the editor moves (the Mac's shared field editor would otherwise apply typing undone after a move to the next cell's text). The draft is written into the note when typing pauses for 400 ms and whenever the editor moves or closes, as one undoable edit made by `MarkdownTableEditing` (Core), which changes only that cell's characters: spacing, alignment padding, outer pipes, indentation and line endings elsewhere stay as written, a typed `|` is escaped and a line break written as `<br>`. The block's menu (long press, secondary click) adds a Row and a Column submenu for the cell under the pointer: add above and below, before and after, move, delete, and the column's alignment; `RenderedBlockMenuContext` carries a block view's own items to the menu, which keeps one per hosting view and gives it to the view through the environment. "Edit Source" still shows the Markdown. Each edit gives the table a new key; while its view edits it, `LivePreviewRenderedBlocks.blockEditedInItsView` passes the view, its measured height and the cell being typed in to the table found at the same place, as the properties keep their view. That place is the table's start, moved through every character edit before it (`moveBlockEditedInItsView`), so text added above the table, as by another app, does not lose it. The coordinator finds the edited table at that place before its key (`rangeOfBlock(withKey:editedBy:in:source:)`): after an edit of one of two identical tables, the other has the key the first had, and a row added in the same moment went into it. When the blocks no longer list the table, as when they are let go for Source mode, it is found again in the text, so the draft written as the views go is kept. The hold belongs to the editor that took it and is let go half a second after that editor ends, once the last edit's restyle has passed the view on; another table's editor ending, as a tap moves editing to that table, leaves it. The coordinator waits a turn while the text is mid-edit or composing. A cell edit that makes the table wider than the column moves it into its scroll view, which builds the cell editor again and closes it (the draft is written first).
- **Edits made for the iPad's text view without the keyboard.** `UITextView.replace(_:withText:)` on a text view that did not have the keyboard ran the system's smart dashes over the whole note, though they are off for it (iOS 27): writing one table cell turned every `---` of the delimiter row, and of the frontmatter, into `—` (seen once before after a property edit, without a cause). The iPad's editor makes such edits (adopting text from a rendered view or an external change, an edit from the toolbar, a task's checkbox) through `replaceCharacters(in:with:in:)`, which uses `replace` only while the text view has the keyboard and otherwise changes the text storage and registers the undo itself.
- **Bases inside notes.** Tables, cards and lists in a note take their natural height and scroll with the note (at most 100 rows, with a note pointing to the full base), because a scrolling box inside a scrolling note traps the finger. Maps keep a fixed height, the plugin's `mapHeight`, except that a note narrower than 600 points (a phone) makes a map no taller than it is wide (`BaseEmbeddedHeight`), so it leaves room beside it to scroll the note.
- **Drawn replacements.** Bullets, task checkboxes, quote bars, `Note > Heading` separators and `$…$` inline math are drawn by a custom layout fragment (`ConcealedReplacementLayoutFragment`) over their invisible source characters, by both editors: the fragment draws through UIKit on the iPad and AppKit on the Mac (a flipped `NSGraphicsContext` over TextKit's context; symbols tinted in one color so a checked box's mark stays cut out). Kerning reserves the drawn width. Tapping or clicking a drawn checkbox edits `[ ]`/`[x]` through the text view, so undo works.
- **Focus.** The text view starts editing only when touched or when Graphite asks. SwiftUI's focus system otherwise hands it focus when another control finishes editing, which would raise the keyboard and scroll to the cursor. While the note's view is dismantled (another tab shown, reading view, the split changing), the text view refuses focus (`MarkdownTextView.refusesFocus`): ending editing in the embedded PDF inside it hands focus on to the text view, and one touched within the last second took it, began editing, and made the note's tab active again, which undid a link or an embed's Open in PDF View that had just shown another tab of the same side. The markup at the cursor is revealed on the next turn of the run loop after editing starts: UIKit places a tap's cursor after `textViewDidBeginEditing`, and restyling before that would invalidate the layout the tap is measured against.
- **Heading jumps.** A jump to a heading lays out the text before it and keeps the heading at the top while the views above it settle their heights (`HeadingJumpPin`): while a block on screen above it has not reported its height yet, and for 1.5 seconds after the heading last had to be moved back or such a block reported (layout passes stop while a base loads, so the pass after its report is the one that moves the heading), at most 10 seconds after the jump; dragging the note or starting to edit ends it. When a restyle replaces the heading's line while a block above grows, TextKit lays it out again only within the viewport, which the growth can leave below the heading, so the pin lays out the text through the heading itself, as the jump does. A base inside a note reports no height while it shows its progress placeholder (`LivePreviewEmbedLoadingKey`), as other embeds do while loading, so a base still loading its rows keeps the jump pinned and its text does not shrink to the placeholder and grow again. UIKit lays the viewport out for the jump's offset only after the text view's own layout pass, which therefore still sees the lines laid out for the old offset; when those start below the top of the view or end above its bottom (`ViewportLayoutCoverage`), the viewport is laid out again and the blocks placed on it, so a base just under the heading is not left blank (iPhone, `Restaurants.md` with 14 embedded bases, 2026-10-19). A jump names the heading by its text and its occurrence among headings that read the same, so the Outline reaches the one chosen, in the editor and in reading view.

Source mode is the same editor with nothing hidden.

Fenced code is colored by the language its fence names (```` ```cpp ````, ```` ```vhdl ````, …), in Live Preview, Source mode and reading view, on the iPad and the Mac. Core's `CodeLineHighlighter` tokenizes code line by line over UTF-16 units, in pure Swift without regular expressions or a JavaScript runtime, into `CodeTokenKind`s (keywords, types, functions, strings, numbers, constants, comments, preprocessor directives, attributes, keys, variables, other names, operators; a C preprocessor line is one directive throughout). A line ends in a `CodeLineState` (inside a block comment, a string spanning lines or a markup tag) that the next line starts in. `CodeLanguage` holds each language's words and rules and resolves aliases (`c++`, `hpp`, `vhd`, `sv`, `py`, `sh`, `yml`, …); a language it does not know stays plain. The editor's style scanner gives each code line's span its `FencedCodeBlock` (the fence's language, where the code starts, its quote depth), kept in the scanner's block state, so `MarkdownTextStyler` colors only the lines a restyle covers: it follows the block's earlier lines to find the state the first one starts in, without making tokens, and keeps each highlighted line's starting state in an attribute (`codeLineStateKey`). When the restyled lines end in a different state than the next line was colored for (typing `/*` or `"""`), it recolors the following lines until a line's stored state agrees again or the block ends; hidden lines (folds, callouts drawn as views) keep their concealment. Reading view gives Textual Graphite's tokens through a hook added to the vendored copy (`textual.codeSegmenter`, patch 14), synchronously and cached by block text (`CodeSyntaxHighlighter.tokens`), so a block never shows uncolored first; Textual's Prism highlighter, through JavaScriptCore, still colors languages Graphite does not tokenize, there only. Colors come from a `CodePalette` (`CodeSyntaxColors.palette`) for the code theme chosen in Settings › Editor (`CodeColorTheme`). Obsidian's, the default, is Obsidian's own `--code-*` colors, made readable as text by `AccentLegibility` and moved further with Increase Contrast, and a vault theme that changes them (its palette or its `--code-*` variables, read by the theme probe from Prism token classes) has all of them used instead. One Monokai, Dracula, GitHub, Solarized and Xcode each bring their own box and text colors, in a light and a dark version that follow the appearance, each color moved just enough to read on the theme's box (`ThemeContrastGuard`, 4.5:1, comments 3:1, 7:1 and 4.5:1 with Increase Contrast).

Both editors draw a fenced code block as one box across the text column, with a one-point border and 4-point corners (the vault theme's border and radius where it sets them): each line carries a `CodeBlockLineDecoration` (`ConcealedReplacement.codeBlockKey`), and `ConcealedReplacementLayoutFragment` fills that line's slice of the box from the column's left edge (TextKit places an indented paragraph's fragment at its indent), rounds it at the opening and closing fence, draws a thin guide at each level of indentation (the vault's tab size), strokes its part of the border (the sides, and the top or bottom with its corners on the first and last lines), and draws the language as written after the fence at the top right. Code lines are inset from the box's edges and set without the space between paragraphs. In Live Preview a block's fences are hidden, leaving short lines that pad the box above and below, unless the selection starts or ends in the block; `applyRevealedMarkupChange` restyles the fence lines of the block the selection enters or leaves, and `MarkdownEditorStyling` does after an edit that moves the selection out. Source mode keeps the fences in the box. Code quoted in a callout keeps a plain background inside its quote's bars. Reading view's `ObsidianCodeBlockStyle` draws the same box, border, label and colors.

A code block the user changed is formatted when the selection leaves it, or editing ends with the cursor in it (Settings › Editor › Format Code Blocks, on by default). `MarkdownEditorStyling` notes a block's code when the selection enters it and, when the selection leaves, formats it only if that code changed meanwhile, so a note read, scrolled or moved through is never rewritten; each editor makes the replacement on the next turn of the run loop through its text view (`perform` on the iPad, `shouldChangeText` and `didChangeText` on the Mac), so Undo takes the formatting back as one step. Core's `CodeFormatter` re-indents by brackets and, for VHDL, Verilog, MATLAB, Lua, Ruby, shell and LaTeX, by block keywords (`CodeBlockKeywords`: `if … end if`, `case … when`, `begin … end`, `then … fi`, `\begin … \end`), keeps the indentation width the code already uses (else the language's usual one), trims trailing spaces, keeps at most one blank line in a row (two in Python) and none just inside a block, and adds spaces in code only: after commas, in `){`, `}else{` and `if(`. Strings and comments keep their text, a block comment's later lines are aligned under its first, and C's preprocessor lines start at the left edge. Python, YAML, SQL, assembly and markup keep their indentation; Markdown and quoted code (in callouts) are not formatted. It is lexical, like the highlighting, not a language's own formatter (clang-format, gofmt, black).

Fonts and font size (Settings › Appearance › Font): `NoteTypography` (UI) is the three resolved families, made once per change of the vault's font lists in `WorkspaceModel.applyVaultAppearance`, never while typing. Live Preview and Source mode get it in `EditorConfiguration.typography`: `MarkdownTextStyler` sets body text, headings (still `HeadingTypography` multiples, semibold), callout titles, footnote numbers and the inline title in the text font, and code, inline code, frontmatter source and Mac source math in the monospace font. A change restyles the open note through the same path as a size change (attributes only, so the cursor, the selection and the rendered blocks stay); measured block heights are keyed by the fonts too. Reading view and every embedded or Live Preview SwiftUI block read the `noteTypography` environment value, set by the root view (and by the editor for its hosted blocks): `ObsidianMarkdownText` sets its font, a code block style of Graphite's own (`ObsidianCodeBlockStyle`, Textual's default with the monospace font, since `.monospaced()` does nothing to a named font), and inline code in a named monospace family (SF Mono keeps Textual's own heading-relative code style). The interface font (`View.interfaceFont`) is used by content-like chrome only: file and folder names, tab titles, the outline, search result names, paths and excerpts, and backlink names and excerpts. Buttons, menus, alerts, toolbars, the properties table and Settings keep the system font, following Apple's guidance on system type for controls; an installed interface family follows Dynamic Type through `Font.custom(_:size:relativeTo:)` and Bold Text through `legibilityWeight`. Typing cost in long notes: Live Preview finds the note's folding regions after every edit (`NoteFolding.regions`), which read every line and had run a heading pattern again for every line of every section and the list pattern on most lines: about 15 ms of a keystroke in a 5,000-line note in the simulator's debug build. Heading levels are now found once per line, list items are read character by character (`NoteFolding.isListItem`, checked against the pattern by a test), and an edit inside one line of plain text moves the regions instead (`NoteFolding.regions(_:across:replacementLength:before:after:)`; refused for line breaks, headings, list items, fences, blank lines or a change of indentation). A text storage edit reported wider than what changed (a whole line, when attributes are set in the same edit) is narrowed to the characters that differ (`CharacterEdit.narrowed`) before blocks and folds are moved, so the first keystroke after a restyle no longer scans the whole note. Typing in a list item moves the blocks as typing in a paragraph does, unless the item's text starts with block syntax or the line holds `` ` ``, `~`, `$` or `|` (it could become a rule, a table row, code or math). Typing in a body line of a callout finds only that callout again, in its own lines (`LivePreviewBlockShifting.entriesFindingEditedCalloutAgain`): the line must start with `>` before and after the edit and hold no `` ` ``, `~` or `$`, and the callout found must cover all its lines, or the note is scanned. Both had scanned the whole note on every keystroke (Mac, 40-section note: 10.1 to 8.3 ms a keystroke in a list item, 10.4 to 8.6 ms in a callout).

## Canvas

A `.canvas` file (JSON Canvas 1.0, Obsidian's format) opens in a tab as a `CanvasSession`, while the Canvas core plugin is on. The file's bytes are the document: `CanvasFile` (GraphiteCore) reads them with a JSON reader (`CanvasJSON`) that records where every value is written, and exposes the cards and connections it understands; everything else (unknown keys and card types, entries it cannot show, key order, whitespace, line endings, a byte-order mark) stays in the bytes. An edit (`CanvasChange`, `CanvasFileEditing.swift`) becomes byte splices at those positions, so moving a card rewrites its `x` and `y` digits and nothing else, and new cards and connections are written as Obsidian writes them (one line each, its key order, ids of 16 hexadecimal digits), in the file's own layout. Applying splices yields the inverse splices, which the canvas's undo history keeps instead of copies of the file; undo gives the file back byte for byte. A canvas only looked at is never written; edits are saved after a pause through the vault's revision-checked writer, and a file changed elsewhere is never overwritten (the pane offers "Save a Copy" or "Use Other Version"). Untrusted input is bounded (16 MB, nesting depth 64, 2,000,000 values, 50,000 cards, 100,000 connections, coordinates within ±10⁷), and a damaged file opens nothing, says what is wrong, and is left alone.

The board is drawn in SwiftUI in three layers: one picture for the dot grid, groups, connections and cards too small or too many to show their content (below a third of full size, or beyond the 60 cards nearest the middle of the view); card views only for the cards in view, moved and magnified as one layer so a pan changes one transform; and the selection. Geometry (viewport, connection routes as Béziers leaving and arriving at right angles, hit testing, selection rectangles, group contents, snapping to the 20-point grid and to other cards, reading order) is plain Core code in `CanvasGeometry`. Gestures are UIKit recognizers on a view around a hosting controller that holds the board (`CanvasBoardHost`), since only they give a two-finger pan that also takes trackpad scrolling and see touches on the cards themselves; what a touch does is decided in `CanvasInteraction`, in view coordinates, the same for finger, Pencil and pointer. Canvases get no ink. Text and note cards use the reading view's renderer (`ReadingViewBuilder`), a PDF card one page, a media card the existing player, a base card the base's view; link cards show the site's name and address and open the browser rather than loading remote pages on the board. With VoiceOver or Switch Control on, the cards not shown as views get invisible elements positioned on the board, so every card is an element in reading order. The Mac app can look at a board; editing is iPad-only, as PDF annotation is.

The index reads canvases for their links (`CanvasLinks`) and not for search, as Obsidian does not search them either: file cards and group backgrounds are stored as whole paths from the vault's root (`/Folder/Note.md`), which match exactly their file in backlinks, and text-card links as note links are. Renames and moves rewrite file cards, backgrounds and text-card links through `CanvasFile.replacing`, in the same plan as note links (`VaultFileOperations`), and an open canvas takes the change in at once.

## Library and creating notebooks

The scope and its open parts are in [the checklist](Notebook-library-and-new-file-todo.md). On the iPhone the library takes the sidebar's file list's place. `LibraryView` holds no workspace: the views that do hand it values and actions (`LibraryVault`, `LibraryActions`, `LibraryEntryPresentation`, made in `WorkspaceLibrary.swift`), and failures reach it as `LibraryFailure` cases it words itself. `LibraryModel` (one per window, in the environment) lists the folder through `VaultStore.children`, filters and sorts it with Core's `LibraryListing` in the vault's sort order, and lists again when the vault, its sort order or `directoryVersion` changes. Recently seen previews stay in an `NSCache` keyed by path, modification date and size, bounded at 240 entries and 64 MB of decoded pixels (each entry costs its pictures' bytes); it is replaced on a vault switch and empties itself under memory pressure. Favorites are Obsidian's bookmarks. ### Scanning documents

Scanning is a native feature like the camera, not a core plugin. It uses VisionKit's `VNDocumentCameraViewController` (`DocumentScanner`, GraphiteUI, UIKit only) and is offered only where `VNDocumentCameraViewController.isSupported` is true, so an iPhone or iPad with a camera; the simulator and the Mac show no scan control. The offer is a value: `NewItemActions.saveScannedNotebook` and `EditorActions.scanDocument` are nil where scanning is not supported, and the New menu, the attach menu above the keyboard, the Insert menu and the editor's context menu build their entries from that. Cancelling the scanner returns nothing and writes nothing.

The scanner's pages (`CGImage`, turned upright) go to `DocumentScanProcessing`, which owns the one task that makes the PDF while the person waits (a progress overlay with Cancel over a note; in the New menu the button shows a spinner and a tap cancels). `ScannedDocumentPDFBuilder` (GraphiteApple, an actor, so recognition, JPEG encoding and PDF writing run off the main actor and stop at the next page when the task is cancelled) writes one PDF into memory: each page is sized to A4 width (595 points) and its picture's own proportions (at most 14,400 points tall), the picture is encoded as JPEG at quality 0.8 and drawn from those JPEG bytes so the PDF carries them as `DCTDecode` without encoding them again, and an invisible text layer is drawn over the words (`Tr 3`, Helvetica sized to each word's box height and spread with a kern to its width, because a stretched text matrix leaves the glyph positions unscaled and PDFKit then selects only the unstretched width). The words come from a `ScannedPageWordRecognizer`, a struct of one closure; `.onDevice` runs Vision's `RecognizeTextRequest` at the accurate level with language correction and the language detected from the page, one box per run of non-blank characters. A page whose recognition fails is still written, as a picture only, and the result lists those pages (`pageIndicesWithoutRecognizedText`); the workspace then says the scan was saved but cannot be searched. The PDF exists only in memory until the workspace saves it: Cancel or a failure leaves no file.

Saving goes through the paths a camera photo and a new notebook use. In a note, `insertScannedDocument` calls `saveAttachment`, so the file is "Scan 2026-10-21 14.05.pdf" (`ScannedDocumentName`, Core: Gregorian, the device's time zone, minute resolution; a second scan in the same minute takes the next free name) in the folder the vault's attachment setting resolves, and its embed goes in at the cursor with the same rules as any attachment (kept, with an alert, when the note closed or is in conflict). From the New menu, `createScannedNotebook` writes the file with `.absent` under a free name in the folder shown (or the vault's location for new files), refreshes the index and the listing, and opens it in a tab like a new notebook. Graphite's own index does not read the text of PDFs, so the text layer is for selecting, copying and Read Aloud in Graphite's PDF view and for searching in other PDF readers; vault-wide search of PDF text does not exist yet. `NSCameraUsageDescription` (already in `App/Info.plist`) now also names scanning.

## Reading Goodnotes and Notability files

Phases 2 and 3 (steps 1 to 7) of [the import checklist](Goodnotes-Notability-import-todo.md): the readers, and the conversion of pages, paper and ink into a PDF ([the Phase 3 design](Goodnotes-Notability-import-phase-3-design.md)). Nothing in the app calls them yet (Phase 4). Both live in GraphiteCore (`Sources/GraphiteCore/NotebookImport/`), import only Foundation, CoreGraphics and zlib, use no third-party code, and do no file I/O: each takes the archive's bytes, which its caller memory-maps, and returns plain `Sendable` values, so pages can be read from any task. `ZipArchive` reads the ZIP container (stored and deflated entries, each checked against its CRC-32 and inflated only when asked for into a buffer of exactly its recorded size). A notebook's files are not copied whole where that can be avoided: a stored file is a slice of the mapped bytes (`data(of:)`), and a recording is handed out in pieces (`copy(_:chunkByteCount:to:)`, one 256 KiB buffer for a deflated one, the size and CRC-32 checked at the end). `NotebookImportLimits` bounds every size read from a file before anything is allocated.

`GoodnotesNotebookReader` reads a `.goodnotes` notebook as `Docs/Goodnotes-format.md` describes it. Opening reads `schema.pb` and the event log into a `GoodnotesNotebook` (title, pages in order with their paper and bookmarks, outline entries, recordings); `page(at:)` decompresses and decodes that one page's layer into a `GoodnotesPage` of elements in drawing order (strokes with their path in one of the four tpl layouts, shapes, fills, pictures, text boxes with their rich text, older RTF text boxes and sticky notes). The protobuf wire format is read without a schema (`ProtocolBufferMessage`), ink paths through Apple's LZ4 framing (`AppleLZ4Decoder`) and tpl (`TplImage`), and all failures are typed (`throws(GoodnotesReadingError)`).

`NotabilityNoteReader` reads a `.note` as `Docs/Notability-format.md` describes it. `Session.plist` is read by Graphite's own bounded `bplist00` reader (`BinaryPropertyList`), because `PropertyListSerialization` hands back a keyed archive's UIDs as opaque objects; `KeyedArchive` resolves the archive one reference at a time, with a visiting set and a depth limit, and only along the format's key paths, so a cyclic object graph cannot make it loop. Opening reads the document-level values into a `NotabilityNote` (paper attributes, page geometry, shapes, pictures, typed text runs, imported PDF pages, recordings from the XML `Recordings/library.plist`, which `PropertyListSerialization` reads, and the timing of curves) and a small index of the curves; the packed little-endian curve arrays stay as slices of the session's bytes, and `curve(at:)` and `page(number:)` decode only the curves asked for, with their per-knot width factors, forces, altitudes and azimuths. Failures are typed (`throws(NotabilityReadingError)`).

Unknowns are reported, never guessed: each reader returns issues (`GoodnotesReadingIssue`, `NotabilityReadingIssue`) for every record kind, field, key, class or version the format documents do not describe, and for every part it skipped, with the typed error that made it skip. A part that cannot be read (an element, a record, a picture) is skipped and listed; the rest of its page is returned. Values read as strings are decoded once into enums with an `unknown(raw)` case (Goodnotes template ids, Notability paper attributes, shape kinds). The Python readers in `scripts/` remain the reference; `scripts/import-reference-counts.py` gives their counts for the sample tests.

Hardening from the audit's Import area (`Docs/solid/areas/import.md`):
- A deflated ZIP entry that declares more than deflate can produce (1,032 times its compressed size) is refused before anything of the declared size is allocated. `NotebookImportLimits.standard` allows 512 MiB per entry on the Mac and 256 MiB on the iPhone and iPad.
- A binary property list expands to at most `maximumPlainValueCount` values (250,000).
- Packed arrays are checked once, when they are made (`PackedLittleEndianValues`), and every little-endian read checks its range.
- A note's damaged recordings library, text run, PDF page layout or stroke timing is skipped with an issue, so its ink is still read. A Goodnotes schema that cannot be read is a version not known. A notebook without its event log is a typed error.
- Unknown Goodnotes element kinds and path layouts are kept as elements and reported by element.
- A path read from a file is a `NotebookArchivePath` before anything uses it: relative, no `.` or `..`, a non-empty name.

The conversion is planned in GraphiteCore and written in GraphiteApple:
- **Planners:** `GoodnotesPagePlanner` and `NotabilityPagePlanner` turn a reader page into an `ImportedPagePlan`: the page size in points; the background (a source PDF page, plain paper, or Notability's ruled or grid paper as `ImportedRuledPaper`); the strokes sampled into PencilKit points with their widths, force and tilt; shapes as ink along their outline (`ShapeOutlineSampling`, `NotabilityShapeSampling`); the pictures with file, frame, angle, crop and flips; and whether the page is bookmarked. What is simplified or not converted yet goes into the page's `ImportReportEntry` list.
- **Writer:** `NotebookImportWriter` (GraphiteApple) writes the plans into one new PDF, one page at a time. Ruled paper is drawn by `PDFTemplateGenerator` with the source's `PaperRuling` (line colour, width, row extent, grid column anchor; a paper without one draws exactly as before). Pictures are placed as Graphite pictures before the ink (`ImportedPagePictures`); a picture whose file is missing or does not decode is left out and reported. The ink goes through `PDFPageInkTracker`, so an imported page re-edits and saves like one drawn in Graphite. Each stroke's PDF appearance is the planned shape: Goodnotes' own outline, or the samples at their planned widths. PencilKit's point size is not the width it draws (`PencilInkRenderedWidth` holds the measured relation per ink). A bookmarked page gets Graphite's bookmark outline item (`PDFPageManager.bookmarkLabelPrefix`).
- **Recordings:** `GoodnotesRecordingPlanner` and `NotabilityRecordingPlanner` plan a notebook's recordings (`ImportedRecordingsPlan`), and `NotebookImportRecordingWriter` (GraphiteApple) writes each as an `.m4a` file of the source's bytes, copied in pieces into a staged file that is moved into place only when the copy checked out and nothing is at the destination. The stroke timing of a recording is reported as not kept.
- **Report:** `NotebookImportReport` gathers what the import did, as plain values for the import's caller: each source page written (with its strokes, placed pictures and bookmark) or left out, with its `ImportReportEntry` list; the notebook-wide entries (recordings, pages that cannot be cut, reader issues outside the pages); and a summary with one line per kind of entry (`ImportReportEntryKind`, each simplified, left out or a reading issue), its total and its pages.

## Responsiveness and freeze evidence

Graphite keeps evidence of freezes on the device, outside the vault, in `Library/Diagnostics` of its container (`DiagnosticRecords`, GraphiteApple; at most 80 JSON files, oldest removed first). `GraphiteDiagnostics.start()` runs from `GraphiteApp.init`:
- `MetricKitDiagnostics` subscribes to `MXMetricManager` and writes every `MXDiagnosticPayload` (hang, crash, CPU and disk diagnostics) as delivered, usually on a later launch, one file per payload period, also the payloads delivered before it subscribed.
- `MainThreadWatchdog` pings the main queue every half second from a utility queue. When a ping waits more than 2 seconds it suspends the main thread for a moment, walks its frame records into a buffer allocated beforehand (nothing is allocated while it is suspended), resumes it, and writes `MainThreadStall-*.json`: the return addresses with their image and offset, each image's load address and UUID for `atos`, and `DiagnosticContext` (the document and mode shown, the window size, and the last 30 events such as tab switches). `MainThreadStallEnded-*.json` follows with the duration if the main thread answers again. It does not run under a debugger.
- `PDFPaneHealthMonitor` (GraphiteUI) watches a PDF view that stopped taking touches, the freeze seen on the owner's iPad on 2026-10-13: a passive recognizer on the window (`PDFTouchSequenceObserver`, never recognizing or delaying) follows finger gestures that start on the PDF, and `UnansweredGestureCount` counts those that should have scrolled or zoomed and changed nothing (no scroll, zoom, edit or selected text; not within 2 seconds of the Pencil; not on a page with nowhere to scroll). A gesture that moved the pages counts the same when something put them back where it found them within a second (`UnansweredGestureCount.wasUndone`: moved at least 20 points or 5 % of the zoom, then back within 2 points), unless the gesture ended past an edge or a zoom limit, where the scroll view rightly springs back; it is settled a second after it ends, or when the next gesture begins. Three in a row within 30 seconds, with the touches reaching the PDF view, write `PDFStoppedTakingTouches-*.json` (with a `cause` field) (what the touch reached, every recognizer of the PDF with its state and touch count, the Pencil's activity, each canvas's state, the selection frames) and build the PDF view again (`PDFSession.viewGeneration`, as switching tabs does) after every canvas's ink is recorded. Touches reaching another view over the PDF only write `PDFTouchesReachedAnotherView-*.json`, at most every five minutes. Once a second it also puts right, and records as `PDFRepaired-*.json`, states that cannot last: a recognizer of the PDF under way with no touch for 2 seconds (reset), a page canvas on screen that is not counted as shown, does not record its changes, or takes no touches while writing, a canvas whose drawing a held shape switched off and whose touch never ended (`HistoryCanvasView.resumeDrawingLeftOff`), and a canvas on screen that is not the page's own (the view is built again). The embedded PDF viewer gets the checks but never the rebuild.

Ink is recorded before any canvas goes: `PDFAnnotationCoordinator.recordUnrecordedInk` compares a canvas's drawing with the drawing last recorded and applies the difference, at release, before every save (`PDFSession.save` asks for pending records before deciding there is nothing to save) and before a rebuild. When PDFKit lets go of a page's view while Graphite keeps the page's canvas, the kept canvas goes into the new overlay with its drawing, history and pending record; a new canvas restored the page's last saved record and lost the strokes drawn since.

`PencilActivity` hears a Pencil touch still going on at the touch's own timestamp, which UIKit advances only as the touch changes, and forgets a touch object whose type is no longer `.pencil`; a touch object left going without change, or given to a finger, otherwise kept every finger taken for a resting hand. `PalmRejectionRecognizer` also lets go of hand touches whose phase ended without the end reaching it. Whether either happens on an iPad is not established.

A word read aloud updates only the texts it leaves and enters in the reading view. The note's pane passes `MarkdownPreview` a `ReadingWordSource`, a function the view calls only from `ReadingWordTracker`, a small view of its own, so neither the pane nor the reading view is updated for a new word. The tracker hands the word to `ReadingWordCells`, which finds the text holding it by binary search over where the texts' first words start and sets that text's `ReadingWordCell` (observed only by that text, `ObsidianMarkdownText`) and clears the previous one; callouts that open for the word read `current`. Following the word keeps the highlight frames, the viewport and the scroll proxy in `ReadingFollowState`, outside the view's state. The build request is compared, not hashed (`ReadingBuildRequest`), and `ReadingNoteBlocks` holds values and a `ReadingBlockActions` object of stable identity, which SwiftUI compares with `==`; it is not wrapped in `.equatable()`, which makes it one view to the lazy stack, and every block of the note is then made at once. Measured in hosted tests on a 0.8 MB note (2,600 blocks), Debug build on the simulator: under 1 ms of main-thread time per word with words changed twenty times a second (19 ms before; 900 ms with every block made at once), and the main thread busy 3 % of the time while the note is read aloud for real (20 % before).

## Scaling to 10,000 and 100,000 files

1. Separate discovery from content indexing. Enumerate metadata incrementally; never preload every note body or every PDF. Skip hidden configuration, Git internals, symbolic-link cycles, and packages unless explicitly supported.
2. SQLite with FTS5 indexes searchable text. B-tree indexes support paths, basenames, tags, aliases, and links. Search returns a bounded page (normally 50), with cancellation/debounce. No full-table Swift filtering on each keystroke.
3. Scan in bounded batches with backpressure. Keep an inventory generation and prune missing records only after a successful scan. A canceled or failed scan must not purge the index. Track modified metadata, then read only changed notes; hash only open documents. Reconcile changes missed while suspended. Today a scan checks enumerated files 256 at a time, reads each batch's changed notes under one file coordination without hashing them, and parses them outside the index actor; it asks for the iCloud download state only for changed notes it would read. Batches are limited to 64 files or 4 MiB of note text. A note saved during a scan is written with the scan's generation and is never pruned or overwritten by the scan's older reading. A name that `VaultPath` rejects, or a failed write of one file, does not block pruning, and notes that are too large, not downloaded or not UTF-8 are not read again until they change. Link queries (resolve, backlinks, file counts) run outside the actor and stop when their caller is cancelled.
4. Do not force-download an entire cloud vault. Inventory available metadata; mark unavailable bodies as pending. Prioritize the current folder, open note, and explicit searches. Report partial search coverage.
5. Navigation expands only requested folders. For huge flat directories, serve paged directory results from the inventory. A first cold listing can still cost O(n) with Foundation's directory API; measure it and replace that adapter if it becomes material.
6. UI observes visible slices and individual document state. No global array of rich Note objects. Bound open editor sessions and release inactive PDF documents after saving. Today PDFs are bounded: hidden tabs keep at most the most recently visible PDF open, and older hidden PDFs are released after a successful save (never with unsaved edits, a save running or a conflict) and reopen at the same page, without their undo history. Hidden note sessions (their text and state) are not bounded yet; their native editors are, by `MarkdownEditorRetention`.
7. PDFKit renders visible pages. Per-page overlay providers allocate Pencil canvases on demand and release offscreen canvases. Thumbnails require a byte-budgeted cache and cancellation. Never rasterize a whole textbook.
8. Parse the active Markdown document on a worker and debounce derived updates. Native text input must not wait for preview, link indexing, or image decoding. Large single notes are a different benchmark from many small notes.
9. Record to disk continuously. Never buffer a lecture in memory. Recording finalization and file-provider publication must not block input. Keep a normal recoverable media file until publication succeeds.
10. Instrument signposts for open, first editable frame, search, indexing, PDF save, and drawing export. Limit worker concurrency during handwriting and recording; QoS alone is not a resource budget.

### Proposed performance budgets (targets, not measured promises)

On a representative supported iPad: warm note navigation p95 under 150 ms; search first 50 results p95 under 100 ms after debounce; typing main-thread work under 8 ms per update; browsing/indexing incremental memory under 150 MB excluding active document and system PDF caches. Measure Pencil responsiveness on physical hardware. Set image/thumbnail byte budgets relative to device memory. No claim of 100k-file readiness until on-device mixed-vault tests pass.

Benchmark 10k and 100k Markdown files; 100k mixed file inventory; huge flat folders; 1k-page PDFs; a multi-hour recording; large single Markdown notes; non-downloaded cloud files; rapid navigation; external edits during save. Report cold/warm times, peak memory, p50/p95, hardware, OS, and coverage. A 100k-row synthetic index benchmark alone does not validate a 100k-file cloud vault.

## Reuse assessment

- Apple: SwiftUI navigation, TextKit native editing, Foundation file coordination/presentation/bookmarks, PDFKit rendering/annotations, PencilKit capture/tools, ImageIO PNG decoding, AVFoundation recording/playback, OSLog instrumentation.

- [Textual](https://github.com/gonzalezreal/textual), MIT: selected native rendering library; supports math and block rendering. Inspected README, package manifest, source and license. Requires iOS 18/macOS 15. UIKit/AppKit remain the text input layer. Vendored in `Vendor/textual` with eleven documented patches (`GRAPHITE-PATCHES.md`): math keeps its natural width (formulas alone in a table cell were garbled, and `E = mc^2` wrapped its exponent), list item styles can see the item's content (task checkboxes replace bullets), a public inline-math measuring and drawing helper for the Live Preview editor, Obsidian's inline-math delimiters (so "$5 and $10" is not a formula), unparseable formulas left as text, no isolated-conformance warnings from attachments, a table layout that fits the width it is offered (columns sized as a browser sizes them, images sized to their column), empty table cells that keep their row and column, explicit formula colors, a way for controls inside selectable text to receive touches (task checkboxes), and public display-math measuring and drawing for equations laid out with their numbers. Return to the upstream package when it has equivalents.

Return to the upstream package when it has an equivalent.
- [GRDB](https://github.com/groue/GRDB.swift), MIT: selected SQLite access/migration layer, using SQLite FTS5. Database is disposable.

- [FSNotes](https://github.com/glushchenko/fsnotes), MIT: inspected Storage, Note, Markdown and file watcher organization. Useful file-based reference, but its global in-memory note collection and application-specific bundles are not Graphite's architecture. No source copied.

- [SwiftMarkdownEngine](https://github.com/nodes-app/swift-markdown-engine), Apache 2.0: compelling native editor, but currently AppKit-specific and its wiki-ID storage semantics must not leak into Graphite. Reassess reuse for the macOS editor.

## Technical risks and choices to review

- PencilKit brushes are richer than standard PDF ink (texture, pressure, variable opacity, masks). Each stroke is saved as standard `/Ink` with its centre line in `/InkList` and, as its appearance stream, the variable-width outline from `StrokeOutliner`, so readers that draw appearance streams (PDFKit, Quick Look, Poppler, Ghostscript) show the width variation, and readers that redraw ink from `/InkList` fall back to the average width. Texture and opacity masks are still simplified; never advertise exact fidelity. Validate lasso, transparency and metadata removal against Preview and another PDF renderer.
- PDFKit overlays already rotate with pages. Overlay-local coordinates should not be rotated a second time. Isolate view-to-page mapping and test crop-box origins, all right-angle rotations, zoom, and round trips.
- Whole-file PDF replacement costs scale with file size. PDFKit offers no simple guarantee of incremental updates. Background saves, batching and visible save state help, but a very large PDF still requires free space and I/O time.
- PNG editing has a fundamental pixel-memory cost. Enforce canvas/export budgets before allocation; retain the original on encoding failure. A huge handwriting canvas should become PDF pages rather than an unbounded PNG.
- iOS cannot guarantee ongoing arbitrary indexing or camera recording while backgrounded. Audio recording can use the audio background mode with user authorization. Handle interruption and explicit resumption. Video background restrictions must be reflected honestly in the UI.
- Obsidian plugin execution compatibility began on 2026-10-10, at the owner's request (`Docs/Community-plugins.md`). Plugins run in one `WKWebView` per vault, in WebKit's content process, so their JavaScript never runs on the app's main thread; Graphite starts it only when the person has turned community plugins on for the vault and enabled at least one. While no panel shows it, the web view stays in the window, invisible, because WebKit slows the timers of a page outside a window to about one a second. The runtime reimplements the `obsidian` module rather than embedding Obsidian. Since 2026-10-12 plugins also reach Graphite's native surfaces (`CommunityPluginReadingBlocks.swift`, `CommunityPluginMenus.swift`, `CommunityPluginTyping.swift`, `CommunityPluginViews.swift`, and `community-plugin-runtime-reading.js`): code blocks a plugin draws (in the reading view and, as in Obsidian, in Live Preview), parts of a note its post-processors change, and its views are laid out in the runtime's page (sections and blocks off to the side, transparent; views at the size of their tab or sidebar panel) and shown in the note, tab or sidebar as copies in small web views that run no page script (`allowsContentJavaScript` off; Graphite's own script, in its own content world, measures the copy, patches it in place and reports taps, typing and keys by element path, which the runtime replays on the plugin's element; context menus, hovering and drags are forwarded where the plugin listens, which the runtime marks on its elements as listeners are added). A `MutationObserver` sends each change of a shown block or view, gathered over 60 ms; copies are capped at 4 MB and Graphite keeps the last 64. File, folder and editor menus ask the runtime for plugins' items when they open (the editor's edit menu through `UIDeferredMenuElement`, the Mac editor's context menu before it opens; SwiftUI's list menus through a "Plugin Actions…" dialog, since they cannot wait); the focused note's text goes to the runtime at each change and cursor move while plugins listen (`editor-change`, `EditorSuggest`), in order, capped at 512 KB, and their suggestions appear in Graphite's completion list. Files a plugin shows in its own view (its registered extensions, or notes it claims by patching `setViewState`, as Excalidraw does) open in a tab that shows the runtime's web view itself, live, so drawing, Apple Pencil and gestures reach the plugin; the one web view is live in one tab at a time, and a live view beside it keeps a picture of itself until tapped; the views shown in tabs and the sidebar are saved with the vault's tab layout (type and state, as Obsidian's workspace) and opened again once the plugins load; plugins' Bases view types show the same way inside Graphite's base; pastes and drops go to plugins that listen before Graphite handles them; and views split from the note open on the other side of Graphite's split. Links whose action a plugin registered (`graphite://advanced-uri?…`) are handed to that plugin; plugins' `window.open` and clipboard go through Graphite, because WebKit gives the hidden plugins' page neither; a plugin's notice offers its buttons on Graphite's toast; and each plugin's load result and failures go to the unified log (`CommunityPlugins`). Every message Graphite waits on has a timeout (2 seconds for menus, 4 for typing, 5 for taps, 20 for drawing a block), so a plugin that loops or never answers leaves a block saying so, a menu without its items, or no suggestions; the app's main thread never waits. The largest compatibility risks remain structural: Graphite's editor is native, so CodeMirror editor extensions (Live Preview decorations, keymaps, autocompletion) do not run, and code that needs CodeMirror's editor view fails saying so; Obsidian's undocumented internals are only partly provided (a sweep of 48 directory plugins on 2026-10-12 found 16 working, 13 partly and 17 blocked, mostly by these and by Graphite's native interface, which plugins cannot take over; `Docs/Community-plugins.md`); copies of blocks and views pass a finger's drag only for elements marked draggable; and plugins have the access they have in Obsidian (every file of the vault, the network), which the consent switch, the vault boundary and revision-checked writes bound but do not sandbox further. In the iPad simulator, the metadata of 5,000 notes was read in 8.5 seconds with the app's main thread idle 97% of the time; the runtime's memory, its start-up time on a device and vaults of 100,000 notes are unmeasured. Universal compatibility remains a goal, not a verified state.
- TextKit 2 estimates the height of text it has not laid out, and the estimates change as it lays out more. Live Preview's views follow laid-out fragments and are placed again when heights change, but a large jump can briefly show them misplaced. A layout pass that never runs again after TextKit's final relayout is the failure mode to watch.
- Graphite requires iOS 27, iPadOS 27 and macOS 27 (the owner's floor), so no code branches on an older system. macOS 27 runs only on Apple silicon; TextKit 2 there reports each layout of the viewport, on which the editor places its rendered blocks. Pencil capture remains device/platform dependent; macOS can view/edit other document content.
